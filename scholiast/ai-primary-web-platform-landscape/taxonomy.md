# Taxonomy: AI-primary web-platform approaches

**As of 2026-08-22.** Source IDs resolve through [`sources.md`](sources.md). “Substantial” describes evidence and implementation depth, not fitness for Amanuensis.

## Bottom line

The state of the art is not one framework. It is a layered architecture:

1. pre-render a semantic document and durable links;
2. make the document complete before client code runs;
3. add local, bounded enhancement at stable DOM boundaries;
4. introduce a data runtime or component framework only when a measured interaction crosses a threshold;
5. keep the generated artifact independently inspectable and test it as a projection.

For a read-mostly reorientation surface, standards-native generated multi-page HTML remains the strongest default. Static-site compilers, reactive data-document systems, and specialist browser analytics are substantial alternatives, but each earns its extra build/runtime contract only for a narrower need. The evidence does **not** support “choose the framework the model has seen most” as a general rule.

Copy-owned registries are a substantial addition to the landscape, but they occupy a different layer: they acquire and customize source. They do not choose static versus client rendering, eliminate package primitives, or certify the emitted DOM. Their best AI-primary mechanism is inspectable local source plus structured retrieval/diff tooling; their compensating costs are more repository context, semantic ownership, drift integration, and provenance review (C019–C026).

## Operational classifications

An approach is **substantial** here when it has all of: a documented mechanism beyond syntax sugar, a current usable release or stable browser primitive, clear license/provenance, an implemented artifact path, and credible maintenance/testing evidence. It may still be mismatched.

An approach is **thin** when the implementation is real but the differentiating mechanism is narrow, project continuity is concentrated, or the value over a smaller platform primitive is not established. Thin does not mean bad.

An approach is **unreliable** when a load-bearing claim rests on promotional comparison, one-run benchmarks, implicit CDN/`latest` resolution, unclear output behavior, or an unmaintained/ambiguous dependency. Reliability is claim- and configuration-specific; this survey does not label a whole mature project “unreliable” from one defect.

**AI-legibility** is evaluated by inspectable mechanisms, not vibes: source-to-DOM correspondence, locality of behavior, number of indirection layers, explicit state/event boundaries, stable platform vocabulary, generated-code ratio, reproducible build inputs, and the ability to validate output independently. These are proxies. No controlled evidence found here establishes a universal framework ranking for AI authors/readers.

## What “AI-primary” changes

The strongest available empirical evidence is cautionary rather than prescriptive:

- Web-Bench’s 50 sequential web projects remained difficult for its benchmark agent; this supports stronger validation gates, not a winning framework (S026).
- A preregistered 151-participant Java experiment found no systematic downstream maintainability advantage or disadvantage for AI co-developed code; it does not transfer a framework ranking to front-end agents (S030).
- An observational preprint found humans performed most subsequent maintenance of agent-generated files; provenance and human-readable output remain necessary (S031).
- FrameBench is useful as a proposed protocol, but its disclosed one-run-per-combination design, one-commit repository, training-distribution bias, and app-only candidate set make its current comparative results too weak for this decision (S027).
- DesignBench found framework-specific syntax/reuse limitations and weak issue detection in its design-to-code tasks; ComUICoder treats component reuse and consistency as a problem to solve rather than an automatic model behavior; A11YN starts from measurable accessibility failures and improves them with explicit automated penalties (S066).
- None of those studies compares copy-owned registries against package-owned components or native templates for long-lived repository maintenance. Registry “AI-ready,” skill, or MCP support is therefore a tool affordance, not a demonstrated net correctness or maintainability advantage (C026).

Accordingly, Amanuensis should optimize for **validation leverage**: a smaller vocabulary, complete pre-JS HTML, deterministic output, structural read-back, link traversal, accessible-name/keyboard tests, and narrow enhancement boundaries. Familiarity to a model is not allowed to override those controls.

## Unreliable patterns to reject regardless of framework

1. CDN or `@latest` dependencies in a supposedly durable report build.
2. Client-only rendering of primary prose, tables, navigation, or status.
3. “Accessible by default” claims without testing the authored result.
4. One-run AI framework benchmarks used as rankings.
5. Stars, download counts, or a recent tag used alone as project-health evidence.
6. “Static,” “offline,” “self-contained,” or “lightweight” without the four-axis definitions in [`vocabulary.md`](vocabulary.md).
7. A large client query/runtime engine when the questions can be answered during generation.
8. “Own the source” used to hide package-owned primitives, CSS compilers, or application frameworks.
9. Mutable third-party registry addresses, unreviewed dependency declarations, or overwrite-based upgrades without captured payload provenance and a clean diff.
