§Cache coherenceT2 (Cache Coherence Failure)

concern CC-1

Review in
C-01, D-01, D-02, D-03, K-01, M-01, M-02, M-03, M-04, M-05, M-06, M-07, M-08, P-01, P-02, P-03, P-04, R-01, R-02, R-03, R-04, R-05, W-01, W-02, W-03, W-04, W-05, W-06
The code-index sidecar caches parses keyed by (blob_sha, lang) under an extractor_id directory. In mcp-server/src/code-index/store.ts and extract.ts, check that extractor_id changes whenever the grammar wasm, the queries/*.scm files or the extractor logic change, so a stale generation is never served after an upgrade; and that generation garbage collection (collectStaleGenerations) cannot delete a generation another process has open.

concern CC-2

Review in
C-01, D-01, D-02, D-03, K-01, M-01, M-02, M-03, M-04, M-05, M-06, M-07, M-08, P-01, P-02, P-03, P-04, R-01, R-02, R-03, R-04, R-05, W-01, W-02, W-03, W-04, W-05, W-06
A reconciliation stands only while its ledger, scope and exclusion digests match the store. In mcp-server/src/tools/git.ts (detect_changes) and the readers that test standing (update_subsystem_status to mapped, materialize_docs, get_dashboard), check that every writer of ledger rows, scope rules, sorting rows and retirements changes an input of those digests, so no write leaves a reconciliation standing that no longer describes the store.

concern CC-3

Review in
C-01, D-01, D-02, D-03, K-01, M-01, M-02, M-03, M-04, M-05, M-06, M-07, M-08, P-01, P-02, P-03, P-04, R-01, R-02, R-03, R-04, R-05, W-01, W-02, W-03, W-04, W-05, W-06
Derived state (SQL views such as file_standing and finding_state_current in mcp-server/src/schema.sql, dashboard counts, standing.ts, and the materializer's read model) is computed from append-only tables. Check that each derived reader selects the newest effective row the same way the writers define it, so a superseded claim, withdrawn scope row or retired ledger row is never still served as current.

§ConcurrencyT8 (Concurrency Race Windows)

concern CR-1

Review in
C-01, D-01, D-02, D-03, K-01, M-01, M-02, M-03, M-04, M-05, M-06, M-07, M-08, P-01, P-02, P-03, P-04, R-01, R-02, R-03, R-04, R-05, W-01, W-02, W-03, W-04, W-05, W-06
The server is single-threaded but several server processes can share one store (several agent sessions in one worktree, or AMANUENSIS_STORAGE_ROOT). Check which read-then-write sequences in the tools span more than one SQLite transaction (check-then-insert on unique keys such as vocabulary terms keyed across the store, subsystem status advances, write_locks acquisition in tools/locks.ts) and what an interleaving second process does to them.

concern CR-2

Review in
C-01, D-01, D-02, D-03, K-01, M-01, M-02, M-03, M-04, M-05, M-06, M-07, M-08, P-01, P-02, P-03, P-04, R-01, R-02, R-03, R-04, R-05, W-01, W-02, W-03, W-04, W-05, W-06
The Python materializer reads memory.db read-only while a server may keep writing. Check in materializer/amanuensis_materializer/db.py and core.py whether one render reads inside a single read transaction (one WAL snapshot), so pages built in one run cannot mix records from before and after a concurrent write, and how read-back then compares pages with the store.

concern CR-3

Review in
C-01, D-01, D-02, D-03, K-01, M-01, M-02, M-03, M-04, M-05, M-06, M-07, M-08, P-01, P-02, P-03, P-04, R-01, R-02, R-03, R-04, R-05, W-01, W-02, W-03, W-04, W-05, W-06
Two processes may create or garbage-collect shared sidecars at once: the code-index generation directories and the call-log sidecar under the storage directory. Check in code-index/store.ts and call-log.ts that creation is idempotent under a race (busy handler, create-if-absent) and that cleanup never removes a generation or file another process has open.

Tool handlers in mcp-server/src/tools/*.ts often write several rows and then validate. Check that a failure in the child process, the read-back or the promotion leaves the previous docs/ intact, removes the staging directory and records no receipt claiming a clean publication; and that the Python side (materialize.py, readback.py) exits non-zero on every failure it detects.

Review in

Check that a failure part-way through a multi-client install or a repair --apply-plan leaves each file either unchanged or fully rewritten, with its backup, and that the exit status reports the partial result.

Two worktrees of one repository share a project_key but must get separate stores. In mcp-server/src/scope.ts and the write guards (add_evidence, add_files_to_scope, explanation/narrative writers), check that a path excluded at one revision and present under another name or status at the cited revision is judged consistently, and that the include/exclude specificity and tie-break rule is the same in the TS resolver and in dev/check-store-fully-surveyed.mjs.

Symbols are named by bare or qualified name and resolved per revision. In mcp-server/src/tools/evidence.ts and code-index/search.ts, check that a symbol resolved to one definition at ref_sha is stored as that revision's symbol_id, and that find_symbol references matched by name are never treated as call sites or anchors in another revision or file.
