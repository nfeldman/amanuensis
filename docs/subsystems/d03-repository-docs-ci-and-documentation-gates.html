Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Repository docs, CI and documentation gates

§Purpose

The GitHub workflows test the server, the materializer and the installed package on every branch push, and publish @gruetech/amanuensis to npm when a v* tag is pushed; that run checks the packed artifact, which runs the MCP compatibility test on the installed server, not the full suite. The dev/ documentation gates check the README, HISTORY, backlog and roadmap against the code and the plans.

Recorded at 94d98773. 5 of its 8 cited files changed since: .github/workflows/test.yml, INSTALLATION.md, README.md, dev/test-code-index-docs.mjs, dev/test-scope-docs.mjs.

§Scope

The README, installation, contributing, history and licence, release notes, root configuration (.gitignore, .mcp.json, .tool-versions), the GitHub workflows, and the dev gates that check docs, backlog items and the roadmap against code.

§How it works

There are four GitHub workflows. Three test and ship the npm package @gruetech/amanuensis, and pages.yml deploys the docs/ directory to GitHub Pages. Documentation gates in dev/ check the wording of the README, INSTALLATION, HISTORY and BACKLOG against the code and the design plans.

test.yml runs on every branch push and on pull requests to main, never on tags. Its mcp-server job runs on the Node 24.18.0 and Python 3.12.13 that .tool-versions pins. Other jobs cover the materializer on Python 3.11 and 3.12.13 and the packed tarball on Node 20 and 22. The roadmap gates run only locally, as the workflow's header says. dev/render-roadmap.mjs validates dev/roadmap.json against the pinned practice catalog and regenerates ROADMAP.md, and its sabotage test is dev/test-roadmap.mjs. No workflow runs either.

Pushing a v* tag starts publish.yml. It requires the tag to equal v plus the version in mcp-server/package.json. It then runs npm ci, an audit that fails only on critical advisories, and the packed-artifact test, and publishes under the latest dist-tag. It does not wait for the tests workflow. published-smoke.yml is run by hand: it installs a published version and drives its CLI and server.

A documentation gate reads a live document, checks its text against facts read from source, a manifest or a plan, and prints one GATE line. Most checks are substring and regex matches. The gates that run in CI are the backlog gates (O0, SO0, SI0, SC0), the skill-text gates SI9, SC8, O10 and SO10, SI11 and SC9, all in the mcp-server job. SC9 compares README and HISTORY with start copies in dev/fixtures/scope-docs/start/, each pinned by sha256. README's Trust section must differ from its copy by exactly one inserted sentence. HISTORY must stay byte-identical from the 0.2.0-beta.7 entry down. Any other edit to that section or those entries fails the gate.

Recorded at 94d98773. 3 of its 11 cited files changed since: .github/workflows/test.yml, dev/test-code-index-docs.mjs, dev/test-scope-docs.mjs.

§Structure

The subsystem's GitHub workflows test and publish the package, and its dev/ scripts check the project's documents against the code. .tool-versions pins Node 24.18.0 and Python 3.12.13, the same versions the main CI job installs, and .mcp.json starts the checkout's own server through mise exec.

Each workflow has its own trigger, and none waits for another. tests runs on a push to any branch and on pull requests to main. It has four jobs: the server suite, the materializer suite on Python 3.11 and 3.12, the packed tarball installed on Linux and macOS, and a build on Node 20 and 22. publish runs when a v* tag is pushed. It requires the tag to match the version in mcp-server/package.json, then publishes to npm. published smoke is started by hand. It installs a version from npm and checks the command-line entry points, the client adapters and lazy repository binding.

A documentation gate reads part of a live document and compares its wording with the code, a design plan or a frozen copy. It prints one GATE line, green, or red with a reason. The backlog gates (O0, SO0, SI0, SC0), SI11 and SC9 run as steps in the server job. SI11 and SC9 also check that test.yml runs the gates their plans list. SC9 compares README and HISTORY with start copies kept in dev/fixtures/scope-docs/start. Each copy is pinned by sha256, so the gate needs no Git history. render-roadmap.mjs validates dev/roadmap.json against the pinned practice catalog and regenerates ROADMAP.md. test-roadmap.mjs runs it over altered copies of the roadmap and checks that a selection of its rules fail when broken, among them dependency cycles, practice coverage and release claims.
