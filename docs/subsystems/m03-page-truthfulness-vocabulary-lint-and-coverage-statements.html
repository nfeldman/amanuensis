Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Page truthfulness: vocabulary, lint and coverage statements

§Purpose

Keeps the pages from claiming more than the store holds. vocabulary.py, generated from the vocabulary contract, supplies labels, meanings and the SQL for open findings and obligation-bearing files. lint.py withholds recorded prose that asserts survey status or states a count as a fraction; the server runs the same check on writes. Tests check page counts and placeholders against the store.

Recorded at 94d98773. 1 of its 6 cited files changed since: materializer/amanuensis_materializer/vocabulary.py.

§Scope

The materializer's vocabulary and render-time lint, and the tests that hold what pages say about coverage, freshness, ledgers, claims, history and placeholders to the store.

Start here materializer/amanuensis_materializer/vocabulary.py, then materializer/amanuensis_materializer/lint.py

§Survey note

11 files, about 12,000 lines, mostly tests. Concerns SE-3, concern SE-4.

§How it works

orientation_violations in lint.py masks code spans and fenced blocks, then refuses a forbidden term after a copula whose subject is "this codebase", "this project", "the conspectus", "the survey", "the documentation" or a one-letter id such as M-03. It also refuses a slash fraction whose part is no larger than its whole, unless it is part of a chain like 0/1/3. composite_index_violations refuses a bare percentage, or a ratio after a score-like label ("health", "grade"). It withholds only the project purpose, and also runs over the whole text of the Overview and About this survey.

The render is authoritative. It lints every explanation and narrative again (all but a declined project purpose, whose reason prints unchecked), prints explanation_refusal's sentence in place of a refused body (THESIS_REFUSED, or THESIS_REFUSED_COMPOSITE for the project purpose), and fails the publish. Read-back imports the same sentences, so page and check share their wording. The server's writers also run orientation_violations, in a python -I child (mcp-server/src/orientation-lint.ts), and refuse a write it flags; if that child cannot run, the write goes through.

vocabulary.py is generated from the vocabulary contract by gen-vocabulary.mjs. Never edit it by hand, because CI's --check fails on any byte difference. The lint's nine forbidden terms come from it, as do each enum value's label, meaning and cannot_justify sentence. The renderer splices its OPEN_FINDING_SQL and OBLIGATION_BEARING_SQL into its queries, read-back only the latter, so the pages count open findings and obligation-bearing files as the server does.

The nine tests check what the pages say about coverage, freshness, ledgers, claims, history and unfilled slots against the records they were seeded with. Each seeds stores from the real schema.sql and runs materialize.py in a subprocess. The freshness gate uses get_dashboard's own subqueries from dashboard.ts.

§Structure

The rules live in two modules, vocabulary.py and lint.py, and nine gate scripts test what gets published.

vocabulary.py is generated from the vocabulary contract by gen-vocabulary.mjs, and CI fails on any byte difference, so change the contract and regenerate. It carries every enum's label, meaning and cannot_justify sentence, shared SQL predicates, and the forbidden status terms.

lint.py's orientation_violations masks code spans and fenced blocks, then flags a forbidden term only after a copula whose subject is the survey, the conspectus, the documentation, this project, this codebase or a subsystem id. It also flags a slash fraction of two numbers, not a chain such as 0/1/3, whose part is no larger than its whole. That shape is what lets "a stale cache" and "memory-mapped" through. composite_index_violations flags a bare percentage, or a ratio after a label such as health or score.

The orientation check runs at write, render and readback. Before recording an explanation or narrative, the server runs it in a python -I child and refuses the write on a violation; if the child cannot run, the write goes through. At render, renderers.py runs it over every published explanation and narrative except a declined project purpose, and a violation fails the publish with a warning. The refused body is replaced by explanation_refusal's sentence (THESIS_REFUSED for the project purpose), and readback.py expects that same text. Only the materializer applies the composite check: to the project purpose, and at render to the whole text of the Overview and About this survey.

Bar the vocabulary-source gate, each gate seeds a store from the server's schema.sql with hand-written rows, runs materialize.py as a subprocess and compares the published HTML with expectations written into the test or read from an independent source, such as the contract or the server's dashboard SQL. Many then tamper with a published page and require --readback-only to report the mismatch.
