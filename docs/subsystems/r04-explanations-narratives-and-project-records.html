Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Explanations, narratives and project records

§Purpose

It keeps the survey's prose in the store, not in files. The prose is each subsystem's and the project's purpose and account, the longer narratives, and project-wide records such as the name and runtime crossings.

§How it works

The survey's prose and project-level facts are rows in the store, not files. The writers of explanations and narratives check each write, including the shape rules and lint below, then insert the row and its evidence links in one transaction. Nothing is updated in place: a correction is a new row, and the later of two racing writes wins.

The effective row is derived at every read, in invariants.ts, and no flag is stored. For a narrative it is the newest row for its section and topic. For an explanation it is the newest whose ref_sha is a commit in the workspace's object store, or the newest when none is bound. The materializer's Python read-back applies the same rule, and both sides' tests run explanation-effective-cases.json.

A subsystem's explanations can be recorded once it reaches Structural. The project account needs one Structural subsystem; the project purpose needs none. Subsystem narrative sections wait for their rung, from Scoped for structure to Challenging claims for challenge; project sections have none. Advancing a subsystem to Reviewing concerns or Mapped reads these rows back. reset_subsystem appends withdrawn rows, which read as not recorded.

orientation-lint.ts has no rules of its own. It runs the materializer's orientation_violations in a python -I child. If that cannot run, the write goes through and the render-time lint still withholds the text.

project-records.ts appends the project name, runtime boundaries and territory dispositions, and the newest row for each key stands. The import may write the project purpose as imported, which reads as recorded for that slot only. register_artifact (kind other only) and review-session exports upsert by path.

§Structure

The layer is a set of MCP tool handlers over append-only SQLite tables. explanations.ts holds record_explanation, decline_explanation and get_explanations, and the shape rules the other files import: the byte caps, the 64-row evidence cap, the one-paragraph test for purposes and reasons, and isStoredProse. isStoredProse tests each line outside fenced code alone for a heading or table mark and, outside code spans, an HTML tag or inline image, so a tag split over lines or a reference-style image passes.

The explanation and narrative writers check in one order: an active session, then the subject, then the body's size and shape, then the write-time lint, then the evidence where the record carries it, then the revision. A subsystem must have reached the status its slot or section requires; the project's purpose is accepted at any status. Only then is the row inserted, with its evidence links, in one transaction. A correction, or a reset's withdrawal, is a new row.

orientation-lint.ts holds no rule of its own. It runs the materializer's Python orientation_violations in a child process. When that cannot run it returns null, which every caller treats as clear, and the pages run the same lint again at render.

get_explanations leaves the choice of effective row to readExplanation in invariants.ts, which serves the newest row whose revision the bound workspace still resolves. get_narratives leaves it to readNarratives, which serves the newest row for each section and topic. contracts/explanation-effective-cases.json holds the cases for the explanation rule. Both the TypeScript tests and the materializer's Python tests run them, so the server and the pages agree on which explanation stands.

Withdrawing a runtime-boundary edge in project-records.ts appends a row flagged as withdrawn. artifacts.ts keeps the older file registry. It refuses every hand-written kind and names the record tool that replaced it. It upserts by path, which makes it the only writer here that overwrites a row.

§Vocabulary

  • narrative rung — The subsystem status a narrative section waits for: structure at scoping, concern-reasoning at concerns, challenge at adversarial; project sections have none.
  • stored prose — The text shape the store accepts for accounts, narratives and topics: paragraphs, lists, code spans, fenced code, emphasis and links, with no heading or table line outside a fence and no raw HTML or image outside code.
  • write-time lint — The server's call into the materializer's Python orientation lint before an explanation, narrative or reason is stored, so an author hears at once that the pages would withhold the text.
