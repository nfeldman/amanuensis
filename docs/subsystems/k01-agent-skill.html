Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Agent skill

§Purpose

The skill is the method an agent follows to survey a codebase through the Amanuensis server. SKILL.md routes requests to references that say which tools to call, in what order, and what the server will refuse. The skill ships in the npm package and is installed into each host's skill directory. Its dev tests check that the text matches the server's tool names, refusals and statuses.

Recorded at 94d98773. 1 of its 6 cited files changed since: .claude/skills/amanuensis/SKILL.md.

§Scope

The shipped Amanuensis skill (SKILL.md and its references), the dev tests that check its text (code index, no file writes, scope, workflow text) and their fixtures.

§How it works

The skill is the method a host agent follows, and none of it runs as code. SKILL.md has a session load the deferred amanuensis tools and bind with get_project_info(workspace) before it reads any record, then routes each request to a file under references/ or gives its steps inline. A survey runs the five phase references one phase at a time, Phases 1-4 preferably in subagents, Phase 5 in the coordinator. All state goes through server tools, and the skill has the agent write no file.

subsystem-survey.md says when each phase sets the status and what each rung needs, and this matches the gates in mcp-server/src/invariants.ts, though the concerns gate also accepts an unwithdrawn imported survey body.

Prepack copies .claude/skills/amanuensis into the npm package. The installer's findBundledSkill uses the bundled copy unless a source checkout's repository copy has a SKILL.md file.

Four gates read only the repository's copy.

  • O10 (test-skill-workflow-text.mjs) holds the status table to survey_passes in the vocabulary contract.
  • SO10 (test-skill-no-file-writes.mjs) checks that refusals quoted in <tool> refuses: ... code spans appear in mcp-server/src/tools, except pieces under eight characters or with a digit, quote mark or |.
  • SC8 (test-skill-scope.mjs) checks onboarding's seven scope steps and replays them against the built server.
  • SI9 (test-skill-code-index.mjs) compares the skill with copies pinned at 984f09b. Each non-blank line of those copies must still appear, trimmed, save the navigation lines it replaces. Added or moved lines pass that, but guidance between the code-index markers must not restrict reading or follow a colon.

R-05 (Vocabulary contract and parity checks) checks tool and argument names in name(...) code spans, registered refusals, and the ladders in SKILL.md. Other argument values and prose are checked only where a gate pins their words or allowed values or matches them to a pattern. Check such text against vocabulary.ts and the tool handlers.

§Structure

The skill is Markdown that an agent reads. It holds no state and runs no code. SKILL.md is the entry point. Its session-start steps have the agent load the deferred amanuensis tools and bind with get_project_info before it reads any record. Its routing table sends most owner requests to a file under references/ and handles others, such as resume, reinit and stop, in place. Those files are read one at a time, as the work reaches them. A survey request goes to subsystem-survey.md, the coordinator's loop. That loop sets the status and hands the first four phase references to a subagent where possible, with the subsystem id, the session id and its revision, and runs Phase 5 itself. Every result is written through the server's record tools. The server, not the skill, refuses a step whose prerequisites are missing. The references state those prerequisites so the agent meets them first. The server's locks are advisory: record writers do not check them.

Users get this directory as it was at pack time. Prepack copies it into the npm package. The installer's findBundledSkill finds it and planSkill plans its copy into each host's skill directory. In a source checkout, findBundledSkill prefers the repository copy to the bundled one.

Four gates under dev/ test the repository copy, never an installed one. SI9 compares eight files with start copies pinned by sha256 under dev/fixtures/skill-code-index/start. Each file's code-index blocks, read together, must carry its required guidance, and every start line must survive save the navigation lines they replace; added or moved lines pass. SO10 checks the tool and argument names of calls in code against the built server's schemas and each tool refuses: quote's literal runs of eight or more characters with no digit, quote mark or | against tool sources, and flags sentences telling the agent to write a .md or Markdown file. SC8 replays onboarding's Phase 0b against the built server in a scratch repository. O10 checks the status table against the contract's survey passes.

§Known defects here

4 defects here are open or awaiting verification. Each one's full record, with its evidence, is on Open findings.

  • An agent that follows open-questions.md calls resolve_open_question(id, resolution="<the person's words>") or resolution="wont-resolve", and the server refuses both. The page also tells it that record_open_question is unavailable without autoprogress, so in an interactive session it may not record a question it could have recorded. — K01-1 · Low · Open
  • SKILL.md's 'What the server refuses', where each line is said to quote what comes back, lists 'carried finding(s) have no terminal outcome'. No server tool ever returns it, so an agent can reach mapped and publish with an undecided carried finding while believing the server would have stopped it. onboarding.md 195-200 repeats the sentence. — K01-2 · Low · Open
  • concern-territories.md tells the coordinator to record a disqualified territory's condition in the onboarding report's Concern Calibration section. That report can no longer be registered, so the condition is either lost or written to a file the store never reads. — K01-3 · Low · Open
  • phase-3-concerns.md's evidence-kind ladder omits runtime-observed, which the server ranks second. Its list of finding-evidence roles omits fix-verification, which verify_finding_fix requires. An agent working from the page cannot name either value. — K01-4 · Low · Open
