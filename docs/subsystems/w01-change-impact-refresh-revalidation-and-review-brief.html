Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Change impact, refresh, revalidation and review brief

§Purpose

Keeps recorded claims in step with changing code. It predicts which claims a git range touches and, when applied, closes them at the new revision. A trigger in mcp-server/src/schema.sql opens their revalidations, which only new evidence can satisfy. A refresh run chains these steps unattended and resumes after a crash. A review brief packs one change's impact into a token-bounded context.

Recorded at 94d98773.

§Scope

predict/apply change impact, refresh runs over the stale backlog, the revalidation scheduler, and the impact-aware review brief; their tests and manifests.

Start here mcp-server/src/tools/impact.ts, then mcp-server/src/tools/refresh.ts

§Survey note

10 files. Concern IF-3.

§How it works

This subsystem closes the claims a base..head change may have broken and tracks their revalidation. predict_change_impact (impact.ts) finds the claims valid at base in the subsystems the diff reaches. It maps changed paths, with renames and copies detected, to subsystems through the file ledger, then follows xrefs and seams to a depth limit. It stores the prediction in one transaction and calls no model. apply_change_impact closes each predicted claim at head in one transaction, links the git change as contradicting evidence and records an invalidated validity event. Only it, reset_subsystem and the claim tools close claims. Marking an invalidation applied fires a schema trigger that opens one blocking revalidation obligation per claim.

plan_revalidation_run (revalidation.ts) takes those obligations and fixes limits on concurrency, attempts, tokens, cost, readable sources, write prefixes and authority; a dispatch past a limit is refused, and a violation in a landed or scored result fails the run. An obligation closes only on an accepted score that cites in-survey evidence, and closing it as revalidated also needs a replacement claim with the same key. Scoring writes no claim and clears no staleness.

execute_refresh_run and resume_refresh_run (refresh.ts) take a planned run from prediction through revalidation to a clean-publish read-back, committing each stage separately. Child ids are deterministic, so a resumed run adopts what an interrupted one already wrote. Results return through land_refresh_result and score_refresh_result, and a run completes only with a read-back bound to head. A plan outside policy, or a change to an active ledger file when no invalidation was applied, leaves the run blocked, and a blocked run cannot be resumed.

compile_review_brief (review.ts) fits one impact run's items to a token budget. Required items go in first, every inclusion, drop or block gets a trace, and each gap becomes an obligation. Publishing re-checks the stored snapshot, not live rows.

§Structure

Four tool modules share one key, the change-impact run, and pass work on in store rows.

An impact.ts prediction diffs base..head, maps changed paths through the file ledger to subsystems, walks xrefs and seams to a depth limit, and reaches findings, open questions and claims through their evidence or subject. Each claim valid at the base becomes an invalidated claim or an unaffected control, with the reason path that reached it; an unexcluded path of an unmapped change becomes a gap. Applying closes each predicted claim at the head with contradicting evidence and an invalidated validity event. A schema trigger, not this code, opens one blocking revalidation obligation per applied invalidation.

revalidation.ts plans work for an outside provider, then dispatches, lands and scores its attempts. A plan compiles a packet per obligation (the claim, its allowed evidence, the impact neighborhood) and fixes bounds on providers, authority, writes, concurrency, attempts, tokens and cost. An accepted score closes the obligation only over in-survey evidence, and a revalidated outcome needs a replacement claim already recorded; scoring writes no claim. Dispatch refuses requests past bounds; a landed overrun or boundary breach fails the run as a protocol violation.

refresh.ts runs the chain unattended: impact's predict and apply, revalidation's plan and dispatch, then reconcile, a resolution audit and a clean-publish read-back. It advances refresh_runs.status after each stage. Stages commit separately under ids derived from the run, so resume adopts what a crashed run wrote. A run with no invalidations blocks if the range changed active ledger files no obligation owns. Refresh clears no staleness.

review.ts compiles a brief from an impact run. Items fall in fixed sections and are filtered by context profile, then added greedily, required first, until the token budget is full. A required item that does not fit blocks publication and opens a blocking obligation. Publishing checks the stored snapshot, not live state.

§Vocabulary

  • change-impact run — A stored prediction of which claims, findings, seams and obligations a commit range reaches, which apply_change_impact can then turn into claim invalidations.
  • revalidation obligation — A blocking work item, one per invalidated claim, that a revalidation run dispatches to a provider and closes only when an accepted score cites in-survey evidence.

§Known defects here

5 defects here are open or awaiting verification. Each one's full record, with its evidence, is on Open findings.

  • A refresh run can complete without an obligation even though the range changed active ledger paths. If git diff fails or times out in the unowned-drift guard, the run sees no changed paths and never blocks. — W01-1 · Low · Open
  • land_refresh_result marks the refresh dispatch 'landed' even when the underlying landing was refused. A second land call on an attempt already scored or failed returns ok:false, but rewrites that attempt's outbox row to 'landed'. — W01-2 · Low · Open
  • A revalidation attempt can report a written artifact or consulted source such as src/../secrets and pass the write and read boundary checks for prefix src/. — W01-3 · Low · Open
  • The review brief can present closed or expired records as current, in two ways. Under the integral-head profile it lists findings with status confirmed-bug as "current high-severity system risk" even when their resolution state is accepted or fixed. And a git error in its ancestry check makes an expired claim read as valid at the reviewed revision. — W01-4 · Low · Open
  • If any one claim in the store names a revision git cannot compare, for instance after history was rewritten, predict_change_impact fails outright for every range. — W01-5 · Low · Open
