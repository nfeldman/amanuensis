Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Page renderers

§Purpose

The renderers.render_* functions turn the survey store into published pages. Each reads memory.db and returns a page model (page.py) and hashes of sources it read; the manifest re-renders when these or the model change. The HTML writer in M-04 (HTML projection, search index and diagrams) lays the model out and escapes text; diagrams.py escapes its SVG.

Recorded at 94d98773.

§Scope

The renderers that turn store records into page models, the page and prose builders, and the cross-reference resolver; the conversion, record-page, narrative-placement, severity, xref and prose-retention tests.

Start here materializer/amanuensis_materializer/renderers.py, then materializer/amanuensis_materializer/xref.py

§Survey note

14 files, about 14,000 lines (renderers.py 5,981). Concern TR-2.

§How it works

Each published page is built by a function in renderers.py: a render_* function, or record_page for the onboarding record, review checklist and first reading path, which defers to legacy_prose.imported_page when only an import exists. M-01 (Materializer entry, read model and publication)'s page plan calls it with a read-only SQLite connection and the storage path. It returns a RenderResult, which is a page model plus a dict of source hashes. It writes neither HTML nor the store. The model in page.py is a tree of frozen dataclasses, a Page of nodes typed by the unions Block and Inline, that hold raw record text.

Renderers query memory.db directly. They read the current claims (valid_until_sha IS NULL), the finding_state_current and finding_resolution_current views, and ledger rows narrowed by survey_filter. Effective explanations and narratives come through readback's helpers (M-05 (Publication read-back)). Record values are bound as parameters, and the SQL text interpolates only constants.

Most record text is set into inline-markdown strings and parsed by prose.parse_inlines or render_prose; an Overview subsystem name goes straight into a Link node. _html_href turns any link scheme other than http, https, mailto or # into #. Before a recorded explanation is printed, M-03 (Page truthfulness: vocabulary, lint and coverage statements)'s orientation lint runs on it, in _published_explanation or, for the project purpose, in readback's project_purpose_text.

M-01 then passes each model through xref.resolve_model. It turns whole-token record ids into relative links, longest first, and an id that names the current page into bold text, except in the middle of a bold run, where it is left plain and the run is split around it.

The test-store-only-convert-* scripts rebuild fixture stores from memory.sql and compare each page family with golden HTML written by M-07 (Golden corpus generator and rebuildable goldens).

Recorded at 94d98773.

§Structure

Each page is built by one function in renderers.py, which returns a page model and hashes of the store sources it read. The manifest uses the hashes to tell which pages a change touches. No renderer writes HTML. M-01 calls each renderer with a read-only connection, passes the model through xref.py's resolve_model, and hands it to M-04's writer. The renderers share one mutable cache, of parsed imported bodies.

page.py holds the model: frozen dataclasses for inline nodes, block kinds and the Page. Record text stays raw in Text and CodeSpan nodes, and only the writer escapes it. Most text enters the model through prose.py, which reads an inline-markdown subset. The only raw HTML it keeps is marker comments and id-only anchors, and a link with a scheme other than http, https or mailto becomes "#".

The renderers query the store with SQL that interpolates only constants and binds record values. Effective explanations, narratives and the finding lenses come from readback (M-05), and labels and predicates come from the generated vocabulary (M-03). Explanations and narratives, bar a declined project purpose, pass the write-time lint again: a refused body becomes its refusal sentence. A store lacking a reader-lens view is refused by name; some absent newer tables read as empty.

resolve_model links each id the index holds, as a whole token and longest first, relative to the current page. An id on its own page turns bold, or plain amid bold text. Code and chips are left alone; an existing link may gain a "concern" prefix or a following name. Target pages and anchors are checked only by the read-back.

Store-only convert tests match M-07's golden pages byte for byte, bar one workspace-dependent page, and the start tree's pages but index, about and how-to-read once lineage_style.py cuts both to the article body and carries style changes across. They also fail on unexpected Markdown parser calls.
