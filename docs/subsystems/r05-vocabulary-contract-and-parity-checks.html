Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.

Reader's guide

Vocabulary contract and parity checks

§Purpose

One JSON contract defines some of the store's constrained vocabularies, each value with its label and meaning; the server and published pages use code generated from it, and the schema's CHECK lists it names must match. Checks compare the skill's instructions with the server: calls in code spans must use tools and arguments the server defines, and each registered refusal must appear in both.

Recorded at 94d98773. 2 of its 7 cited files changed since: mcp-server/contracts/conspectus-vocabulary.json, mcp-server/src/vocabulary.ts.

§Scope

The conspectus vocabulary contract and its generated TypeScript copy (src/vocabulary.ts), the generator, the evidence-vocabulary, reference-call and refusal-parity checks, the refusal-parity contract, and their tests.

Start here mcp-server/contracts/conspectus-vocabulary.json, then mcp-server/scripts/gen-vocabulary.mjs

§Survey note

9 files. src/vocabulary.ts says it is generated but it is not a D1 golden, so it is read. Concerns SE-2, concern SE-4.

§How it works

conspectus-vocabulary.json is the one source for the enums it declares, not all the store, server and pages share: each value carries its label, meaning and cannot_justify sentence. gen-vocabulary.mjs validates the contract and writes src/vocabulary.ts and the materializer's vocabulary.py from it. Edit the contract, never the copies: CI's --check fails on any byte difference. vocabulary.ts holds data only. The tool layer imports its arrays as validator lists and schema enums, and set_disposition treats positions in EVIDENCE_KINDS and EVIDENCE_QUALITIES as ranks, so their order matters. The contract declares evidence_quality same_values_as evidence_kind, and the generator requires the two lists to match in order.

The schema's CHECK literals are not generated, because schema.sql is applied to live databases on every open. --check-sql compares the first CHECK (col IN (…)) on each column the contract binds against the contract's values as a set, and fails if it compared none.

The other checks hold the hand-written skill to the server by string identity, so none of them can tell whether either side is right. check-evidence-vocabulary reads the contract, both copies and SKILL.md as text. The copies must match the contract in order, and SKILL.md's four ladders must match it as sets, less Deferred. It does not check argument values. check-refusal-parity works from the refusal register, refusal-parity.json. Each phrase must appear in its server file and its named references, which may quote part of it. Tools under refuses must state it and tools under instructs must not. A skill file that names a registered tool must carry one of that tool's phrases.

§Structure

This subsystem keeps two contracts, the shared vocabulary and the refusal register, and checks the rest of the repository against them with scripts that run in CI as separate Node processes.

conspectus-vocabulary.json declares enums the store, the server and the pages share, each value with its label, meaning and cannot_justify sentence. gen-vocabulary.mjs renders it as vocabulary.ts for the server, which loads only that file, and vocabulary.py for the materializer. Before writing anything it refuses duplicate values or labels, and any same_values_as pair whose values differ in order. Evidence kinds and evidence qualities form such a pair. With --check it compares both files byte for byte instead of writing them. schema.sql is not generated, because it is applied to live databases on every open. Instead, --check-sql compares each bound column's CHECK literal with the contract as a set. check-evidence-vocabulary.mjs reads both copies and SKILL.md as text, never by import, and holds four prose ladders in SKILL.md to the contract.

refusal-parity.json is kept by hand. Each entry ties a phrase to the file that states it, the tools that throw or document it (refuses), those whose callers must be warned (instructs) and the skill references that must quote it. check-refusal-parity.mjs reads tool definitions and handlers as text and checks each entry against the server and the skill. Each string in invariants.ts, helpers.ts or src/tools/ thrown or not an argument and opening "cannot advance", or a tool or interpolation then "refuses:" or "requires", must contain a registered phrase. check-reference-calls.mjs loads tool schemas from the built dist and requires each snake_case call in the skill's code spans to name a real tool, and each argument it parses to be one of its properties.

test-refusal-parity.mjs tests check-refusal-parity.mjs by breaking a fixture tree through --root, one edit at a time. test-reference-calls.mjs exercises the span parser and requires a run over the real skill to read at least 140 calls.

§Known defects here

2 defects here are open or awaiting verification. Each one's full record, with its evidence, is on Open findings.

  • The reference-call check's own test calls itself its red arms, but it never feeds the checker a drifted call. A checkReferenceCalls that reported no problem at all would pass every case, provided it still counted 140 calls. — R05-1 · Low · Open
  • The derived refusal scan treats a refusal message as registered when any registered phrase from any entry or file appears inside it. The register holds phrases as short as "mark needs a" (12 characters), "is limited to" and "mark takes no". So a new refusal in one of the three watched forms that happens to contain such words is not reported, even though no entry concerns it. — R05-2 · Low · Open
