Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Decisions, design sessions and codebase brief

§Purpose

Only a human or the owning system can accept a decision revision for an architecture choice. A CodebaseBrief, compiled from one review session without model calls, goes to three independent design lenses. Their options combine into at most a lean, which only advises. Decision-impact detection on an applied change-impact run opens a blocking review for accepted revisions whose premises it touches.

Recorded at 94d98773.

§Scope

Decision revisions with premise custody, dialectical design sessions, and the codebase brief with its contract and JSON schemas; their tests and fixture.

Start here mcp-server/src/tools/decisions.ts, then mcp-server/src/codebase-brief-contract.ts

§Survey note

10 files.

§How it works

Briefs compiled from a frozen source feed a design session, whose lean a decision can cite. A CodebaseBrief source is a frozen, hashed list of candidates that prepare_codebase_brief_source builds from one review session. The objective and typed constraints become required candidates. Review items, inferred intents and options become optional ones, each tagged with the brief modes it may appear in. compile_codebase_brief projects a review, design or generative brief from the source. Required and registry-named candidates go in first, then the best lexical matches up to item_limit. Each candidate left out is recorded with a reason: policy, irrelevant or budget.

plan_design_session gives three design lenses (immanent, adversarial, speculative) briefs of the matching mode, all from one source. It needs at least two model families, at least one of them different from the orchestrator's. No lens gets another's output, and none may land until all three are dispatched. Aggregation offers an advice-only lean only when one option has a strict majority of at least two lenses, rejects no highest-priority desire, leaves no exclusive desires tied and cites evidence. Otherwise the session is underdetermined.

A decision is a chain of revisions whose payloads are frozen once written. draft_decision_revision takes only direct-user desires. If it names a design session, that session must be qualified and the accepted option must be its lean. Acceptance needs a human or owning-system actor whose authority_scope covers the decision. Schema triggers enforce this rule, the frozen payload and the allowed status moves. Accepting a revision supersedes its accepted direct predecessor. detect_decision_impacts matches the claim, evidence and code premises of each accepted revision against an applied change-impact run and opens a blocking decision-review obligation, but the revision stays accepted until it is invalidated or superseded. Research, learning, the crosswalk and the Chorusmith adapter read these records.

§Structure

The three tool modules take a code review to a recorded decision through a CodebaseBrief source, a design session and a decision revision. They do not call one another: each stage reads, by id, the rows the one before wrote to the store.

prepare_codebase_brief_source builds the source from one review session. The objective and the typed constraints become required candidates, and each review item an optional one. Inferred intents and options become candidates for the design and generative modes. The list is frozen under a content hash. compile_codebase_brief makes a brief in one mode from that source. It takes required and registry_ids candidates whatever the mode, then others the mode allows by lexical score against lexical_query (default the objective), up to item_limit. Every candidate left out is listed with its reason: policy, irrelevant or budget.

plan_design_session plans three lenses over briefs from the same source: the immanent lens reads the review brief, the adversarial lens the design brief and the speculative lens the generative brief. A lens's packet uses no brief but its own, and carries the user's desires. The panel must use at least two model families. No lens output can land until all three lenses are dispatched. A landed option may cite only candidates in its lens's packet. If a strict majority of lenses prefers one option key, that option cites evidence and rejects no top-priority desire, and no exclusive desire group is tied, it becomes the session's advice-only lean. Otherwise the session is recorded as underdetermined.

If a decision revision names a design session, its accepted option must be that session's lean. Only accept_decision_revision makes a revision current, and only with an authority scope that covers the decision. Accepting it supersedes the direct predecessor if that one was accepted. detect_decision_impacts checks accepted revisions' premises against a given applied change-impact run; a match opens a blocking review obligation.

§Vocabulary

  • CodebaseBrief source — A frozen, hashed list of candidates — the objective, typed constraints, a review session's items, inferred intents and options — from which review, design and generative briefs are compiled.
  • advice-only lean — A design session's furnished preferred option, given only with a strict two-of-three majority, cited evidence and no unresolved or rejected top-priority desire; it is never a decision.
  • decision revision — One immutable proposal for a decision — desire sources, accepted option, alternatives, constraints, consequences, falsifiers, premises and code links — that only an explicit human or owning-system event can accept.
  • design lens — One of three independent architecture analyses in a design session — immanent, adversarial or speculative — each given only its own brief's sections and the desires.
  • premise custody — The typed claim, evidence and code premises an accepted decision rests on, watched by detect_decision_impacts so a change to any of them opens a blocking decision-review obligation.

§Challenge

§W03-1

W03-1 would be wrong under any of three conditions:

  • draft refused a rejected predecessor;
  • the schema allowed only one accepted revision per decision;
  • readers selected authority through current_revision_id rather than through status.

None holds:

  • draft refuses only a draft predecessor. The decisions test drafts a successor of a rejected revision and calls that reconsideration.
  • schema.sql has no unique index or trigger over accepted revisions of a decision. The monotonic trigger allows draft to accepted for any draft.
  • detect_decision_impacts selects every status='accepted' revision. The learning ledger in W-04 counts a revision as no longer live only when its status is superseded or invalidated.

The finding stands. Severity stays medium: the current pointer is right, but every status reader sees two authorities.

§W03-2 and W03-3

W03-2 would fall if invalidate read the run's status somewhere, or if a schema trigger refused an invalidated event for an unapplied run. Neither is the case. The impact_run_id foreign key only requires that the row exists. The only scope trigger fires on accepted events, so reject's scope is never compared.

W03-3 would fall if any server path validated a brief against the JSON Schema before writing schema_ok. A search of the source tree finds the schema file read only by the two test files. The insert writes the literal 1, and the validation-reconcile trigger checks semantic_ok and error_count but not schema_ok.

Both stand at low severity: each overstates a check rather than corrupting a record.
