Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Survey scope, ledger and reconciliation

§Purpose

Decides which files the survey must account for and keeps the file ledger in step with them. The survey set is a commit's tree minus excluded paths, including the owner's exclusions and the commit's own ignore files. detect_changes reconciles the ledger against that set at a revision, marking drifted or deleted files stale, and materialize_docs will not render until it has.

Recorded at 94d98773.

§Scope

The survey set (gitignore, owner rules, meta sorting) and its resolver (scope.ts, tools/scope.ts), the file ledger (tools/files.ts), detect_changes and git state (tools/git.ts), staleness (tools/stale.ts), and the scope tests and fixtures.

Start here mcp-server/src/scope.ts, then mcp-server/src/tools/git.ts

§Survey note

17 files, about 12,500 lines, most of it tests. Every mapped advance and publication depends on a standing reconciliation recorded here. Concerns CC-2, concern AT-2, concern SI-2, concern IF-3.

§How it works

Survey membership is decided by decide in scope.ts, in a fixed order. The most specific active owner rule comes first: an include keeps the path and an exclude removes it (source user). Next come the commit's ignore files (gitignore), then the most specific onboarding sorting row (meta removes the path). An exact pattern beats a prefix or glob, then more literal characters win, then the later row. A pattern without * or a trailing / matches only that path, so a directory named without the slash covers nothing under it. Ignore files are read from the commit's own blobs, so the working tree, info/exclude and global excludes never change the answer.

Until detect_changes runs, the ledger and scope_gaps still reflect the old rules. In one BEGIN IMMEDIATE transaction, it resolves the survey set at the commit and marks ledger rows stale as git-drift, absent or unverifiable-ref. It clears the flag on rows whose file matches again, unless absent, then rebuilds scope_gaps, advances last_checked_sha and appends a scope_reconciliations row.

That row's digests come from functions in invariants.ts. The materializer's db.py restates the exclusion digest and the reconciliation selection in Python, so both sides must change together.

Other tools write the ledger too. add_files_to_scope upserts a batch but keeps a stale row's commit; only clear_staleness moves it, and it refuses a row recorded as absent. Rows on excluded paths are kept as inactive, their stale flags unchanged. retire_ledger_file deletes an absent row, or an excluded one if others remain. clear_staleness and retire_ledger_file read the row outside the transaction that writes it.

§Structure

R-01 decides which paths of a commit a survey owes, records which subsystem owns each one, and reconciles that record against the tree.

scope.ts makes the decision. Membership follows a fixed precedence: the most specific active owner rule, then the commit's own ignore files, then the most specific onboarding sorting row. A path nothing covers is in the survey set. An exact pattern outranks a prefix or glob, so a directory named without a trailing / covers nothing under it. Ignore files are read from the commit's blobs in a scratch repository, so neither the working tree nor global excludes affect the answer.

set_scope_rule and record_scope_sorting append rows without reconciling. A later row withdraws an earlier one through supersedes. add_files_to_scope and update_file_classification write the file ledger and refuse excluded paths. Neither moves a stale row's ref_sha to another commit. Only clear_staleness does, and it records the basis of each clear in staleness_clears. A row recorded absent cannot be cleared, so retire_ledger_file deletes it instead. That tool also deletes rows on excluded paths, except a subsystem's last row, unless it is recorded absent.

detect_changes lists the tree and its ignored paths at the resolved commit. Then, in one IMMEDIATE transaction, it resolves the survey set from the stored rules and runs one git diff per distinct hex ref_sha of tracked, non-excluded rows. It marks rows stale (git-drift, absent, unverifiable-ref) or fresh again, rebuilds scope_gaps, and appends a scope_reconciliations row with its digests and the excluded paths. Ledger rows on excluded paths are kept but inactive. The standing check computes these digests the same way; publication and a subsystem's advance to mapped depend on it, unless the subsystem leaves Deferred with no parking recorded. Write guards read rules live. A new rule therefore governs writes at once, but it shows in the recorded reconciliation only after the next detect_changes.

§Vocabulary

  • exclusion source — Why a path left the survey set: user (an owner rule), gitignore (the commit's ignore files) or meta (an onboarding sorting row).
  • scope gap — A survey path with no ledger row (unledgered) or a ledger row whose path is gone from the tree (absent), rebuilt from scratch by every detect_changes.
  • stale reason — Why detect_changes flagged a ledger row stale: git-drift (content changed since its ref_sha), absent (path gone from the tree) or unverifiable-ref (its ref_sha cannot be diffed).
  • survey set — The paths of a revision's tree the survey must account for: the tree minus paths excluded by owner rules, the commit's own ignore files, or meta sorting.

§Known defects here

2 defects here are open or awaiting verification. Each one's full record, with its evidence, is on Open findings.

  • A ledger row whose file was deleted at one reconciliation and restored before the next stays stale with reason absent indefinitely, although the file is tracked again and may be byte-identical to its ref_sha. clear_staleness refuses it and tells the caller to restore the file, which has already happened and changes nothing; add_files_to_scope holds it stale. The only way out is retire_ledger_file followed by re-adding the row, which retire_ledger_file's own description says it refuses for a tracked, in-survey file. A single reconciliation from the first revision to the last would have judged the row fresh or git-drift, so the incremental result differs from the full one. — R01-1 · Low · Open
  • When a stale file's code has only moved and every claim on it still holds, a refresh can clear the file but cannot record where the cited text now is. After clear_staleness the ledger row is at the new revision, and every evidence row citing the file still names its old revision and old lines, linked to nothing at the new revision. get_stale_backlog's anchor_state reports the move only while the file is stale, so the clear erases the one signal. This is the successor to carried finding B03-R3 (store-59913eaff3daad8d), narrowed. The survey had not filed this defect before stage K. — R01-2 · Low · Open

§Challenge

§R01-1

To overturn R01-1, some code would have to re-derive or clear a stale reason of absent for a file that is tracked again. A search of the server's sources for writers of file_ledger and stale_reason finds five: detect_changes' markStale (stale=0 rows only) and markFresh (absent excluded), clear_staleness (refuses stored absent), update_file_classification (refuses to move a stale row's ref_sha), add_files_to_scope (holds a stale row's ref_sha) and retire_ledger_file (deletes). None re-derives the reason, so the row stays stale until it is retired and re-added. The derived-staleness gate's restore test covers drift and return, not deletion and return, which is why it passes. The finding is upheld at LOW: the state is wrong and the refusal's advice misleads, but it needs a delete and restore between two reconciliations and has a working, if lossy, way out.
