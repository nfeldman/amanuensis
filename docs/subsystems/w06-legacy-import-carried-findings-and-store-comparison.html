Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Legacy import, carried findings and store comparison

§Purpose

Keeps an earlier survey's work when a store is upgraded or rebuilt. The import copies an earlier version's hand-written files into the store verbatim, and fills in the project's purpose, name and runtime table where the store has none. The carry moves prior findings over, and an open one stays undecided until re-filed, ruled out or shown repaired.

Recorded at 94d98773.

§Scope

Importing an earlier version's hand-written artifacts, carrying findings from an archived store with terminal outcomes, and comparing two conspectuses; the legacy-store fixtures, their builder and the real-store acceptance script; their tests.

Start here mcp-server/src/tools/carried.ts, then mcp-server/src/tools/import.ts

§Survey note

28 files. Stage K of the lane carries 21 archived findings through the tools surveyed here.

§How it works

import_artifact_bodies copies, byte for byte, the hand-written files that an earlier version registered in artifacts. Each body keeps its sha256 and whether that still matches the registered hash. Only paths with no imported row are taken, so a rerun copies only files skipped before and a body that reset_subsystem withdrew stays withdrawn. An unreadable, non-UTF-8 or out-of-storage path goes into not_imported instead of failing the call. The import also sends the stored entry point and onboarding report, never the files on disk, to the materializer's legacy_extract, which returns the thesis, project name and runtime edges. Each value is written only where nothing is recorded yet. The thesis becomes the project purpose with the disposition imported, and an edge is skipped if any row, withdrawn or not, has the same endpoints and mechanism. It is all one transaction, and dry_run writes nothing.

The store rebuild uses the carry to bring an archived store's findings forward, each to be given an outcome. begin_carry_run records the source's archived_store_id, anchor revision and declared counts. carry_finding writes one carried finding per call, unique by store and finding id and capped at imported_count. If the archive had already closed the finding, it records the outcome archived-terminal. finish_carry_run only compares counts. Other outcomes go through record_carried_outcome. Successor-finding needs a finding filed in this session, ruled-out needs evidence collected in it, and repaired needs a commit touching a cited path plus a reading at or after it. The carry tables refuse UPDATE and DELETE, so a correction is a new outcome replacing the current one. Live and carried findings share one id namespace: add_finding refuses an id a carried record holds, and a carry onto a live finding's id reports the clash.

compare_conspectuses opens two memory.db files read-only, reports counts and subsystem overlap, matches findings by signature and shows where concern verdicts and priorities agree.

Recorded at 94d98773.

§Structure

Three tool modules, none importing another, bring an earlier version's work into the current store or compare two stores.

import_artifact_bodies copies an earlier version's registered hand-written Markdown (nine kinds) into imported_artifacts, skipping paths that already have a row. A missing file, a path outside storage or bytes that are not round-trip UTF-8 is reported, not raised. Each body records whether it still matches its registered hash. The materializer's legacy_extract, run in a Python child, reads the stored entry-point and onboarding-report bodies, never the files on disk, and returns thesis, project name and runtime rows; each is kept only where nothing is recorded. The copies and these rows are written in one transaction.

The carry, driven by the rebuild script in dev/, brings an archived store's findings into a rebuilt one as obligations to decide. begin_carry_run writes an immutable run row declaring the source and its counts. carry_finding writes one record per call, refuses any beyond the declared count or already carried from that store, and pre-records archived-terminal where the archive had closed the finding. finish_carry_run only compares the counts. record_carried_outcome decides a record later; an outcome needs a finding or evidence from this session, or a repair commit with a reading after it. The four carry tables refuse every update and delete, so a change names the outcome it corrects.

compare_conspectuses opens two memory.db files read-only and reports what they share: subsystem ids, findings matched by a (subsystem, symptom, root cause) signature since ids differ between runs, concern verdicts and priority agreement.

The fixture stores were written by the server at an earlier commit and are committed as sqlite3 dumps with their files; one has an entry point edited after registration. The import gate runs on copies, and the acceptance script runs the import on snapshots of real stores.

§Vocabulary

  • archived-terminal — The carried-finding outcome that records the archive had already closed a finding (accepted, ruled-out or verified-fixed); it asserts nothing about this store and only carry_finding writes it.
  • carried finding — An archived store's finding copied into this store as an obligation to decide, unique by (archived_store_id, archived_finding_id) and never a live finding.
  • carry run — One append-only record of a carry out of an archived conspectus: its source, archived store id and anchor, and the two declared counts (findings the source holds, records this run will write).
  • finding signature — compare_conspectuses' key for matching findings across two stores: subsystem id plus trimmed, lowercased symptom and root cause, ignoring finding ids.
  • imported artifact — A hand-written file an earlier version registered, copied byte-for-byte into imported_artifacts with its sha256 and whether it still matches the registered hash.

§Challenge

§W06-1

The finding was challenged on three points.

First, does the code close the first handle on the failure path? compare() calls openReadOnly(aPath), then openReadOnly(bPath), and only then enters the try whose finally closes a and b. openReadOnly throws on its existsSync check when path_b names no file, after a is already open, and nothing references or closes a afterwards. A file that exists but is not a database may instead fail at its first query, inside the try, where the finally closes both. So the leak is certain only for a missing path_b.

Second, is the path reachable through the server? path_b is a required string with no other existence check, and test-compare.mjs test 5 drives exactly the missing-path case and expects the throw.

Third, is the handle held forever? That depends on whether better-sqlite3 closes a collected connection. Its source sits under the gitignored node_modules and was not read, so the finding is upheld as written: the code never closes it, and at best it is reclaimed at garbage collection. The severity stays LOW because the connection is read-only and opens no transaction.
