Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Evidence, claims and findings

§Purpose

Evidence cites a file's lines at a resolved commit; a given symbol is tied to its definition if the code index reads the file. A claim is a typed statement over evidence, valid from one revision until closed there or at a descendant. A finding's resolution history is deleted with the finding on a subsystem reset. Overturning a finding or verifying its fix needs evidence from the session doing it.

Recorded at 94d98773.

§Scope

Evidence rows and their line-range and symbol anchoring, temporal claims with challenges and marks, findings with severity, status and resolution proof; their tests and shared test fixtures (cited-source, claim-key, evidence-anchors-repo).

Start here mcp-server/src/tools/evidence.ts, then mcp-server/src/tools/claims.ts

§Survey note

18 files, about 11,400 lines. Concerns SI-3, concern EP-1.

§How it works

add_evidence refuses a path outside the survey set and checks line_range and excerpt against the file at that commit. For a symbol in a language the code index parses, resolveEvidenceAnchor anchors the citation to the symbol's indexed definition before the insert transaction opens. If the index is off or cannot read the file or the span hash differs, the row is written unanchored rather than refused.

A claim is an immutable version under a claim_key, valid from its valid_from_sha until it is closed. add_claim requires every cited evidence commit to be an ancestor of the assertion commit. Key-type, state-container and flow claims also need code-verified or contract-stated evidence on the subject's own file. invalidate_claim and supersede_claim close a version at its valid_from_sha or a descendant, and only with evidence it does not already cite. A successor carries only the new evidence. Both tools refuse a closed version; the closing UPDATE itself is unconditional, and one open version per key rests on the partial unique index in schema.sql. Flow marks attach only to current flow-step claims and must rest on evidence from the step's subject file.

A finding opens as confirmed-bug or confirmed-acceptable, and add_finding writes the row and its opening resolution event in one transaction. update_finding_status moves a finding to fixed-pending-verification only with a fix_sha that changed fix_location's file. It moves it to ruled-out only if the finding has evidence tagged with the active session, whose newest row's revision becomes effective_sha. Only verify_finding_fix records verified-fixed, from in-session fix-verification evidence at or after the fix commit. audit_resolution_invariants writes nothing; for findings it checks only that fixed ones have a resolution event and verified-fixed proof.

Other subsystems use the tables directly: the status gates count claims by key prefix, describe_locus replays findings by effective_sha, and apply_change_impact closes claims itself.

§Structure

Evidence is the root record, which claims, findings and dispositions cite through link tables. add_evidence stores a citation at a resolved commit once the path is in the survey set and the lines and excerpt exist there. If the span no longer hashes or the index cannot read the file, the evidence is written unanchored rather than refused.

Claims are immutable versions keyed by claim_key, each with a validity interval. Only one version per key is open at a time, and a version closes once; the schema's partial unique index and immutability trigger hold this, not the handlers. add_claim opens a version, supersede_claim closes it and opens a successor under the same key in one transaction, and invalidate_claim closes it on new contradicting evidence. Each writes a claim_validity_events row; an overturned challenge must cite the invalidated row that closed the claim, a superseded one the superseded row. Cited evidence must be reachable from add_claim's asserted_at_sha or the other two's at_sha. Flow marks attach to current flow-step claims and lapse when the claim closes.

A finding keeps a coarse status on its row and its history in finding_resolution_events, which the tools only append to; its rows are deleted with their finding. A repair stays fixed-pending-verification until verify_finding_fix sees fix-verification evidence from the current session at or after the fix, unless update_finding_status sets another status first. audit_resolution_invariants reads these tables and reports violations without repairing them.

§Vocabulary

  • evidence anchor — The evidence_anchors row that binds a symbol-bearing citation to one code-index definition (blob, symbol_id, span hash) at its ref_sha.
  • flow mark — An append-only annotation on a current flow-step claim: commit-point, crash-point, exit, crosses-seam or trigger (step 00 only).
  • validity interval — A claim's span of commits from valid_from_sha (inclusive) to valid_until_sha (exclusive, null while current), closed exactly once by invalidate_claim or supersede_claim.
