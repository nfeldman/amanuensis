Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Activation evidence and release-readiness harness

§Purpose

In six Codex CLI runs, this subsystem shows maintainers the Amanuensis MCP server binding each run to its repository and leaving the user's Codex config as it found it. The evidence is receipts from a real Codex CLI host launching it in scratch Git repositories. A beta release-readiness report gathers them by digest, and red-gate tests show that each receipt checker refuses a sabotaged receipt.

Recorded at 94d98773.

§Scope

Development scripts that run real Codex host and operating-envelope harnesses, adopt, check and clean up their evidence, and render and check release readiness, with their red-gate tests.

Start here dev/run-codex-host-harness.mjs, then dev/check-codex-host-evidence.mjs

§Survey note

20 files. The evidence these scripts write lives under dev/activation-evidence/, which the owner excluded; survey the scripts from their own code only.

§How it works

These scripts produce and check the JSON receipts in dev/activation-evidence/, the evidence for activation initiatives A19–A26 and the A26 release decision. run-codex-host-harness.mjs (A22) and run-activation-operating-envelope.mjs (A25) drive a real Codex CLI in scratch Git repositories, so the server (P-01 (Server runtime and dispatch)) starts as a user's config.toml would start it. Each runs three hosts at once, then the rest in turn, and fails if config.toml changed, as it does when Codex trusts the scratch repositories. The cleanup scripts then back up the file and remove those entries, and adopt-codex-host-evidence.mjs builds the A22 receipt from the logs and the scratch the failed run kept. For a real-host receipt, check-codex-host-evidence.mjs also wants a sanitized stale-process log, a session read-back from each store and a parent-cd block. refresh-a22-evidence.mjs adds that block and re-stamps source digests.

For release, run-friction-free-candidate-suite.mjs runs the candidate commands in sequence, and run-friction-free-release-replay.mjs runs the package, parity, first-use and rollback tests and re-checks the committed A25 receipt without starting a host. render-friction-free-release-readiness.mjs builds the readiness report and checklist from the roadmap and these receipts. check-friction-free-release-readiness.mjs verifies their digests and counts and refuses a decision that conflates readiness with publication.

A checker prints the refusals it has collected and exits 1, but malformed JSON in a referenced file makes the host-evidence checker throw before it prints them. Its red gates are cases in mcp-server/fixtures/activation, applied with --case as JSON-pointer edits to a base receipt, and each must exit non-zero with a named error.

Recorded at 94d98773. 1 of its 13 cited files changed since: dev/test-activation-evidence.mjs.

§Structure

Each D-01 chain (A22, A25, A26) has a runner that writes a JSON receipt into dev/activation-evidence and a checker that validates it. Each checker picks its checks from the evidence mode the document under check declares. A red-gate test drives the checker over sabotaged cases from a red-matrix fixture in mcp-server/fixtures/activation. Given --case, the checker clones the fixture's base receipt and applies that case's JSON-pointer edits first.

The codex-host chain (A22) launches real codex exec runs in scratch repositories, three at once and then four in turn. It fails if the bytes of the user's Codex config.toml changed. A failed run keeps its scratch. The harness's own receipt cannot pass the checker, which requires blocks that only adoption and refresh write. The adopt script rebuilds the receipt from the saved logs and scratch stores and sanitizes the stale-cwd log. The refresh script folds in the parent-cd run and re-stamps the source digests. The cleanup script removes the scratch trust entries Codex added.

The operating-envelope chain (A25) runs six workspaces over five repositories, including a worktree, a nested launch and a parent --cd. A negative control then wraps the server in capture-activation-launch, a stdio pass-through that logs the launch arguments and the server's stderr.

The release chain (A26) starts no Codex host. Its replay reruns the package, parity, first-use and rollback tests and re-checks the committed A25 receipt. Its candidate suite runs commands in sequence, among them the A22 and A25 checkers and their red-gate tests. The renderer combines the replay and suite results with the A19–A25 receipts and the roadmap into the readiness report and a Markdown checklist. The readiness checker verifies the report's references by digest. test-activation-evidence checks each top-level receipt in dev/activation-evidence for schemaVersion 1, a unique A19–A26 initiative and source digests.

§Vocabulary

  • evidence mode — A field in a receipt or report, "real-host" or "fixture-red", that the checkers read to decide which checks apply.
