Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Lens golden pages

§Purpose

A synthetic survey for testing what the materializer publishes. test-lens-pages.py (CI gate P8) seeds it, publishes it and checks the page plan, navigation, Files index and Not yet surveyed. make-golden.py writes the same fixture to lens/ as a memory.sql dump and its HTML, which the store-only tests rebuild and compare byte for byte, except About this survey and Not yet surveyed.

Recorded at 94d98773. 1 of its 3 cited files changed since: materializer/fixtures/store-only-golden/lens/md/how-to-read.md.

§Scope

The preserved lens golden pages (HTML and Markdown, inputs and store) and materializer/test-lens-pages.py, which compares against them.

Start here materializer/test-lens-pages.py

§Survey note

63 files that must be read (62 lens pages and the test), about 11,500 lines; slightly over the 60-file guide, kept whole because the pages are only meaningful against their test.

§How it works

The lens fixture is LensFixture, a fictional project of five subsystems. Three of its paths collide under slugify and must reach three distinct file anchors. On Not yet surveyed the pair denominators read 5 of 6 seam sides and 15 of 20 concern pairs, where the global predicates read zero.

test-lens-pages.py runs in CI and builds everything under one temporary root. make_workspace commits a throwaway git tree and then a later commit, so the head differs from the checked revision. seed runs mcp-server/src/schema.sql and inserts the fixture by raw SQL, bypassing the server's writers, so the inserts still meet the schema's CHECKs and triggers, and one the fixture violates shows up as a seeding failure. The gate then runs materialize.py --clean-publish as a child process and checks the published HTML. It checks the navigation against a group table written out in the gate, not imported from NAV_GROUPS. Every assertion goes through check, which records a failure and carries on, and any failure ends the run with exit 1.

The gate never opens the committed lens/ directory. make-golden.py writes it: it loads the gate as a module, calls make_workspace and seed, and records memory.sql, inputs.json and html/. A change to the seed reaches the golden only at a full regeneration. test-store-only-model.py rebuilds a store from lens/memory.sql, renders it and compares each page byte for byte. It skips about.html and not-yet-surveyed.html, which depend on the throwaway workspace the corpus does not carry, and --recorded skips them too. about.html is not in the corpus. Nothing writes or reads the md/ tree.

Recorded at 94d98773.

§Structure

The subsystem is two parts that never read each other. test-lens-pages.py is gate P8. It seeds LensFixture, a made-up project with five subsystems. lens/ is the golden corpus built from that same seed, and the gate never opens it.

The gate first confirms that NAV_GROUPS names the five lenses in order, that PagePlan and SitePage each carry a subgroup field, and that three seeded paths still collide under slugify. make_workspace then commits the tracked tree to a throwaway git repository and adds a later commit so the head differs from the checked revision, and CHECKED_SHA is rebound to the first commit. seed runs schema.sql and inserts the fixture rows directly, bypassing the server's writers, so a trigger or CHECK added to the schema later that rejects a seeded row shows up as a seeding failure. publish runs materialize.py --clean-publish as a child process and reads the last line of its stdout as the summary. Every assertion goes through check, which records a failure and carries on, so one run reports them all. Any failure check records ends the run with exit 1 and a GATE P8 RED line.

make-golden.py loads the gate as a module and calls the same make_workspace and seed. A change to the fixture therefore reaches lens/ only when the corpus is regenerated in full. In the corpus, memory.sql is the seeded store as dumped, inputs.json holds the page plan, context, locus index and notice the HTML stage was given, and html/ holds the printed pages.

The store-only tests rebuild a store from memory.sql and compare the printed pages byte for byte, except lens about.html in one test and lens index.html in the other. They also skip not-yet-surveyed.html, which reads the tree of a workspace the corpus does not keep. --recorded skips it too, so it changes only on a full regeneration and is the one lens page that still holds folded inline assets. Nothing reads lens/md, and a full regeneration would delete it without writing it again.
