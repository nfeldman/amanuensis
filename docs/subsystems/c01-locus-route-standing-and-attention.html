Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Locus route, standing and attention

§Purpose

This is how agents ask the survey what it knows. describe_locus answers for one file, symbol, subsystem or term, and leads with its standing, so an unread or stale file is not mistaken for a read one. get_attention lists what is unresolved, get_history what was concluded, and get_dashboard gives project totals. The locus tools declare what a bounded reply leaves out.

Recorded at 94d98773.

§Scope

describe_locus and the per-locus standing gate, get_attention and get_history, get_dashboard, their JSON schemas, and their tests.

Start here mcp-server/src/standing.ts, then mcp-server/src/tools/locus.ts

§Survey note

11 files, about 12,000 lines (locus.ts 3,725). Concern CC-3.

§How it works

standing.ts decides what kind of locus a name is and what the record authorizes saying about it. locus.ts builds describe_locus, get_attention and get_history on that, and dashboard.ts gives project-wide counts. None of them writes.

describe_locus resolves the locus kind: the caller's kind, then an exact subsystem id, then an exact vocabulary term (before the colon test, since terms carry colons), then a symbol, then a path. It then computes standing. A path the survey scope excludes stands excluded, and standing reads none of its ledger rows. With git, an examined file stays examined only while its ledger revision is an ancestor of HEAD, and is otherwise examined-stale. Without git, it stays examined but authorizes only what examined-stale does. Standing gates content: for a file or symbol whose weakest owner is neither examined nor examined-stale, the structure section withholds its claims and says why. Subsystems and terms are not gated. A claim is current when valid_until_sha is null; under as_of_sha, git ancestry decides.

describe_locus, get_attention and get_history each have a byte budget. describe_locus gets 15360 plus 4096 for each optional section, up to 32768. get_attention gets 12288 and get_history 8192. Items are dropped round-robin across sections against the re-measured wire size, and the omission ledger (omitted[]) records each drop with an exact count. Census and counts are never cut, so a response can still arrive marked within_budget false.

get_attention returns what is unresolved. get_history returns a subject's record over time, including every resolution event, open ones too, and the sessions that cite it whether or not they have ended. Both read finding_resolution_events.

A path that is not excluded and has no ledger row stands absent if scope_gaps records an absent gap for it, and unledgered otherwise.

§Structure

Five read-only tools live here: describe_locus, get_attention and get_history in locus.ts; get_dashboard and get_hot_subsystems in dashboard.ts. Nothing here writes a row or calls a model. standing.ts computes the standing beneath them, and other tool modules import its exclusion helpers. get_dashboard takes its counts from one SELECT, less a second SELECT's counts of ledger rows on excluded paths, and from scopeCounts.

describe_locus first decides what kind of locus it was given: the caller's kind if supplied, otherwise a subsystem id, then an exact vocabulary term (a term may contain a colon), then a symbol, then a path. The file_standing view gives each owner's state, and standing.ts settles the rest: whether there is an owner, whether owners disagree (mixed, ranked at the weakest), and whether an examined row's revision is still an ancestor of HEAD (if not, examined-stale). For a file or symbol locus whose standing is below examined-stale, structure claims are counted but not served.

A claim is current when its valid_until_sha is null; given as_of_sha, currency is judged by git ancestry against that revision. Where a subsystem has no claims, structure points to its narratives or imported survey bodies by record id, never their text.

describe_locus allows 15360 bytes plus 4096 per optional section, up to 32768, measured as the bytes the host receives. Each requested optional section sheds items while over 4096 bytes; then, to fit, it drops unknown[] samples first, then items round-robin from the deepest section, then the id samples in omitted[]. A response still over budget is served marked within_budget: false; one over the ceiling before that mark is added is refused. If served plus omitted items don't equal a section's census, the call throws. get_attention (12288 bytes) and get_history (8192) share a second engine, serveWithinBudget, whose ceiling is twice the budget. get_history uses the same standing resolver.

§Vocabulary
