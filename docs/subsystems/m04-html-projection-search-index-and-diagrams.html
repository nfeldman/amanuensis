Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

HTML projection, search index and diagrams

§Purpose

It turns the survey's page models into the published report: a static HTML site that works from file:// as well as from a web server. Diagrams are drawn during materialization as inline SVG or HTML, so the browser needs no diagram runtime; unrecognized Mermaid prints as source. Every page shares one navigation rail, a search index, and a stylesheet and script stored under content-hashed names.

Recorded at 94d98773.

§Scope

The HTML projection of page models with its shell, search index and assets, and the build-time diagrams (method, seam, flow strip, coverage badges, orientation map); their tests.

Start here materializer/amanuensis_materializer/html_projection.py, then materializer/amanuensis_materializer/diagrams.py

§Survey note

9 files, about 12,300 lines. Concern TR-2.

§How it works

render_html_projection writes the HTML site. M-01 (Materializer entry, read model and publication)'s materialize_docs calls it with M-02 (Page renderers)'s page models, one SitePage of plan metadata per planned page, and the previous manifest's file list. _HtmlWriter turns each model into HTML, and _shell fills the slots of site/page.html. The same call writes search-index.js and the shared stylesheet and script under content-hashed names in assets/. A file whose bytes are unchanged is skipped. A file that the previous manifest listed but this run did not produce is deleted. Every write goes in place with no temporary file; only clean_publish, off by default, renders into a staging directory and swaps it in whole. The returned hashes become the manifest's projection_files.

M-02's model carries raw strings, so the writer escapes record text, as svg_text in diagrams.py does for diagram labels. Link schemes are left to prose._html_href, which filters them earlier. Marker comments are printed verbatim. The search index is data only: one JSON assignment in its own file, which site.js renders with textContent.

diagrams.py builds diagram models as pure functions of store rows and the vocabulary contract, and infers no relationship from names. draw_svg draws the method, seam-contract, flow-strip and coverage diagrams as inline SVG at build time, on a fixed grid with no layout engine and no browser script. html_projection.py draws the boundary diagram itself. Node and edge order comes from ids, sorted keys and fixed sequences, such as the contract's pass order and a seam's field order, which keeps the golden files stable. A diagram that holds links is a labelled group whose drawing is hidden from assistive technology, and one without links is an image. diagram_access.py checks this rule for the gates.

The read-back (M-05 (Publication read-back)) uses this module's own _inline and diagram code to work out what a page should print. The gates (M-06 (Orientation exposure), M-08 (Lens golden pages)) parse class names, headings and the NAV_GROUPS rail, so a markup change can fail a gate even when a reader would see no difference.

Recorded at 94d98773.

§Structure

diagrams.py turns store rows into page-model blocks, and html_projection.py prints them. Layout is computed from ordered queries. Step and mark counts set flow column widths and band heights, and wrapped text sets runtime row heights, so one store always prints the same SVG.

Only Diagram blocks go to draw_svg: method diagrams, coverage bars, seam contracts and flow strips. The writer draws the atlas, topology, boundary and runtime maps itself. diagrams.py draws a flow strip only when its subsystem is at Structural or deeper and has three to twenty current steps, and a seam party's arrows only when that party is at Structural or deeper; otherwise the model carries a sentence saying why.

M-01 calls render_html_projection once per publication. It writes search-index.js, the content-hashed assets/site.* CSS and JS, and README.md, then prints each page's model through _HtmlWriter into the site/page.html shell, skipping a page whose bytes are unchanged. Files the previous manifest listed that this run did not write are deleted last. Writes are in place.

Record text is escaped in two places only: the writer, and diagrams.py, through svg_text, the attribute escapes and svg_root's escaping of the title and description. Link schemes are filtered upstream in prose.py. After printing, _identifier_markup re-parses body and navigation to wrap known ids in <abbr> definitions.

site.js builds the search combobox, row filters and help popovers, reading the index from one global. With scripts off, every page, anchor and row stays reachable.

The gates publish seeded copies of the golden store and hold the output to it: every box and arrow that carries a record mark (data-node, data-edge) is compared with SQL over the store or, for method diagrams, with what the vocabulary contract implies, and SVG roles are checked through diagram_access.py. They also reseal sabotaged pages to show the read-back notices.
