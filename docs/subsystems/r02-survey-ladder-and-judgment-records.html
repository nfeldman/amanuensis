Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Survey ladder and judgment records

§Purpose

These tools record each subsystem's place on the ladder and the survey's judgments: concern review, seams, terms and open questions. The ladder runs from unmapped to mapped; a phase is granted only once the previous one's deliverables are on record, except when resuming from an unrecorded parking. A disposition is refused before its phase and must cite evidence at revisions that resolve.

Recorded at 94d98773.

§Scope

Subsystems and their status ladder with its refusals, priorities, concerns, dispositions, diagnosticity matrices, seams, xrefs, field notes, open questions, contradictions and domain vocabulary terms; their tests.

Start here mcp-server/src/tools/subsystems.ts, then mcp-server/src/tools/dispositions.ts

§Survey note

16 files. Concerns CR-1 (vocabulary terms keyed across the store), concern EP-1.

§How it works

A subsystem's status runs Unmapped, Scoped, Structural, Reviewing concerns, Challenging claims, Mapped; each rank past Scoped needs its deliverable stored. Deferred sets it aside at any depth. update_subsystem_status and upsert_subsystem check each rank a status rise climbs, from the held depth if recorded, with enforceForwardPrerequisites in invariants.ts. Structural takes ledger rows, a claim, and a term with a resolving first_seen anchor or a declared absence of one. Reviewing concerns takes a structure narrative, a declined one or an imported survey body; Challenging claims a disposition. Mapped takes challenged claims, no unexcluded candidate file, a reconciled store and both explanation slots answered. Each status change appends a subsystem_status_transitions row in the same transaction.

Bar leaving Deferred, reset_subsystem is the only way down. In one transaction it deletes its dispositions, findings, field notes and xrefs. A reset below Structural also drops ledger rows and claims, though a claim that carries a flow mark is closed rather than deleted. Explanations, narratives and imported survey bodies are withdrawn by appended rows.

A disposition is the verdict on one concern for one subsystem, one row per pair that each set_disposition overwrites. It is accepted from Reviewing concerns on (Challenging claims for an adversarial pass). It must cite evidence rows whose revisions resolve, and its evidence_quality may not outrank the strongest evidence kind attached. Both are ranked by position in the generated EVIDENCE_QUALITIES and EVIDENCE_KINDS arrays, so their order matters. Attachments go in as supports, and a revision never removes one.

define_term keeps one row per term across the store, scoped to every subsystem that has defined it, with the last writer's gloss.

A contradiction between two findings is resolved only on evidence from the active session attached to one of them. A diagnosticity matrix accepts a verdict only for a concern and evidence row already in its grid.

§The status ladder and its three writers

A survey session declined to write this at 94d98773 on 2026-11-27. Folded into this subsystem's single structure narrative.

§Judgment records: which are kept and which are replaced

A survey session declined to write this at 94d98773 on 2026-11-27. Folded into this subsystem's single structure narrative.

§Structure

R-02 is ten tool modules, each an array of MCP handlers over the shared SQLite store. They hold no state of their own and check their gates before writing.

The ladder is subsystems.status. Three tools write it: update_subsystem_status, upsert_subsystem and reset_subsystem. Each status change appends a subsystem_status_transitions row in the same transaction. An advance refuses a move down the ladder, except into or out of deferred, and checks each rung from the depth held, if recorded, to the target. Structural needs a ledger, a claim and vocabulary or a declination; concerns needs a structure narrative, even declined, or a live imported survey body; adversarial needs a disposition. Mapped needs challenged claims, no live candidate file, a reconciled store and both explanation slots answered. These rules live in invariants.ts, outside the subsystem. Resets never exceed a known depth. In one transaction it deletes the subsystem's dispositions, findings, field notes and crossing edges, and below structural its ledger rows and claims as well. A claim carrying flow marks is closed instead of deleted. Explanations, narratives and imported survey bodies are withdrawn by appended rows.

Most judgment records keep only the latest verdict. A disposition is one row per subsystem and concern, replaced by each set_disposition from the concerns rung on (adversarial for an adversarial pass). Its evidence is attached in the same transaction, and earlier attachments keep their roles. Its evidence_quality may not rank above the strongest attached evidence kind. Vocabulary holds one row per term across the whole store: vocabulary_scopes keeps every subsystem that defined a term, but the gloss is the last writer's. A contradiction row is overwritten too, but each resolution is also appended as an event. Seams merge each side's half of the contract. add_xref stores a crossing edge only when its context carries a citation token whose revision resolves.

The test scripts drive these handlers against scratch stores and git fixtures.

§Vocabulary

  • crossing edge — An xrefs row recording a data flow or dependency that crosses from one subsystem to another, carrying at least one file:symbol@sha citation in its context.
  • diagnosticity matrix — An Analysis of Competing Hypotheses grid of two or more concerns against evidence rows, used when several concerns could explain one symptom.
  • disposition — The verdict on one active concern for one subsystem (confirmed-bug, confirmed-acceptable, ruled-out, out-of-scope or unresolved-competition), with the evidence rows it rests on.
  • knowledge-depth contract — The rule that a subsystem's status (unmapped, scoping, structural, concerns, adversarial, mapped) only climbs, and climbs a rung only when the record holds that rung's deliverable.
  • vocabulary discharge — The structural rung's obligation that a subsystem either carries at least one domain term with a resolvable first_seen anchor or has declared, with a reason, that it has none.

§R02-2

Claim A: the status writers and set_disposition check prerequisites outside the transaction that writes, so a concurrent reset from a second server process can land between check and write.

Claim B: looked for a mechanism that makes the interleaving impossible. The dispatcher calls tool.handler(args, ctx) directly with no wrapping transaction or lock (mcp-server/src/index.ts lines 526-529). db.ts's only immediate transaction is at store opening (line 126). The pid owner file in project.ts guards only initialization staging (lines 838-860), not later writes. The write_locks table behind acquire_lock is advisory, and no R-02 writer reads it. A second server process on one store is a supported case: several sessions in one worktree, or a shared AMANUENSIS_STORAGE_ROOT. One bound does hold: inside one process, better-sqlite3 calls are synchronous, so two calls in the same server cannot interleave.

Verdict: upheld, and scope-restricted to multi-process use of one store. Severity stays LOW, since it needs a concurrent reset of the same subsystem.
