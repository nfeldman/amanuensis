Scope

Claim

Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern

Reader's guide

Workspace binding, activation and installer

§Purpose

Once bound, calls use one repo and store, except compare_conspectuses. This part picks the workspace once, freezes it in a binding receipt that each valid call rechecks, and builds the store, by default .amanuensis inside the workspace, on first use. Its amanuensis CLI writes the server into Claude, VS Code or Codex configuration, prints steps for other hosts, and copies in the workflow skill.

Recorded at 94d98773.

§Scope

How a server process binds to one repository and one storage directory (project.ts, codex-host.ts, get_project_info), first-use initialization, cloud storage root, and the amanuensis CLI that installs, diagnoses and repairs host registrations (cli.ts); package-artifact and release-rollback tests, activation fixtures and contract.

Start here mcp-server/src/project.ts, then mcp-server/src/cli.ts

§Survey note

35 files. project.ts calls node:child_process directly but passes STARTUP_PROBE_TIMEOUT_MS on its git calls; its execSync import is unexamined (concern TB-1). Concerns SI-1, concern AT-4, concern EP-3, concern TR-4, concern RL-2.

§How it works

P-03 decides which repository a server process serves and where its store lives. P-01 (Server runtime and dispatch)'s index.ts chooses the workspace (codex-host.ts reads a parent Codex CLI's --cd) and refuses a second one. resolveProject (src/project.ts) canonicalizes the workspace, refuses the filesystem root and picks the store by storage policy: the workspace's own .amanuensis, or one store per repository identity under AMANUENSIS_STORAGE_ROOT. It checks that the store stays inside its root, crosses no symlink (a dangling one at the store path counts as absent and passes) and records the same repository identity, then returns a frozen ProjectContext.

Before any tool handler runs, assertProjectBinding re-derives the realpath and repository identity and rechecks containment; any change throws. Nothing is written until a call needs the database, so get_project_info on a fresh repository leaves no store. Then ensureProjectStorage builds a new store in a sibling initialization stage, including memory.db through P-02 (Store schema, migrations and storage history)'s initializer, and publishes it with one rename. Concurrent starters need no lock: the loser of the rename adopts the winner's store. It also reclaims stages whose owner pid is dead, migrates a legacy store only if it proves the identity, and excludes a worktree-local store from the repository's git. resolveStorageOutputPath applies the same containment to materializer and review-export output.

src/cli.ts registers the server and copies the skill, bundled at prepack from .claude/skills/amanuensis, for Codex, Claude Code and Copilot. A user-level install creates each host's home directory, plans every host and refuses on any conflict or unwritable target before writing files, then applies hosts in turn with no rollback. Config and skill files are written as a temporary file renamed into place; a config file is first copied to a backup, and a differing skill file is overwritten only when forced. doctor --repair applies a Codex repair only with the plan id computed now.

§Structure

P-03 binds one server process to one repository and its store, and its amanuensis CLI registers that server with Codex, Claude Code and Copilot.

resolveProject canonicalizes the workspace, derives the repository identity from a parseable git origin (or, without one, local: and the realpath), chooses the store by storage policy, checks containment and symlinks, and returns a frozen ProjectContext with its binding receipt. Under Codex, codex-host.ts reads the parent's --cd unless it is an app-server. Before each valid call once bound, assertProjectBinding re-derives the identity and throws on any change. resolveStorageOutputPath holds materializer and review-export output inside the store by the same containment rule.

The store is created when a call first needs the database. ensureProjectStorage builds it in an initialization stage beside the store path (identity records, memory.db, storage git, a completion marker) and publishes it with one rename. There is no lock: a starter that loses the rename adopts the winner's store, and a dead starter's stage with a readable owner record is removed later. The first-use recovery test stops a worker at each named step of store creation and checks that the next start completes it. A legacy store is moved only if it proves the binding's identity. end_session closes the session row and, when the store is a git repository, commits it.

A user-level install creates the host homes, then plans every host before writing files, refusing on any conflict or unwritable target. Only then does it apply the hosts in turn, writing each file to a temporary file and renaming it over the target. A configuration file is backed up first; a differing skill file conflicts unless forced or the user-level skill is a symlink. The skill comes from the repository's .claude/skills/amanuensis in a source checkout, otherwise from the copy prepack-bundle-assets.mjs put in the package. doctor --repair applies a plan only when given the id of the plan computed now.

§Vocabulary

  • binding receipt — The frozen record of which repository and which store a server process is bound to, with a sha256 binding id over its fields.
  • initialization stage — A sibling directory named after the store plus .initializing- in which a new store is fully built, marked complete, then renamed into place.
  • repair plan id — The SHA-256 digest of a doctor repair plan; --apply-plan applies the repair only when the id it is given matches the plan computed now.
  • storage policy — worktree-local (the store is the workspace's own .amanuensis) or shared-repository-identity (AMANUENSIS_STORAGE_ROOT holds one store per repository identity).

§Known defects here

4 defects here are open or awaiting verification. Each one's full record, with its evidence, is on Open findings.

  • For a repository with an origin remote, one git remote get-url origin call that fails or exceeds its 5 s bound makes the server derive a different identity (local:realpath instead of remote:host/path). At bind time an existing store is then refused as an "identity collision"; after binding, every tool call is refused with "bound repository identity changed after startup" until the probe succeeds again. If the first store-creating call happens while the probe is failing, the new store records the local identity and every later start with a working probe is refused as a collision. — P03-1 · Low · Open
  • amanuensis init --client copilot (user scope by default) and amanuensis init --client claude --scope user fail with "installer path escapes managed root" for the host's own skill directory, after creating the Codex home directory if it was missing. — P03-2 · Low · Open
  • When amanuensis install or upgrade for several hosts fails after writing has begun (an I/O error, or a hand-written entry that appeared after planning), the hosts before it stay installed, the failing host may have its skill copied but no registration, and the command exits 1 with only the error message: it does not say which hosts were completed and skips the restart notes for them. — P03-3 · Low · Open
  • Each install, upgrade, uninstall or repair that changes a host configuration leaves another .bak.timestamp copy next to it (for example beside ~/.claude.json or Codex config.toml); nothing prunes them, and a real run does not print the backup path, only a dry run does. — P03-4 · Low · Open

§Challenge

§Challenge

The adversarial pass re-read each claim's code looking for the case it did not cover. Three claims were too broad and were superseded.

  • Store initialization does not begin with stage cleanup. Before cleanup it revalidates the binding, writes the store's line into the surveyed repository's info/exclude and creates the parent directory.
  • A legacy store is migrated only when it proves the binding's identity. An unverified legacy store, or one that conflicts with a different store at the destination, is kept where it is and reported on stderr.
  • Installer backups precede configuration rewrites only. A forced overwrite of a skill file has no backup.

The rest survived. The binding and its receipt are frozen, and the dispatcher cannot reach a handler without the per-call check. No code writes into the store path before the publish rename. The stage cleanup removes only stages it can attribute to this store and a dead process. The installer has no write before its conflict gate and no rollback after it. Store creation uses no lock.

The pass surfaced one more observation, recorded as a field note rather than a finding. Under the default policy the initialization stage and the migration directory sit beside .amanuensis in the workspace root, and the exclude line does not cover their names. While a store is being created, or after an initializer is killed, the surveyed repository shows them as untracked.

The four findings stand as recorded. All four were traced by reading, and none was run.
