Reader's guide

Server runtime and dispatch

§Purpose

Every Amanuensis tool runs in this process. It speaks MCP over stdio, binds to one workspace for its lifetime and holds one store connection; compare_conspectuses opens two more. Call outcomes go to a sidecar database, best effort; the reply never changes.

Recorded at 94d98773.

§Scope

The MCP server's entry point, tool registration and argument validation, shared helpers, bounded subprocesses, the call-log sidecar, sessions, locks, logging and dispatch records; package configuration, tool-schema and SQL-identifier checks; smoke, compatibility, startup, adversarial and performance tests.

Start here mcp-server/src/index.ts, then mcp-server/src/helpers.ts

§Survey note

§How it works

The server is one Node process speaking MCP over stdio. main in index.ts binds it to a workspace taken from --workspace, the environment or the launch directory's git root. Otherwise it binds the non-Git launch directory or waits for get_project_info(workspace) to bind an absolute path (its git root if any). From then on any other workspace is refused.

Each tool module exports an array of ToolDefinitions. index.ts joins them into one registry and compiles every input schema with Ajv in strict mode. dispatchTool refuses an unknown name or non-conforming arguments before any handler runs. It then re-checks the binding and opens the store, kept for the life of the process; get_project_info opens it only if the file exists. The handler gets a shared ctx holding the project, the database and one process-wide sessionId that start_session sets. A thrown ToolError becomes a refusal carrying its rule id, and any other throw becomes an exception result. Nothing is rolled back, so whether a refused call leaves partial writes is up to the handler.

Once the response is built, the call is queued, unless the log is disabled, failed or its queue full, for a sidecar SQLite file under the store's call-log/ that holds no argument values or messages. Rows are written later and failures swallowed, so logging never changes a response.

MCP annotations come from tool names. Tools starting get_, list_ or lookup_, and five named reader tools, are read-only. Tools on a hand-kept list are advertised as additive, and every other tool as destructive.

helpers.ts holds the guards other subsystems call, among them requireWorkspaceSourcePath and the survey-scope guards, which refuse a record naming an excluded path. subprocess.ts gives spawnSync and execFileSync a timeout when the caller sets none, 120 s by default, as a hung synchronous child stalls every call.

Nothing queues calls, even in one process: async handlers can overlap while they await.

§Structure

The server is one Node process speaking MCP over stdio; main in index.ts wires its tool modules together. At startup it takes a workspace from --workspace, the environment or the launch directory, or, when none applies, waits unbound for the first get_project_info(workspace), which binds the process for life and refuses any other workspace.

Ajv compiles each tool's inputSchema in strict mode. MCP annotations come from the tool name: get_, list_, lookup_ and five named readers are read-only, an audited list is additive, and the rest are advertised as destructive.

A call goes through dispatchTool. An unknown name or a schema failure is answered ok:false before anything opens. Then the binding is checked, the store is opened on first use and kept for the process, and the handler runs with one shared ServerContext, whose sessionId is a single process-wide value that start_session sets. A thrown ToolError becomes an ok:false refusal, any rule id kept for the call log; any other throw becomes an exception. The dispatcher opens no transaction; handlers that need one open their own.

After the response is serialized, the call is queued for CallLog, a sidecar SQLite file in the storage directory's call-log/, apart from memory.db. It records outcome, rule, throw site, latency and an argument digest, never values. Only its exit flush waits on a busy lock, for at most 200 ms; it cannot change or fail a call.

helpers.ts holds what handlers share: argument readers, revision resolution and the survey-scope write guards. subprocess.ts wraps spawnSync and execFileSync so that a child started during a call without its own timeout gets one (120 seconds, or AMANUENSIS_SUBPROCESS_TIMEOUT_MS) and, unless it names a kill signal, SIGKILL. Such a child blocks the one event loop, so a hung one stalls every later call until killed. This subsystem's three tool modules (dispatch log, write locks, access and query logs) are plain SQL over the store.

§Vocabulary

  • refusal — A tool answer that declines the call, either a thrown ToolError (with an optional rule code) or a returned {ok:false, error}; both reach the host as errors.
  • workspace handshake — The first get_project_info call with an absolute workspace path, which binds a server process to one repository for its lifetime.
  • write lock — An advisory, time-limited claim on an artifact path held under a self-declared holder_id in write_locks, used to serialize sub-agent writes.

§Known defects here

2 defects here are open or awaiting verification. Each one's full record, with its evidence, is on Open findings.

  • Two server processes sharing one store can both be told they hold the same write lock. Each acquire_lock reads that no other holder exists, then each runs its upsert; the second upsert's ON CONFLICT branch replaces the first holder's row, so both callers received ok:true while only the second holds the row. A holder whose lock expired between its own check and a rival's upsert is likewise displaced silently. — P01-1 · Low · Open
  • The guard that reserves .amanuensis/ for tool state can be passed by prefixing a path with ././: requireWorkspaceSourcePath returns ./.amanuensis/x, whose first segment is '.', so the reserved-state refusal does not fire. The survey-scope guard then cannot canonicalize that path (its canonical form is refused) and decides the raw spelling, which no rule or ignore file matches, so a write such as add_files_to_scope would be judged in the survey set and could record a ledger row naming the store's own files. — P01-2 · Low · Open
