Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Store schema, migrations and storage history

§Purpose

The store is memory.db, a SQLite file. This part defines its schema; triggers bar deletes from 104 tables and freeze listed columns. Opening migrates old stores and refuses one lacking a declared table, view, index or trigger. Tools call its checks to refuse what a subsystem's status or the store's reconciliation does not allow. Phase gates and session ends commit the store to git if in a repo.

Recorded at 94d98773. 1 of its 6 cited files changed since: mcp-server/src/schema.sql.

§Scope

memory.db: the SQL schema with its views and append-only triggers, opening and migrating a store (db.ts), the server-side invariants that turn the epistemic contract into refusals (invariants.ts), the storage directory's own git history (storage-git.ts, commit_phase_gate, get_storage_history), and their tests.

Start here mcp-server/src/db.ts, then mcp-server/src/schema.sql and mcp-server/src/invariants.ts

§Survey note

10 files but about 12,600 lines (schema.sql 5,610, invariants.ts 2,455). Every other server subsystem and the materializer read this schema. Concerns IF-2, concern AT-1, concern TB-2, concern CC-3, concern SE-1.

§How it works

The store, memory.db, is the server's persistent record, and schema.sql declares every table, view, index and trigger in it. openDatabase in db.ts opens it writable and refuses if any declared object is missing or of another kind. It also sets WAL and foreign keys, runs runMigrations, executes schema.sql whole, mints the store's identity and seeds the scope mode. The materializer and the read-back open memory.db read-only and rely on that open having created file_standing and finding_state_current.

The schema is written as CREATE … IF NOT EXISTS with no version number, so an existing store keeps the object bodies it was created with. A new column needs a probed ALTER in runMigrations, and a widened CHECK needs rebuildTable. A changed view body reaches only new stores, except concern_coverage, which is dropped and recreated on every open.

Many rules are enforced in the schema, so they hold whichever process writes. An append-only table usually carries an _is_immutable and a _cannot_be_deleted trigger. contracts/append-only-tables.txt lists those pairs by hand, and a gate fails when the schema and the list disagree. Status triggers enforce many run state machines, and a partial unique index keeps one current claim per key.

invariants.ts holds the read-only checks a tool runs before writing. A subsystem moving forward must pass each crossed status's check, target included, unless its parking went unrecorded. Reconciliation standing recomputes the tree, ledger, scope and exclusion digests instead of trusting the stored row. These checks open no transaction, so atomicity is the caller's job. Only recordStatusTransition writes to the store.

The storage directory is, or sits inside, a git repository if git setup succeeds. commit_phase_gate first checkpoints the WAL into memory.db, because the repository ignores the -wal file, and it refuses a busy or partial checkpoint. Then commitStorage runs git add, diff and commit through the shared subprocess wrapper.

§Key types

  • The append-only contract is a hand-kept list of 103 tables, each with the names of its is-immutable and cannot-be-deleted triggers, kept apart from schema.sql so that deleting a trigger pair cannot shrink the gate's denominator.

  • A CHECK cannot be altered in place, so a migration replaces the table: inside one transaction, with foreign keys off and legacy_alter_table on, it creates the canonical table under a scratch name, copies the shared columns, drops the old table, renames the scratch, re-creates the old table's indexes and triggers from their stored SQL and aborts on any foreign_key_check violation.

  • A reconciliation stands at a revision only when git_state.last_checked_sha resolves to that revision, the row was taken there over the same git ls-tree digest, and its scope digest, scope mode, exclusion digest (equal also to the readers' reconciliation) and ledger digest all equal values recomputed now; the newest such row wins. §Concurrency invariants

  • Within one server process every operation here is synchronous (better-sqlite3 and spawnSync), so no tool call interleaves with another. Across processes sharing one store the only coordination is SQLite's WAL locking with the library's default busy wait, the IMMEDIATE scope-mode seed and INSERT OR IGNORE identity mint; migration probes, the invariants predicates and the checkpoint-then-git commit sequence hold no lock across their steps.

§The schema and its append-only discipline

A survey session declined to write this at 94d98773 on 2026-11-27. Folded into this subsystem's single structure narrative.

§Structure

memory.db, one SQLite file per surveyed repository, holds the survey record, and schema.sql defines it. Most survey records sit in append-only tables. A trigger pair (<table>_is_immutable, <table>_cannot_be_deleted) refuses UPDATE and DELETE, so a correction is a new row. On composition_items the update trigger guards only the plan, so status and observations change in place. A few tables, file_ledger among them, stay mutable.

There is no schema version. openDatabase brings a store up to date every time it is opened. It turns on WAL and foreign keys, runs runMigrations, then re-executes all of schema.sql. Migrations come first so that new columns exist before schema.sql's indexes name them. It then mints the store identity, refuses the open if any declared object is absent or of another kind, and seeds the scope mode.

A new table reaches an old store by being declared, because schema.sql creates with IF NOT EXISTS. A new column needs an ALTER probe in runMigrations. A widened CHECK needs rebuildTable, which copies the rows into a canonical replacement in one transaction and restores the indexes and triggers. A changed view body does not reach an existing store, except concern_coverage, which is recreated on every open.

invariants.ts holds the checks the tools run before writing. One of them, the standing reconciliation, recomputes the tree, ledger, scope and exclusion digests rather than trusting the stored ones.

The storage directory is also a git repository, and git ignores the WAL and SHM files, so a plain commit could miss rows. commit_phase_gate therefore first folds the WAL into memory.db with a TRUNCATE checkpoint and fails if the checkpoint is busy or partial. Only then does commitStorage run git add, diff and commit.

contracts/append-only-tables.txt is a hand-kept list of each append-only table and its trigger pair. Gates check it against schema.sql in both directions, so deleting a trigger pair fails the gates rather than quietly dropping that table from the check.

§Vocabulary

  • append-only table — A memory.db table whose rows a pair of BEFORE UPDATE / BEFORE DELETE triggers (<name>_is_immutable, <name>_cannot_be_deleted) refuse to change, so a correction is a new row.
  • phase gate — A commit of the storage directory's own git repository made by commit_phase_gate (or end_session), after a TRUNCATE checkpoint moves the WAL into memory.db, so the store can be recovered to that point.
  • scope mode — A store's survey-scope regime, sorted (every survey path must be sorted product or meta) or legacy (a store surveyed before sorting existed), read from the newest scope_mode_changes row.
  • standing reconciliation — The newest scope_reconciliations row that still describes the store: taken at the revision being claimed, with its tree, ledger, scope and exclusion digests equal to digests recomputed now.
  • store identity — A random 128-bit store_generation minted once into the single-row store_identity table, by which carried records name the store they came from.

The survey's reasoning about the concerns it reviewed here is on Review coverage, under this subsystem.

§Challenge

§P02-1

Claim A: two server processes opening a pre-upgrade store at the same moment can both pass db.ts's hasColumn probe, and the second ALTER TABLE ADD COLUMN then fails its open with a duplicate-column error (LOW).

Claim B, what was looked for: any mechanism that serialises opens or makes the ALTER tolerant.

  • A process-level lock around the open: none. rg over mcp-server/src finds exclusive-create flags only in code-index/store.ts and cli.ts, and no flock, lock file, locking_mode or BEGIN EXCLUSIVE in the open path.
  • A transaction around probe and ALTER: none. mcp-server/src/db.ts:runMigrations@ec39380 runs each as its own db.exec; only rebuildTable wraps its work in a transaction.
  • A caller that serialises: index.ts ensureDatabase opens lazily with no lock (mcp-server/src/index.ts:main@ec39380), and project.ts ensureProjectStorage takes the staging path only for a store that does not exist yet.
  • A catch that retries or ignores the duplicate: openDatabase has no try around runMigrations.

What does bound it: the loser's handle is unreferenced and db stays null, so the next tool call reopens and the probe then sees the column; each ALTER is atomic; the rebuild migrations are idempotent under a repeat because their probe re-reads the stored DDL.

Verdict: upheld. Severity stays LOW. The scope is narrower than any open: only a first open after an upgrade that adds a column, with two processes inside the same few milliseconds.
