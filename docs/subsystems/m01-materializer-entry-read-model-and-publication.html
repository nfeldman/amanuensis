Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Materializer entry, read model and publication

§Purpose

It renders memory.db, opened read-only, as a static HTML site in the store's docs directory. The server's materialize_docs tool runs it. A render refuses when the latest exclusions fail their digest. A default render overwrites the old pages before its read-back against the store; a server clean publish replaces the old site only when the read-back passes. The server records read-backs by run id.

Recorded at 94d98773.

§Scope

The Python materializer's command line and core pipeline, its read-only database model, manifest and slugs, legacy prose extraction, the test-store seed, packaging, and the server tool materialize_docs that spawns it and records publication; their tests.

Start here materializer/materialize.py, then materializer/amanuensis_materializer/core.py and mcp-server/src/tools/materialize.ts

§Survey note

21 files. The schema seam with P-02 (Store schema, migrations and storage history) (concern SE-1) and the publication path (concern EP-2, concern AT-3, concern CR-2) start here.

§How it works

Publication starts at the server tool materialize_docs (mcp-server/src/tools/materialize.ts). It keeps the output inside the store, refuses verify_readback=false, and refuses unless a complete reconciliation stands at HEAD. The server handles no other call while a render runs, because the tool runs materialize.py synchronously, with a 900 s timeout.

materialize.py exits 2 on conflicting flags and, unless --readback-only, on an output outside <storage>/docs without --allow-external-output and when the newest reconciliation's exclusion digest fails. A change to the server's reconciliation query or exclusionDigest must also be made in db.py, which restates both in Python, or the pages will list a different survey set.

Materializer (core.py) opens the store read-only, applies no schema, and refuses when the file_standing or finding_state_current view is absent. _plan rebuilds the page list from the store on every run, and navigation and the read-back's expected paths come from it. Each page's model is built in its own try, so a failure clears ok while the other pages go on. The timeout's SIGTERM is raised as an exception so a clean publish stopped mid-swap restores the old output. .manifest.json keeps per-page hashes for the next incremental run, and .projection-contract.json hashes the bytes written. ProjectionVerifier then reads the output back, and if the read-back fails, so does the run.

A clean publish renders into a staging directory, refuses an output holding files the old manifest does not claim, and swaps in by rename only when the run is ok. An in-place render writes into docs/ directly, so one stopped while writing pages leaves new and old pages under the old manifest.

Bodies imported from an earlier version are printed by legacy_prose.py; the import tool runs legacy_extract.py.

  • A render is one single-threaded Python process with one read-only SQLite connection, started synchronously by the server, so the starting server process handles no other tool call (and makes no store write) until the render exits; a second server process on the same store can still write during the render. §Structure

M-01 turns the store into the published HTML site, across two runtimes. The server's materialize_docs keeps the output inside the store and refuses to run without a read-back or without a complete reconciliation at HEAD. It then runs materialize.py through spawnSync, which blocks the server for the whole render, up to 900 seconds. materialize.py refuses any render when the newest reconciliation's exclusions no longer match their digest, since with the survey set unknown, excluded paths would be published as surveyed. The server writes to the store in recordReadback and the import.

Materializer in core.py opens memory.db read-only and applies no schema. When file_standing or finding_state_current is missing it refuses by name rather than copy their definitions. db.py restates the server's reconciliation query and exclusion digest, so a change to either on the server has to be repeated there. _plan builds the page plan from the store on every run, and the navigation and the reader's guide come from that one list. Each page's build closure in the renderers (M-02) returns a model and its source hashes. The models are linked against one cross-reference index and passed to the HTML stage (M-04 (HTML projection, search index and diagrams)). A page that fails to build fails the run, but the other pages still render.

State outlasts a run in two output files: .manifest.json and .projection-contract.json. The manifest's per-page hashes decide which pages count as re-rendered; HTML is rewritten only when its bytes differ. Its list of projection files lets a clean publish refuse an output that holds files it did not write. A clean publish renders into a staging directory and swaps it in only when the run is ok, read-back (M-05) included unless disabled by hand. An in-place render writes straight into the output directory, docs/ by default. The import runs legacy_extract to pull the thesis, project name and runtime rows from what an earlier version wrote by hand, and legacy_prose prints the imported bodies on the Method pages.

§Challenge

§M01-1

Claim A: a SIGTERM from the server's 900 s bound is swallowed when it lands while page models are built, so the render continues, the server stays blocked and the timeout is misreported as a failure to start.

Claim B, the search for an overturning mechanism: a second handler that re-raises Terminated, a second signal, or a broad handler that would let Terminated through. rg over materializer/amanuensis_materializer and materialize.py finds exactly two broad handlers: the per-page 'except Exception' in core.py:Materializer._materialize@ec393801 (lines 338-351) and main's own in materialize.py:main@ec393801 (274-279). Nothing re-raises from the first, and the summary flag it clears only stops promotion. subprocess.ts:bounded@ec393801 keeps the call's own killSignal, so the wrapper sends no SIGKILL afterwards. Node's spawnSync (library, not in the tree) sends the kill signal once and returns only after the child exits. Outside the page loop, in the HTML stage, contract writing or read-back, Terminated propagates as designed.

Verdict: upheld, scope-restricted to a signal that arrives during model building. The compensating property stands: in a clean publish the run ends not ok, the stage is deleted and nothing is promoted (evidence 709). Severity stays LOW, since no store at the anchor renders for anything near 15 minutes.
