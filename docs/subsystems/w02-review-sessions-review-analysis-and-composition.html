Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Review sessions, review analysis and composition

§Purpose

These tools support reviewing a change at one assembled HEAD. A composition run checks whether every expected item reached that HEAD and passed its check; only then is it green. In a review analysis, generator, refuter and verifier passes contest each suspected defect. A review session combines both into one exportable list; each item gives an evidence count, and expanding it shows the evidence.

Recorded at 94d98773.

§Scope

Independent review sessions and passes, blinded review analysis, and the integral composition run that assesses seams with scored fan-in; their tests and manifests.

Start here mcp-server/src/tools/composition.ts, then mcp-server/src/tools/review-session.ts

§Survey note

9 files, about 6,200 lines. Stage X of the lane runs the composition run surveyed here.

§How it works

Two pipelines share one shape: each fixes its plan once, gives workers observe-only inputs, and takes back their results as landings that the server scores against stored state. A composition run can require an aggregated review analysis, and a review session is compiled from a composition run.

plan_review_analysis takes published review briefs from W-01 (Change impact, refresh, revalidation and review brief) and a sealed hash of the expected outcome. freeze_review_hypotheses groups the generators' candidates by finding key. Refuters, then verifiers, judge each hypothesis without earlier verdicts: an input carrying a truth or prior-verdict field is refused and the run marked contaminated. A refuter's overturn must cite evidence it added. A hypothesis is defeated only when a verifier's overturn cites that same evidence (a verified defeat), survives when every judgment upholds it, and is otherwise contested. The truth is checked against the seal only after aggregation or contamination.

plan_composition_run binds to the checked-out HEAD and a change-impact run for it, and names a concern for each impacted seam. Each item is dispatched, landed and scored once. A test item is scored on the worker's own report; other items against the artifacts registry, git, the aggregated review run, or a narrative or explanation row. After every unit item passes, one integral lane compares the worker's reported checkout with the assembled head and tree. reconcile_composition_run completes the run only when every item and the integral lane passed with no deferral; missing work leaves it open.

compile_review_session builds items from a complete or blocked composition run and the store's findings, closed claims, open obligations and open questions, and refuses an actionable non-obligation item without evidence. A session completed with decisions is exported as two files and read back; the codebase brief (W-03 (Decisions, design sessions and codebase brief)) and the learning ledger (W-04 (Research, crosswalk and learning ledger)) read the session.

Most writes check status first; across processes, schema triggers keep landings write-once and statuses forward-only.

§Structure

Each of the three tool modules records its work in records whose status can only move forward, which schema triggers enforce. The modules meet only through tables: a composition item of kind review-result passes only when its review analysis run is aggregated at the item's commit, and a review session is compiled only from a complete or blocked composition run.

Composition checks that a change's parts came together at one assembled HEAD. A run is planned against a change-impact run at that HEAD, with a concern for each of its seams. Each item is dispatched, landed and scored at most once. Landing stores the worker's observation without reading it; scoring checks it against the artifacts registry, recorded prose, git or the review run, but trusts a test's reported exit code. Only after every unit item passes does the run open its one integral lane, whose checkout is compared with the manifest. Reconciliation completes the run if everything passed and blocks it on any failure, deferral or failed lane.

Review analysis challenges candidate findings independently. Planning stores a sealed hash of the expected outcome. Generator passes record candidates, which are frozen as hypotheses for refuter and verifier passes to judge. Dispatch refuses input with expected-outcome keys, or for a challenger verdict keys, and records each refusal as contamination. A hypothesis survives if every judgment upheld it. It is defeated only when a verifier overturns it citing evidence a refuter added; otherwise it is contested. Revealing the expected outcome checks it against its hash; separate scoring of kept findings excludes contaminated runs.

A review session gathers items from the reconciliation, changed files, findings, challenge outcomes, closed claims, open obligations, questions and candidate concerns. Each item's id is hashed from its source, and the compile fails if an actionable non-obligation item has no evidence. Completion records the reviewer's decisions; export writes and registers review.json and review.md.

§Vocabulary

  • blind truth seal — The sha256 of a salt and the stable JSON of a review analysis run's expected outcome, supplied at planning and checked when the truth is revealed after aggregation.
  • composition run — An immutable fan-in manifest over one assembled HEAD: expected unit and integral-HEAD items, the impacted seams' concerns, and the append-only reconciliations that score it green or red.
  • integral lane — The single composition-scoped verification lane over the assembled HEAD, admitted only after every unit item scored pass with no deferral, and passed only by a clean checkout of exactly that head and tree.
  • review session (decision surface) — A compact, immutable list of review items compiled from one complete or blocked composition run, each with a section, a semantic state, an epistemic kind and an actionable flag, then furnished, exported and read back.

§Challenge

§W02-1

Claim A: a test item and the integral lane pass on fields only the worker reports, while the tool descriptions promise scoring against durable state.

Claim B: looked for any server-side trace a test or checkout leaves that the scorer could compare with: a recorded test run, a stored output, a re-hash, or an inspection of the checkout. A search of mcp-server/src for output_hash and execution_report_hash finds only composition.ts's own non-empty check (mcp-server/src/tools/composition.ts:scoreItem@ec393801fd8140a8a9269d3e7132733c4bcb63df, 585) and land_integral_verification's argument (728); nothing else records or reads them. The tested commit is compared with the manifest's target, and exit_code with zero, both from the observation. scoreIntegral compares the coordinates land stored from the worker's arguments (765-774).

Compensating: the manifest is immutable and each stage write-once, so a worker cannot change its report after landing, and commit, artifact, record and review-result items do check durable state. That bounds the damage to the two self-reported kinds.

Verdict: upheld. Severity stays LOW: the defect is that the contract text overstates the trust property, not that a check misfires.
