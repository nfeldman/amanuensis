Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Evaluation, operating envelope and Chorusmith adapter

§Purpose

Amanuensis measures its own method and opens its tools to an orchestrator. An operating envelope says, per repository, mode, context and model, whether the method beat baseline and its controls held. A historical evaluation scores work on past fixes from the pre-fix trees, checked for leaks. The Chorusmith adapter runs allowlisted tools; a run is verified only if it matches calling them directly.

Recorded at 94d98773.

§Scope

Evaluation programs and the stratified operating envelope, historical evaluation, and the Chorusmith adapter with its parity contracts; their tests, scripts and fixtures.

Start here mcp-server/src/tools/evaluation.ts, then mcp-server/src/tools/chorusmith-adapter.ts

§Survey note

13 files.

§How it works

An evaluation program moves from planned to collecting, ready and published. plan_evaluation_program expands its manifest into one case per combination of stratum, condition role and replicate, and stamps the program with a detector digest, the sha256 of the running module file. publish_operating_envelope derives a verdict for each stratum and refuses a claim that disagrees with that verdict, a pooled claim, or a program whose detector changed since planning. After a detector change, rebaseline inserts a successor report. A stratum is supported only when the effect clears the minimum detectable effect, every control ordering holds, test-retest is stable and every treatment case has an alternative review that survived.

The Chorusmith adapter lets an outside orchestrator drive Amanuensis tools while Amanuensis keeps write authority. A run pins a source commit and an ordered list of steps, each a tool on its kind's allowlist in ADAPTER_CATALOG. execute_chorusmith_adapter_step refuses on commit drift, tracked changes, an out-of-order step or changed arguments. It runs the domain tool's handler inside the transaction that records the step, so a failing tool leaves neither its database writes nor the step, though files it wrote stay. verify recaptures a snapshot of the scoped records, compares it with the caller-supplied direct-path snapshot and marks the run verified only when every comparison passes.

Editing the JSON under contracts/chorusmith changes nothing at runtime: only test-chorusmith-adapter.mjs reads it, and the runtime values are the source constants ADAPTER_CATALOG and CUSTODY_MATRIX.

scripts/historical-evaluation.mjs is a separate CLI that shares no code with the server. It qualifies a corpus of past fixes by exporting each case's target and fix commits without history, scanning them for leaked fragments, and requiring the hidden oracle to fail on the target and pass on the fix. prepare hands one case to a participant and score runs the oracle on their workspace.

§Structure

W-05 is three parts that do not import one another. Two are tool modules that keep their own tables in the store. The third is a command-line script that works on git repositories and never opens the store.

evaluation.ts moves an operating-envelope program through four states: planned, collecting, ready and published. Planning writes one case for each stratum, condition and replicate. Landing a result sets that case's instrument status, and the program becomes ready once every case has landed. Publishing works out a verdict for each stratum from the condition means, the controls, test-retest stability and the alternative-explanation reviews. It refuses any claim from the caller that disagrees with those verdicts. Each report carries a detector digest, which is a hash of the module's own compiled file. If the stored digest or detector version differs from the running module's, verify logs a measurement event instead of comparing. Rebaseline then works out the strata again under the new detector and stores the result as a successor report.

chorusmith-adapter.ts runs a planned list of calls to other subsystems' tools at a pinned commit. Before each step it checks the commit, the worktree and the run's custody. It then calls the next tool's handler and records the step in the same transaction, so the database writes of a refused step roll back. Verify captures the scoped claims, evidence, decisions and obligations again and compares them with the direct-path snapshot given at planning. The adapter's rules are two constants in the source, CUSTODY_MATRIX and ADAPTER_CATALOG. Only the adapter's test reads the JSON files under contracts/chorusmith, and it checks them against those constants.

historical-evaluation.mjs works on a corpus of past fixes. It exports a commit without its history, scans the export for forbidden fragments and runs the case's oracle as a child process. Each of its operations (qualify, prepare, score and rebaseline) writes a JSON receipt.

§Vocabulary

  • Chorusmith adapter run — A planned sequence of allowlisted Amanuensis tool calls executed step by step at a pinned source commit, whose result is verified for parity against a direct-path snapshot.
  • historical evaluation corpus — A manifest of past repository fixes, each with a target commit, an oracle command and forbidden fragments, that the historical-evaluation script exports, scans for answer leakage and scores.
  • operating envelope — A published report of where the method works, derived separately for each repository, mode, context and model-runtime stratum from replicated control, treatment and ablation results, with no pooled program-level efficacy claim.

§Known defects here

3 defects here are open or awaiting verification. Each one's full record, with its evidence, is on Open findings.

  • An operating-envelope rebaseline can publish claims that its own re-derived strata contradict. Separately, verify_operating_envelope stores the outcome of checking a caller-supplied report under the real report's id, with nothing marking which report was checked. — W05-1 · Medium · Open
  • The Chorusmith adapter's parity proof rests partly on values it asserts rather than measures: - Plan accepts a caller-supplied direct-path snapshot and baseline time that only have to agree with their own hash. The tool description calls the snapshot independently captured. - The catalog hash recorded at plan time is never compared again. - The recovery receipt states source_state_mutated_by_recovery as a literal false. - The recovery axis passes after any single resume. — W05-2 · Low · Open
  • The historical-evaluation kill witness accepts a target whose oracle crashed, timed out or could not start: any non-zero or null exit counts as fail. In addition, git and tar run with no timeout, and the oracle inherits the whole parent environment. — W05-3 · Low · Open
