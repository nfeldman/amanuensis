Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Publication read-back

§Purpose

The read-back checks that the published pages say what the store holds. It reads memory.db and the finished files and reports where they disagree: a record missing, repeated or shown in the wrong state, a planned page or link absent, or bytes that differ from the publication receipt. --clean-publish keeps the live pages until it passes, unless --no-verify-readback is given.

Recorded at 94d98773.

§Scope

The read-back that checks published HTML against the store's records before a publication counts, and its tests (read-back, explanation pages, read-back labels, orientation contract).

Start here materializer/amanuensis_materializer/readback.py

§Survey note

6 files, about 6,400 lines. Concerns EP-2, concern CR-2.

§How it works

The read-back checks a finished publication against memory.db, separately from the renderer. If it is red, an otherwise clean publish is not promoted. After the cross-reference pass, core calls write_contract, which writes .projection-contract.json: each page's sha256, its local links and the render notice. ProjectionVerifier.verify reads that receipt, loads every .md, .html, .js and .css file in the output, and opens the store read-only once for censuses on three axes. The state axis requires each finding's hashed marker to appear exactly once, on the page its resolution state selects. Coverage requires the planned pages and no others, and every receipt link still present with a target and fragment that resolve inside the output. Content requires page bytes to match the receipt, site assets that hash to their names, and any render notice the receipt states once in the page foot. If the receipt is missing or loading it raises an OS or JSON error, all three axes go red and nothing else runs. materialize.py --readback-only runs the same check on a published tree; the server reads its last stdout line.

The receipt is written from the bytes it later checks, so its hashes catch only edits made after render. What ties pages to the store are censuses that check each marked record's page and state, re-render prose bodies to compare words, and owe whole territory rows and runtime boundary fields; a finding's root cause is not compared. Coverage figures on About this survey must read "not measured" unless reconciliation_standing re-derives the ledger and tree digests the server recorded.

A defect the renderers share with the read-back goes unseen here. The renderers import their rules from this module (FINDING_LENS_PAGES, finding_marker, effective_explanations, project_purpose_text), and the read-back builds expected text with the HTML projection's own _inline and diagram models. select_explanation is also checked against the JSON cases the TypeScript server runs.

§Concurrency invariants

  • The read-back is single-threaded and writes nothing to memory.db. Its one read-only connection starts in autocommit, so the first census's queries each read their own snapshot; the first survey_filter call (in the stale-ledger census) writes a TEMP table without committing, which under sqlite3's legacy transaction control leaves an implicit transaction open, so the later censuses read one shared snapshot. §Structure

readback.py has two jobs. It defines, in one place, the rules that pages are printed by and checked against: which lens page each finding belongs on, the durable markers, the effective explanation and narrative for each subject, and whether the store's reconciliation stands. renderers imports these definitions. Its ProjectionVerifier reads a finished publication back against memory.db, and a clean publish is promoted only if that read-back passes, unless --no-verify-readback skips it.

write_contract records the publication receipt, .projection-contract.json, with each page's sha256, its local links and the render notice. If the receipt is missing or unreadable, verify fails all three axes and checks nothing else; undecodable bytes raise. Otherwise it reads every .md, .html, .js and .css file in the output and runs its censuses over one read-only connection to the store. It checks that each finding's marker appears exactly once, that the planned pages match the pages present, and that each receipt link survives and resolves to a file inside the output, and to an anchor if it names one. It also compares each page's bytes with the receipt and checks the render notice, the README and the hash-named site assets. Each mismatch is tagged state, coverage or content, and any one fails the read-back.

The censuses read the data-record attribute on each record, data-state where it has a state, and data-node and data-edge on the SVG elements. Each census derives the expected marks from the store, or for some diagrams from fixed vocabulary, so a resealed page fails only where a census looks: a finding's prose is not compared. test-store-only-readback sabotages pages this way. The expected text comes from the renderer's own helpers, so a defect the two share goes unseen. Because renderers imports readback, readback imports the renderer modules inside the functions that need them.

The only module state is BOUND_WORKSPACE, the workspace that git questions are asked in. Nothing here writes to the store.

§Vocabulary

  • publication receipt — The .projection-contract.json file a publication writes beside its pages, listing each page's sha256, its local links and the render notice, against which the read-back's content and link checks run.
  • read-back axis — One of the three independent questions the read-back asks of a publication: state (each authoritative record appears exactly once with its state), coverage (every planned page, link and record is present, nothing unplanned) and content (bytes and prose match the receipt and the store).
  • record mark — A data-record (with data-state) attribute on the element that prints a store record, or data-node and data-edge on a drawn diagram element, by which the read-back finds and compares each rendered record.

§Known defects here

2 defects here are open or awaiting verification. Each one's full record, with its evidence, is on Open findings.

  • Some inputs make the read-back raise instead of reporting a mismatch: a tracked path whose name is not valid UTF-8 at the stamped revision, or a page with a non-numeric data-count on a finding badge. verify then returns no summary, so the server reports only that the materializer exited, with a traceback in place of axes and mismatches. — M05-1 · Low · Open
