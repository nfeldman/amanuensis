Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Standing
What the record says about one file: no record, left out, in scope but unread, read, read but changed since.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Store gates, rebuild, docs promotion and reader measures

§Purpose

Maintainer tools for a store and its published pages. One checks a store against ADR-0001's seven completeness clauses and names up to twelve unmet obligations per clause, or every one with --json. Another discards and reinitializes a store, carrying its findings forward. A third copies a verified publication into the tracked docs/ tree.

Recorded at 94d98773.

§Scope

The store completeness checker, store rebuild, docs promotion and HTML page reading, reader and locus-default measures, the token report, the store-only publish-chain and test-view checks; their tests and fixtures.

Start here dev/check-store-fully-surveyed.mjs, then dev/promote-docs.mjs

§Survey note

22 files. check-store-fully-surveyed.mjs is the checker the lane's completion gate (SV5) runs. Concerns SI-2, concern AT-3.

§How it works

Each of these is a standalone Node script; the server imports none of them.

check-store-fully-surveyed.mjs evaluates ADR-0001's seven clauses on a read-only memory.db and names each unmet obligation, though text output stops at twelve per clause. It exits 0 if all clauses hold, 1 if not, 2 if it cannot run, unless the sqlite import or a table probe throws. It restates the server's digests, standing-reconciliation predicate and glob matcher instead of importing them, so a server change to any of them must be made here too. Other failed queries read as empty; clauses share no transaction.

rebuild-store.mjs discards a store and initializes a new one, carrying the old findings forward. It needs --confirm, --carry-from with a reason, and --discard-populated-store when the store holds a survey. It checks the carry source, snapshots the store, stops its server, and refuses to delete while lsof names another holder. Then it archives the storage directory whole and drives four more server processes to initialize, read back, carry and close. A refusal after the carry run begins leaves the store discarded and the run unfinished.

promote-docs.mjs copies .amanuensis/docs into the tracked docs/ that the pages workflow deploys, since materialize_docs cannot write outside the storage root. It checks the source's bytes against its .projection-contract.json and takes the verdict of materialize.py --readback-only from that command's last stdout JSON line, not its exit status. It refuses a destination holding files beyond its manifest, its contract and what that manifest claims. It swaps the trees by rename, repeats both checks at the destination, and restores the backup if either fails.

token-report.mjs describes call-log and transcript bytes without a verdict; its rule for which tools are read-only is a hand copy of the server's. measure-reader-prose.mjs owns the pinned MEASURE_PLACEHOLDERS that a materializer test reads, and other gates import the sentence splitter in reading-guidance.mjs.

Recorded at 94d98773.

§Promotion, rebuild and the measures

A survey session declined to write this at 94d98773 on 2026-11-27. Folded into this subsystem's single structure narrative.

§Structure

The dev/ scripts here are Node programs run outside the server, against the store, the built server or a publication. reading-guidance.mjs is a module, not a program.

check-store-fully-surveyed.mjs opens memory.db read-only and exits 0 only when all seven of its completion clauses hold, 1 otherwise, and 2 when it cannot run. It restates the server's digests and glob matcher rather than importing them, so a change to those in invariants.ts or scope.ts must be repeated here.

rebuild-store.mjs replaces a store with an empty one and keeps its findings. It takes a snapshot, refuses unless lsof shows no other holder, then copies the storage directory to an archive and deletes it. It then reinitializes, confirms the store is empty, carries the findings of the --carry-from source, if any, through the carry tools, and copies back the archive's Git history.

promote-docs.mjs copies a publication into the tracked docs/ that the pages workflow deploys. It checks the source against its .projection-contract.json and the materializer's --readback-only, judging the latter by the last JSON line printed, not the exit status. It refuses a destination holding files its manifest does not claim. It swaps the directories by renames with a backup, repeats both checks at the destination, and restores the backup on failure.

The measures print figures and set no threshold. measure-reader-prose.mjs counts table characters, prose characters and placeholder sentences on published pages, read through read-html-page.mjs. Its placeholder list is pinned, and the list's hash is recorded with every entry. measure-locus-default.mjs measures the default describe_locus response against a copy of the store, since a read can still write. token-report.mjs summarises call-log copies and transcripts on either side of a cutover, using its own copy of the server's rule for which tools are reads. reading-guidance.mjs exports the sentence test other gates use to catch guidance that restricts reading files.

§Vocabulary

  • carry source — What a store rebuild carries the predecessor's findings from: an archived store read read-only, an export carrying archived_store_id, or 'none' with a reason.
  • docs promotion — Copying a green publication from the store's .amanuensis/docs into the repository's tracked docs/, verified by its contract hashes and a three-axis read-back both before the copy and at the destination.
  • fully surveyed — The store-level verdict that all seven clauses of the completeness predicate hold: inventory, every subsystem mapped, every concern decided, every seam integrally assessed, exact composition fan-in, a green three-axis read-back, and every carried finding decided.
  • obligation id — A colon-separated name for one unmet requirement of the completeness predicate, such as file:&lt;path&gt;:assignment, concern:&lt;sid&gt;/&lt;code&gt;:disposition, seam:&lt;id&gt;:integral-assessment or carried:&lt;store&gt;:&lt;finding&gt;.
  • wire bytes — The size of the whole tools/call result a host receives from describe_locus (text block plus structuredContent), as distinct from the compact payload, the item-free floor and the declared budget.

§Challenge

§D02-1

Claim A: clause 6 of the completeness checker accepts the newest projection verification run of any mode, output directory or source revision, so it is weaker than the clean-export read-back its title names.

Claim B, the search for an overturning mechanism: if only clean publications wrote projection_verification_runs, the newest row would be a clean export by construction. They do not. mcp-server/src/tools/materialize.ts:execute@ec39380 records a row for every run, materialize_docs records mode 'readback' unless clean_publish is set, and verify_materialized_docs records one for a read-back of existing pages in any directory under the storage root (mcp-server/src/tools/materialize.ts:execute@ec39380, lines 312-319 and 337-348). Nothing in the checker reads mode, output_dir or source_sha (dev/check-store-fully-surveyed.mjs:verified@ec39380), and no test in dev/ or mcp-server/ drives clause 6. The compensating mechanism lives outside the repository: the lane's SV7 reads the final clean publication receipt and requires it to be newer than the last write.

Verdict: upheld, LOW. The gate is a development script and the self-survey lane does not rely on it alone, but anyone else running the checker gets the weaker reading.

Recorded 2026-11-24 at ec393801. 1 of its 3 cited files changed since: mcp-server/src/schema.sql.

§D02-2

Claim A: dev/measure-locus-default.mjs leaves a full copy of the measured store under the OS temp directory when it fails after mkdtempSync but before copyStore returns.

Claim B, the search for cleanup: the only rmSync of the temp root on that path is the clone-failure branch (dev/measure-locus-default.mjs:copyStore@ec39380, lines 112-114). cpSync of .amanuensis (123) and, for a local: identity, readFileSync and JSON.parse of initialization.json (130-131) can throw after the copy has begun, and fail() inside copyStore exits the process. main calls copyStore and client before the try whose finally removes root (lines 291-305). There is no process exit hook. The OS may clear its temp directory eventually, which bounds the lifetime, not the leak.

Verdict: upheld, LOW. The window is narrow and the tool is run by hand, but the leaked object is a whole conspectus database.

Recorded 2026-11-24 at ec393801.
