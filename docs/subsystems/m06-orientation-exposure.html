Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim

Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern

The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.

Reader's guide

Orientation exposure

§Purpose

These CI gates check the published site's orientation features against design/orientation/PLAN.md: the page index's "Use it when" lines, the reader's guide, ID links, per-page terms, the overview, survey notes and the command-line render. A gate fails if a page's report or an ancestor is hidden by attribute or inline style. Each publishes a seeded store through materialize.py and reads the HTML.

Recorded at 94d98773.

§Scope

The orientation exposure helper and the orientation page tests (command-line render, guide, ids, index, overview, survey notes, terms, views, workflow).

Start here materializer/orientation_exposure.py

§Survey note

10 files, about 5,000 lines, mostly tests.

§How it works

Each gate is a standalone script. It builds a temporary store by executing mcp-server/src/schema.sql and inserting fixture rows with plain SQL, runs materialize.py --storage as a subprocess, and reads the HTML written with regexes and HTMLParser. The fixtures bypass the server's tools, so its refusals do not shape what is seeded. Each check is a function run through check(), which turns an exception into a failure; the gate prints one GATE <id> GREEN or RED line and exits 1 on red. Only the views and command-line render gates still print a RED line when the script crashes outside check().

Where a gate writes expected wording out, rewriting a string in the implementation cannot also rewrite the test. The guide, workflow, IDs and terms gates take terms, enum wording, passes and ID kinds from the vocabulary contract that generates the materializer's vocabulary module, and the index gate takes lens meanings from that module, so a regenerated contract moves page and test together. The gates also match exact markup the HTML projection owns, such as the page-head, page-foot and page-use-when classes; a markup change can turn a gate red with no visible change to the page.

Every gate also runs orientation_exposure.hidden_pages, which fails when a page hides its report. It walks each .html file under the output and returns the first page where a report container (main, article, header.page-head or footer.page-foot), or any element around one, carries aria-hidden="true", hidden, inert, an inline display: none or visibility: hidden, or role presentation or none. A page with no container also fails, and so does an empty output tree. Elements inside the article may hide themselves, and hiding by class or stylesheet goes unseen. The diagram, map and read-back label gates, outside this subsystem, import hidden_pages too. Each gate also searches .github/workflows/test.yml for its own file name, which a comment would satisfy.

§Structure

The subsystem is nine gate scripts and one shared module, orientation_exposure. Apart from that module and the import helpers in store_only_seed, the gates share no code. Each has its own check, seed and output scrubbing, and its own publish (run in the command-line render gate).

A gate builds a temporary store from schema.sql and inserts fixture rows with plain SQL, so the server's refusals never shape the fixtures. It publishes by running materialize.py --storage as a subprocess with no timeout, then reads the HTML under docs/ with regexes and HTMLParser. Each check returns a reason or nothing, and an exception counts as a failure. The gate prints one GATE … GREEN or RED line. A materializer crash only sets a nonzero exit code, which a check reports as RED. Each gate checks that test.yml names it; those that publish run hidden_pages over their output, though the IDs and command-line render gates skip some later publications.

Most expected strings are written into the gate itself, so a change to the implementation's strings cannot change what the gate expects. Others come from the vocabulary contract JSON. The index gate reads lens meanings from the materializer's own vocabulary module, so the page and the test change together.

The workflow gate also publishes with a changed copy of the materializer, to check that its table comes from the vocabulary constants. The command-line render gate tampers with pages and receipts and expects --readback-only to fail.

orientation_exposure returns the first page with a hidden report container, or with none. The containers are main, article, header.page-head and footer.page-foot, the shell the HTML projection writes. A container is hidden when it hides itself or sits inside an element that hides. The module tracks this with a stack of open elements and the reason each one hides, and it reads attributes only. The map, diagram and read-back label gates in other subsystems call it too.

§Challenge

§Challenge

The adversarial pass re-read the exposure helper line by line and searched all nine gates for their subprocess calls and exception handlers. Six claims held. One did not: the claim that only the cli-render and views gates catch a crash outside the check harness was too broad, because the other gates catch import and seeding errors too. It was superseded by a claim that names what is actually unguarded, which is the publish step and the rest of main.

The strongest test of the helper was whether any page could pass with no report container, or with a hidden one inside a class-hidden ancestor. The first cannot happen. The second can, and that is finding M06-1. The seam claim was checked against the projection's page shell, which writes main, the page-head header and the content article around every body. A projection change that dropped all three would still turn the gates red, because the helper refuses a page with no container.
