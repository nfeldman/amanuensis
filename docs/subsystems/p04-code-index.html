Terms on this page

Survey
The agent's reading of the repository, done in passes, with each conclusion tied to the code it read.
Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
Mapped
The last survey depth: every pass has run. It does not mean every file is read or every bug found.
Scope
The files a subsystem owns, each marked as read, not yet read, or left out with a reason.
Evidence
A pointer to code at a commit (file, symbol, lines) with a note of how strong it is: read in code, seen in a test, stated in a comment, and so on.
Claim
A statement about how the code is built ("this cache is per request"), with evidence.
Challenge
A pass in which the agent tries to prove its own claims and findings wrong. Each claim records whether it survived.
Concern
One kind of defect worth looking for in this codebase, such as a race on a shared cache. The review checklist is the full list.
Concern review
The verdict for one concern in one subsystem: bug found, acceptable, ruled out, out of scope, or undecided.
Finding
A defect the survey confirmed, with evidence, a severity, and a state (open, repaired, verified, ruled out, accepted).
Lead
Something the agent noticed that is not a finding: a pattern, an oddity, a tension, a possible concern.
Decision needed
Something the agent could not settle alone. It records the assumption it used and keeps going; you answer it.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.

What the record says about one file: no record, left out, in scope but unread, read, read but changed since.

Reader's guide

Code index

§Purpose

The code index lets a survey session read a codebase by its definitions at any commit: outline_file lists a file's definitions, read_symbol returns one by name with its source, and find_symbol searches a whole revision. add_evidence uses it to anchor a cited symbol to an exact, hashed span. Parses are cached beside the store, keyed by git blob and language.

Recorded at 94d98773.

§Scope

The tree-sitter code index: extraction with WebAssembly grammars and query files, the content-keyed sidecar store, symbol search, and the tools outline_file, read_symbol and find_symbol; grammar vendoring and installed-package checks; per-language fixtures and tests.

Start here mcp-server/src/code-index/extract.ts, then mcp-server/src/code-index/store.ts

§Survey note

52 files, most of them small per-language fixtures and query files. Concerns CC-1, concern IF-1, concern RL-1, concern RL-3, concern CR-3, concern SI-3.

§How it works

The code index lists what a file defines (outline_file), returns one definition's source (read_symbol) and finds where a name is defined or used (find_symbol), at any revision. It parses with tree-sitter grammars compiled to WebAssembly and caches what it extracts in the sidecar code-index/<extractor_id>/index.db under the store. Nothing in memory.db refers to the sidecar, so deleting it is safe.

extract.ts parses one blob. Definitions come from the index's own queries/<lang>.scm, and references come from the grammar's tags.scm and match by name only. A definition's symbol_id is its enclosing scopes and its name, plus parameter types in Java, C# and C++; TypeScript overloads share one id and differ only by occurrence. It holds no path or position. Its byte span, which span_sha256 hashes, takes in its leading comments. The extractor_id hashes EXTRACTOR_VERSION, the query files and grammars/manifest.json, so a change to extract.ts starts a new cache only when someone bumps that constant.

store.ts keys a parse by (blob_sha, lang), taking the language from the path's extension alone. So that several server processes can share one database, a blob is parsed outside any transaction and then published with its blobs row written last. A reader counts the blob as indexed only once that row exists. find_symbol indexes the whole revision first. It answers partial: true unless the tree completion marker was written, which happens only when every supported entry's blob is present. Unless include_excluded is set, paths outside the survey set are dropped inside its SQL, before LIMIT. read_symbol reads the blob again from git and returns the span only if its hash still matches. Eviction works toward 1 GiB but spares the blobs of the eight most recently touched revisions, so the sidecar can stay over.

add_evidence (R-03 (Evidence, claims and findings)) anchors symbol citations in the index. When the cited blob has not been indexed, it runs index-file.js in a child process to index it.

§Concurrency invariants

  • Several server processes share a generation's sidecar through SQLite WAL with a 5 s busy timeout: blob publication is idempotent, completion is checked and written in one immediate transaction, a corrupt database is set aside under an exclusively created recovery marker, and any other SQLite or filesystem error makes that call unavailable rather than throwing; eviction picks its victims before, not inside, its delete transactions.

§Structure

The code index answers questions about source at a revision, never the working tree. It lists files with git ls-tree and reads blobs through a git cat-file --batch child per indexing pass or read. The extractor (extract.ts) is a deterministic function from blob text and language to an Extraction of definitions, references and imports. Definitions are matched by the index's own queries/<lang>.scm (TSX shares TypeScript's) and references by the grammar's tags.scm, plus JavaScript's for TypeScript and TSX. Grammars are WebAssembly files vendored from the pins in grammars/sources.json, and each is checked against grammars/manifest.json when it loads.

CodeIndex (store.ts) owns the sidecar, a SQLite cache at <storage>/code-index/<extractor_id>/index.db. Evidence anchors in memory.db copy what they cite, extractor_id included, so deleting the sidecar costs only reindexing. Parse rows are keyed by blob and language, tree rows by revision and path. The <extractor_id> directory is a hash of EXTRACTOR_VERSION, the query files and the manifest, so changing any of them starts a fresh cache in the next process. Readers rely on write order. A blob counts as indexed only once its blobs row exists, and that row is written last in its transaction. A revision counts as complete only once its tree completion marker is written, after every supported blob.

outline_file and read_symbol index only the file they name. read_symbol rereads the blob and returns the span only if it still hashes to the stored span_sha256. find_symbol indexes the whole tree within file, byte and time budgets checked between blobs, and reports partial when it stops short. add_evidence anchors a citation through the same sidecar. Its handler is synchronous while parsing is asynchronous, so it indexes a missing blob by running index-file.js in a child process before its insert transaction. search_records keeps a full-text index of the store's records in the sidecar and refreshes it on each search.

§Vocabulary

  • code-index sidecar — The SQLite cache under the store's code-index directory holding extracted definitions, references, imports and tree listings keyed by (blob_sha, lang) and revision; never referenced from memory.db.
  • extractor generation — The extractor_id: a sha256 over EXTRACTOR_VERSION, every queries/*.scm file and grammars/manifest.json, naming the sidecar directory a build reads and writes.
  • symbol_id — A definition's name within one file: its enclosing scopes' ids, qualifier and name plus a language discriminator (parameter types, arity), with no path, revision or position.
  • tree completion marker — A trees_complete row for a revision, written only when every supported entry of that revision's tree has its blob indexed; find_symbol answers partial: true without it.

§Known defects here

2 defects here are open or awaiting verification. Each one's full record, with its evidence, is on Open findings.

  • With two server processes on one store, find_symbol can answer a revision as complete (not partial) while some of its blobs' symbols are missing, because another process's eviction deleted them after the completion marker was written. — P04-1 · Low · Open
  • If tree-sitter's runtime fails to start once, every later parse in that server process fails until restart; and a query that fails to compile leaks a Parser and a Language on the wasm heap on every retry. — P04-2 · Low · Open

§Challenge

§Challenge

Each claim was tested by looking for the code that would contradict it. The connection claim would fall to a per-request open; connection() keeps one handle and reopens only on an inode change. The read flow would fall if read_symbol served cached text; it re-hashes the span from git and refuses stale-entry. The search claim would fall if the completion marker and the hits were read apart or exclusion ran after the limit; both share one read transaction and the filter is in the WHERE clause. The eviction step was re-read line by line, which also confirmed the victim query sits outside its delete transactions.

Every claim survived. The completion claim survives at the moment of writing, with the limit that a later eviction in another process can falsify the marker it wrote (P04-1).

Test strength was challenged as well. The extract tests compare rows against hand-written goldens and check UTF-8 byte offsets on 2-, 3- and 4-byte characters, but they do not check that wasm objects are freed when a parse or query throws, so P04-2 is untested. Two checks cannot fail: the refresh test's hostile git configuration never reaches a fixture that pins its own git environment, and a partial-class check looks for a word absent from the file. The sidecar concurrency test proves convergence of two indexers but not the evict and complete interleaving.
