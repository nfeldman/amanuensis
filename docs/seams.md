| <a id="sm-01"></a>**SM-01** | ServerContext (the resolved project and the lazily opened database handle) | — | **[B-01](subsystems/b01-server-runtime-and-tool-dispatch.md)** ↔ **[B-02](subsystems/b02-repository-binding-and-storage-custody.md)** | ✅ | Assessed as [SC-1](concerns.md#sc-1) at 0fee11b, both sides confirmed-acceptable. The two accounts agree: one connection per process, opened on first use through a getter, never reopened or revalidated. Neither party has an operation that replaces the handle under the other, and both record the same consequence if one is replaced out of band — writes through a stale inode — which is why the rebuild procedure stops the process rather than asking the server to reinitialize. |
| <a id="sm-02"></a>**SM-02** | memory.db and the views initializeSchema creates on it | — | **[B-02](subsystems/b02-repository-binding-and-storage-custody.md)** ↔ **[B-03](subsystems/b03-conspectus-schema-vocabulary-and-invariants.md)** | ✅ | Assessed as [SC-2](concerns.md#sc-2) at 0fee11b, both sides confirmed-acceptable. The owner writes every object CREATE ... IF NOT EXISTS and cannot reach an existing store; the custodian applies the file on every open, asserts the two views by name, and rebuilds a table whose CHECK is strictly narrower than the source. The asymmetry is the point of the seam and both sides record it — with one qualification carried as a linchpin: the owner's comment beside dispositions.evidence_quality still says an existing database keeps the narrower constraint, which the custodian's migration has made false ([B03-4](findings.md#b03-4)). |
| <a id="sm-03"></a>**SM-03** | the ToolDefinition registry (every tool module's exported array) | — | **[B-01](subsystems/b01-server-runtime-and-tool-dispatch.md)** ↔ **[B-04](subsystems/b04-survey-record-tools.md)** | ✅ | Assessed as [SC-3](concerns.md#sc-3) at 0fee11b, both sides confirmed-bug, finding of record [B01-1](findings.md#b01-1). The two accounts agree exactly — a tool becomes visible by being present in an array index.ts concatenates, and by nothing else — and neither party can observe a breach: the producer has no registration call whose absence would show, and the consumer has no list of what exists to diff its concatenation against. The one artifact that holds both sides, gen-tool-inventory.mjs, builds its denominator from the served list and uses the full exported set only to group it. |
| <a id="sm-04"></a>**SM-04** | file_standing and finding_state_current (the two derived views) | — | **[B-06](subsystems/b06-locus-standing-and-the-reader-lenses.md)** ↔ **[B-03](subsystems/b03-conspectus-schema-vocabulary-and-invariants.md)** | ✅ | Assessed as [SC-4](concerns.md#sc-4) at 0fee11b, both sides confirmed-acceptable. The definer holds each predicate once and the reader on this seam consumes it without a fallback; the reader's own CASE expressions aggregate standing_state, a column the view produced. The seam is clean and the concern is not: two readers outside it compute the same predicates inline, recorded as [B04-5](findings.md#b04-5) and [B08-1](findings.md#b08-1), which is why [SC-4](concerns.md#sc-4) is a statement about these two parties and not about the codebase. |
| <a id="sm-05"></a>**SM-05** | finding_resolution_events and the current-state view over it | — | **[B-05](subsystems/b05-findings-dispositions-and-resolution-custody.md)** ↔ **[B-06](subsystems/b06-locus-standing-and-the-reader-lenses.md)** | ✅ | Assessed as [SC-5](concerns.md#sc-5) at 0fee11b, both sides confirmed-acceptable. Both parties treat the event spine as authority and the view as its single mapping: the appender writes one event per state change in the transaction that caused it, and the partitioner selects resolution_state from a view that LEFT JOINs one row per finding, so neither side can put a record in two partitions or in none. Whether the published pages honour that partition is checked separately, by the projection's state axis. |
| <a id="sm-06"></a>**SM-06** | memory.db, opened read-only by the projection while the server holds it read-write | — | **[B-08](subsystems/b08-materializer-rendering-pipeline.md)** ↔ **[B-02](subsystems/b02-repository-binding-and-storage-custody.md)** | ✅ | Assessed as [SC-6](concerns.md#sc-6) at 0fee11b, both sides confirmed-acceptable. The reader's connection is mode=ro, so it cannot repair the schema it finds and refuses the publish by name instead; the writer sets WAL, which is what permits the concurrent open, and truncate-checkpoints before any storage commit so the file a later reader sees carries every committed frame. Neither side claims a snapshot across a long publish, and the read-back compares finished bytes to a receipt precisely because there is none. |
| <a id="sm-07"></a>**SM-07** | .projection-contract.json (the per-page hash receipt) | — | **[B-08](subsystems/b08-materializer-rendering-pipeline.md)** ↔ **[B-09](subsystems/b09-projection-read-back-and-publication-custody.md)** | ✅ | Assessed as [SC-7](concerns.md#sc-7) at 0fee11b, both sides confirmed-acceptable. Membership is decided once: the render's page plan produces the list, the manifest records it, and write_contract hashes exactly the list it is handed. The verifier holds no independent enumeration to disagree with, which is what makes a green content axis a statement about the tree at the path it was read from rather than about a directory that happened to match a pattern. |
| <a id="sm-08"></a>**SM-08** | the conspectus vocabulary (enum values and what each authorizes) | — | **[B-10](subsystems/b10-the-amanuensis-skill.md)** ↔ **[B-03](subsystems/b03-conspectus-schema-vocabulary-and-invariants.md)** | ✅ | Assessed as [SC-8](concerns.md#sc-8) at 0fee11b, both sides confirmed-bug, finding of record [B10-1](findings.md#b10-1). The source declares twenty-five enums and the generated parties are compared against all of them; the hand-written party is compared on two, each located by its own literal regex. Both sides contribute to the gap: the prose publishes vocabularies with no stable anchor to find them by, and the contract declares no anchor a checker could use. The repair belongs on the seam rather than on either party — an anchor per enum the prose publishes, driven from the same loop the generated parties use. |
| <a id="sm-09"></a>**SM-09** | the built server at mcp-server/dist/index.js, spawned by gates over the MCP protocol | — | **[B-11](subsystems/b11-development-harness-and-gates.md)** ↔ **[B-01](subsystems/b01-server-runtime-and-tool-dispatch.md)** | ✅ | Assessed as [SC-9](concerns.md#sc-9) at 0fee11b, both sides confirmed-acceptable. In CI the build is a step before every gate that spawns the server and a failed build fails the job, so the dist a gate judges corresponds to the source in the same checkout. Outside CI the correspondence is not guaranteed — the reader-lenses launcher tolerates a failed build at a red commit on purpose — and the contract that carries the weight there is on the gate side: load the subject defensively, report absence as a failed assertion, never die on the import. |
