Glossary

§Codebase-wide

§file ledger

The file_ledger table: one row per survey path saying which subsystem owns it, how it is classified, the commit it was examined at and whether it is stale.

detect_changes reconciles the file ledger against the tree at a commit, marking drifted and absent rows, and records a ledger digest (path and classification, sorted and NUL-joined) in the reconciliation row; a reconciliation stands only while that digest still matches the ledger. Paths outside the survey set get no ledger row.

First seen: mcp-server/src/invariants.ts:ledgerDigest@ec393801fd8140a8a9269d3e7132733c4bcb63df

§store

One surveyed repository's durable record: the memory.db SQLite database the server opens in WAL mode, in a storage directory that is its own git repository.

The store is memory.db, opened by openDatabase in WAL mode with foreign keys on and migrated on open, kept in the storage directory (the workspace's .amanuensis by default) whose own git history commit_phase_gate and end_session extend. The call-log and code-index sidecars live beside it, outside those commits. The server is its only writer; the materializer and the dev completeness checker read it read-only.

First seen: mcp-server/src/db.ts:openDatabase@ec393801fd8140a8a9269d3e7132733c4bcb63df

§Scoped to C-01

§omission ledger

The omitted[] list a bounded locus-route response carries, naming by section, reason and exact count (with ids) what the byte budget or policy left out.

describe_locus, get_attention and get_history serve within a wire-byte budget. Truncation re-measures the real wire size and drops unknown entries first, then items round-robin; the served items plus the omitted counts must equal each section's census, or the call throws rather than return an unreconciled answer.

First seen: mcp-server/src/tools/locus.ts:describeLocusHandler@ec393801fd8140a8a9269d3e7132733c4bcb63df

§standing

What the record authorizes saying about a locus, computed per call from its ledger rows (unledgered, excluded, scoped-unread, examined, examined-stale, absent, mixed) and an authority ceiling from its owners' status.

describe_locus leads every answer with standing. For a file, owners come from the file_standing view; an examined row stays examined only if its ref_sha is an ancestor of the workspace HEAD; a path the survey scope excludes reads no owner rows and stands excluded. Sections such as structure are withheld, with a declared count, when the standing does not authorize them.

First seen: mcp-server/src/standing.ts:fileStanding@ec393801fd8140a8a9269d3e7132733c4bcb63df

§Scoped to D-01

§evidence mode

A field in a receipt or report, "real-host" or "fixture-red", that the checkers read to decide which checks apply.

The operating-envelope checker validates raw event, stderr and store-custody logs only for real-host receipts. The release-readiness checker skips its roadmap, clean-replay and candidate-suite checks for a fixture-red report. In both checkers the mode is read from the document under check.

First seen: dev/check-friction-free-release-readiness.mjs:validate@ec393801fd8140a8a9269d3e7132733c4bcb63df

§red gate

A sabotaged receipt case from a red matrix fixture. The checker must exit non-zero on the case, with the stated error text.

The red-gate tests run each checker once per case with --case <caseId>. Each case applies JSON-pointer mutations to a base receipt. The test asserts a non-zero exit and that the expected error appears in stderr. The codex-host and release-readiness tests also run a control case meant to pass. Only the release-readiness test asserts that control's exit status.

First seen: dev/check-friction-free-release-readiness.mjs:loadReport@ec393801fd8140a8a9269d3e7132733c4bcb63df

§Scoped to D-02

§carry source

What a store rebuild carries the predecessor's findings from: an archived store read read-only, an export carrying archived_store_id, or 'none' with a reason.

dev/rebuild-store.mjs requires --carry-from and --carry-reason and resolves the source before anything is discarded, because a carry source found unreadable after the discard would leave the rebuild with neither the predecessor nor a way to name it. A store supplies its own identity through readArchivedStore in the built server's invariants.js; an export must carry a top-level archived_store_id and a findings array, and may be cross-checked against the store it came from with --carry-verify-store; 'none' is recorded as an explicit reasoned empty carry run so that 'nothing was carried' differs from 'nobody ran a carry'. After the read-back of the empty store, every finding of the source goes through begin_carry_run, carry_finding and finish_carry_run.

First seen: dev/rebuild-store.mjs:resolveCarrySource@ec393801fd8140a8a9269d3e7132733c4bcb63df

§docs promotion

Copying a green publication from the store's .amanuensis/docs into the repository's tracked docs/, verified by its contract hashes and a three-axis read-back both before the copy and at the destination.

materialize_docs can only write inside the storage directory, so publishing to the tracked tree is a second, explicit step: dev/promote-docs.mjs. It refuses a source whose .projection-contract.json is missing, names no page, names a non-HTML page other than search-index.js and README.md, or no longer matches the bytes on disk; a source with no .manifest.json; a source whose read-back (materialize.py --readback-only) is not green on state, coverage and content; and a destination holding files no manifest claims. It stages a copy beside the destination, swaps it in by rename with the previous tree kept as a backup, re-checks the contract and read-back at the destination, and restores the backup on any failure. With --receipt it writes a promotion receipt (contract amanuensis-reader-lenses/promotion/v1).

First seen: dev/promote-docs.mjs:matchContract@ec393801fd8140a8a9269d3e7132733c4bcb63df

§fully surveyed

The store-level verdict that all seven clauses of the completeness predicate hold: inventory, every subsystem mapped, every concern decided, every seam integrally assessed, exact composition fan-in, a green three-axis read-back, and every carried finding decided.

dev/check-store-fully-surveyed.mjs evaluates the predicate read-only against one memory.db and the repository tree. Clause 1 takes the survey set (the tree at the checked revision minus the standing reconciliation's scope_exclusions) and requires each survey path to have exactly one classified ledger row, plus a sorting row in sorted mode. Clauses 2-4 skip subsystems whose ledger rows are all excluded, and seams touching them. Clause 2 asks every remaining subsystem to be 'mapped'; clause 3 every (subsystem, active concern) pair to have a terminal disposition with at least one attached evidence revision git can find; clause 4 every seam to have two mapped endpoints and to appear in a composition run whose integral lane is scored-pass. Clause 5 asks every composition run ever recorded to have exactly its expected items, all scored-pass; clause 6 that the newest projection verification run is ok on state, coverage and content; clause 7 that every carried finding has a current outcome. A clause whose denominator is zero is reported as not evaluable (printed 'none') and does not pass, except clause 7, which passes over zero carried findings. Exit 0 means fully surveyed, 1 not, 2 cannot run.

First seen: dev/check-store-fully-surveyed.mjs:clause@ec393801fd8140a8a9269d3e7132733c4bcb63df

§obligation id

A colon-separated name for one unmet requirement of the completeness predicate, such as file:&lt;path&gt;:assignment, concern:&lt;sid&gt;/&lt;code&gt;:disposition, seam:&lt;id&gt;:integral-assessment or carried:&lt;store&gt;:&lt;finding&gt;.

Each clause of dev/check-store-fully-surveyed.mjs reports its unmet requirements as a missing list of obligation ids rather than a count, so a red verdict names what somebody has to do. The shapes are inventory:revision / inventory:reconciliation / inventory:tree / inventory:unledgered, file:&lt;path&gt;:assignment and file:&lt;path&gt;:exclusion-reason, unsorted:&lt;path&gt;, subsystem:&lt;id&gt;:phase-sequence, concern:&lt;sid&gt;/&lt;code&gt;:disposition and :evidence-revision, seam:&lt;id&gt;:endpoint:&lt;sid&gt; and :integral-assessment, run:&lt;run&gt;:dispatched|landed|scored:&lt;item&gt; and run:fan-in:no-run-recorded, export:&lt;axis&gt;:read-back, and carried:&lt;archived_store_id&gt;:&lt;archived_finding_id&gt;. The comment at the head of the script says the ids are ADR-0001's own, so a red here has the same destination as a red there.

First seen: dev/check-store-fully-surveyed.mjs:clause@ec393801fd8140a8a9269d3e7132733c4bcb63df

§wire bytes

The size of the whole tools/call result a host receives from describe_locus (text block plus structuredContent), as distinct from the compact payload, the item-free floor and the declared budget.

dev/measure-locus-default.mjs reports four byte figures per locus for a default describe_locus call: wire_bytes (the whole result on the wire), payload_bytes (the compact payload alone), floor_bytes (the response with every item removed, re-serialized in the server's envelope) and budget_bytes (the byte budget the response declares in its trace). Gate EX13 (dev/test-locus-default-measure.mjs) slices the raw result member out of the JSON-RPC line so the wire figure is not re-serialized, and checks the script's figures against a second server.

First seen: dev/measure-locus-default.mjs:measure@ec393801fd8140a8a9269d3e7132733c4bcb63df

§Scoped to D-03

§documentation gate

A dev/ script that reads a live document (README, INSTALLATION, a backlog item, the roadmap source) and checks its text against code, a plan or a pinned baseline, printing one GATE line.

The D-03 (Repository docs, CI and documentation gates) gates SI0, SI11, O0, SO0, SC0 and SC9 each match a document's wording with regexes or substring tests, compare it with what the code, the packet plan or a frozen start copy says, and exit non-zero on drift. Only SI11 and SC9 also run themselves against damaged input. The roadmap renderer and its test belong here too, but no workflow runs them.

First seen: dev/test-scope-docs.mjs:START_COPIES@ec393801fd8140a8a9269d3e7132733c4bcb63df

§start copy

A frozen copy of a user doc as it stood at a lane's start commit, pinned by sha256, that a gate diffs the live doc against.

dev/fixtures/scope-docs/start holds README.md and HISTORY.md at commit 45a0cf5. SC9 refuses a copy whose hash differs from its pin, then allows the live doc to differ from it only in the ways the scope packet intended. The copies therefore freeze those docs: an unrelated later edit in the frozen regions turns the gate red.

First seen: dev/test-scope-docs.mjs:START_SHA256@ec393801fd8140a8a9269d3e7132733c4bcb63df

§Scoped to M-01

§clean publish

A render into a fresh staging directory beside the output, promoted over the previous output by two renames only when the render and its read-back are green.

materialize.py --clean-publish (materialize_docs clean_publish=true) first refuses when the existing output holds a file its prior manifest does not claim (unmanaged_output_files). It then renders with force_full into a mkdtemp directory named .<output>.amanuensis-stage-*, and if the summary is ok renames the old output to .<output>.amanuensis-backup-<uuid>, renames the stage to the output and removes the backup. A red render deletes the stage and leaves the old output as it was. Any exception, including SIGTERM converted to Terminated, deletes the stage and renames the backup back when no output exists. Without clean publish the render writes in place, so a red read-back leaves the new pages in docs/.

First seen: materializer/materialize.py:main@ec393801fd8140a8a9269d3e7132733c4bcb63df

§page plan

The ordered list of PagePlan rows, one per page the store requires, each with its path, nav group and a build closure; recomputed from the store every run.

Materializer._plan returns the static pages (overview, architecture, subsystems map, files, the Unresolved, History and Method pages, plus the three imported-artifact pages when the store has a record or an unwithdrawn import for them), then one page per subsystems row and one per diagnosticity_sessions row. Each PagePlan carries the path, title, label, hint, use_when sentence, nav group and subgroup, and a build closure that returns the page model and its source hashes. The reader's guide route table, the HTML shell's navigation and the read-back's expected paths are all derived from this one plan.

First seen: materializer/amanuensis_materializer/core.py:PagePlan@ec393801fd8140a8a9269d3e7132733c4bcb63df

§recorded publication

A render whose read-back the caller records in the store (projection_verification_runs), so its pages carry no command-line notice.

materialize.py takes --recorded-publication to mean the caller will record the read-back; it then passes an empty notice to every page. Without the flag, cli_render_notice makes every page end with a notice that its read-back was not recorded. The MCP server always passes the flag and records the summary's readback in projection_verification_runs and projection_mismatches (materialize.ts recordReadback). The CLI refuses --recorded-publication together with --no-verify-readback, and the server refuses verify_readback=false, because there would be nothing to record.

First seen: mcp-server/src/tools/materialize.ts:recordReadback@ec393801fd8140a8a9269d3e7132733c4bcb63df

§unmanaged output file

A file in the output directory that the prior manifest does not claim; its presence refuses a clean publish.

unmanaged_output_files treats as owned .manifest.json, .projection-contract.json, the manifest's projection_files and, for a manifest written before HTML became the only view (no views key), its .md pages. An output with no manifest makes every file unmanaged, and an unreadable manifest makes the manifest itself unmanaged. The clean publish refuses rather than delete a file a human placed beside the generated pages.

First seen: materializer/materialize.py:unmanaged_output_files@ec393801fd8140a8a9269d3e7132733c4bcb63df

§Scoped to M-03

§composite index figure

A bare percentage, or a ratio placed after a health, score or readiness label, that lint.py's composite_index_violations refuses in the project purpose.

composite_index_violations checks each line, after removing code spans, for any bare percentage, and for an 'n of m' or 'n/m' ratio that follows a label such as health, overall, composite, readiness, maturity, completeness, confidence, grade, rating or score. orientation_violations does not run it. The overview thesis and the read-back apply it to the project purpose only, and the write path does not run it.

First seen: materializer/amanuensis_materializer/lint.py:composite_index_violations@ec393801fd8140a8a9269d3e7132733c4bcb63df

§status assertion

A sentence that the orientation lint withholds: a survey-status term asserted as the complement of a copula about this project, this codebase, the conspectus, the survey, the documentation or a one-letter subsystem id.

lint.py masks code spans and fenced blocks first. It then refuses one of the nine ORIENTATION_FORBIDDEN_TERMS when that term follows is/are/was/were/remain(s), with one of the _SUBJECT subjects before the verb. The same lint refuses a slash count fraction a/b where a is not larger than b. A term preceded by a hyphen, backtick or word character is cleared, which keeps phrases like memory-mapped usable.

First seen: materializer/amanuensis_materializer/lint.py:orientation_violations@ec393801fd8140a8a9269d3e7132733c4bcb63df

§Scoped to M-04

§HTML projection

The writer that serialises page models to the published HTML pages, search-index.js and README.md, and is the only place record text is escaped.

render_html_projection takes one SitePage per planned page and builds the shell, navigation, inline CSS and JS. It escapes each node for its context: html.escape for text and quote=True for attributes. SVG from diagrams.py, and marker strings, are inserted verbatim. Files are written in place, pages whose bytes are unchanged are skipped, and retired files are unlinked afterwards.

First seen: materializer/amanuensis_materializer/html_projection.py:render_html_projection@ec393801fd8140a8a9269d3e7132733c4bcb63df

§search index

search-index.js, a standalone script assigning one global with the JSON list of searchable records, which pages load with a relative script src.

render_search_index serialises the index with json.dumps (ensure_ascii on). The file is never inlined into a page. The page's inline JS builds results with textContent and createElement rather than innerHTML, so record text in the index is not interpreted as markup.

First seen: materializer/amanuensis_materializer/html_projection.py:render_search_index@ec393801fd8140a8a9269d3e7132733c4bcb63df

§Scoped to M-05

§publication receipt

The .projection-contract.json file a publication writes beside its pages, listing each page's sha256, its local links and the render notice, against which the read-back's content and link checks run.

write_contract builds it from the finished bytes after cross-references are resolved, so it describes what a reader sees. The read-back's content axis compares every page on disk with its receipt hash and requires every planned page to be listed; the coverage axis compares local links with the receipt's link list. The receipt is not signed: it proves the pages have not changed since the publication wrote it, not that they were right.

First seen: materializer/amanuensis_materializer/readback.py:write_contract@ec393801fd8140a8a9269d3e7132733c4bcb63df

§read-back axis

One of the three independent questions the read-back asks of a publication: state (each authoritative record appears exactly once with its state), coverage (every planned page, link and record is present, nothing unplanned) and content (bytes and prose match the receipt and the store).

Every mismatch carries an axis, an object type, an object id and a detail. A publication is ok only when all three axes are green; a clean publish promotes only then, and the server records the axes and mismatches as a projection verification run.

First seen: materializer/amanuensis_materializer/readback.py:ProjectionVerifier@ec393801fd8140a8a9269d3e7132733c4bcb63df

§record mark

A data-record (with data-state) attribute on the element that prints a store record, or data-node and data-edge on a drawn diagram element, by which the read-back finds and compares each rendered record.

_MarkInventory parses a page's marks into occurrences: adjacent elements with the same mark join into one record unless they are article or li, their visible text is tokenized, and status chips inside are collected as the state a reader sees. A drawn node without a shape or words is read as hollow.

First seen: materializer/amanuensis_materializer/readback.py:_MarkInventory@ec393801fd8140a8a9269d3e7132733c4bcb63df

§Scoped to M-08

§LensFixture

The fictional project gate P8 seeds (five subsystems, fifteen ledger rows, three seams, three findings, matrix DM-7) and the golden corpus records as the lens fixture.

Every derived count in the fixture is distinct so that no wrong predicate coincides with the right answer: 12 distinct ledger paths over 15 rows, 13 obligation-bearing rows, 4 candidates, 15 tracked paths with 4 unledgered, three paths that collide under slugify (src/a/b.ts, src/a-b.ts, src/a.b.ts), one path whose owners record different revisions, one whose owners disagree on standing, and one absent path. The same seed, run by make-golden.py, produces the committed lens/memory.sql, inputs.json and html pages.

First seen: materializer/test-lens-pages.py:seed@ec393801fd8140a8a9269d3e7132733c4bcb63df

§pair denominator

Gate P8's rule that a gap is counted in the unit it occupies: unassessed (seam, side) pairs over 2 × seams, undispositioned (subsystem, active concern) pairs over subsystems × active concerns.

The lens fixture is built so that the rejected global predicates (a concern dispositioned nowhere, a seam with no SC disposition on either side) report zero, while the pair predicates report 5 of 6 seam sides and 15 of 20 concern pairs. global_predicates_are_zero asserts that premise against the seeded store, so a not-yet-surveyed page that counted seams or concern codes instead of pairs would print zero and turn the gate red (the VP4 failure the gate names).

First seen: materializer/test-lens-pages.py:main@ec393801fd8140a8a9269d3e7132733c4bcb63df

§workspace-dependent golden page

A lens golden page (index.html, not-yet-surveyed.html) whose HTML depends on the throwaway git workspace the fixture was built in, so no test compares it and --recorded does not rewrite it.

The lens fixture is seeded by test-lens-pages.py into a store whose checked revision is the first commit of a git workspace make_workspace creates in a temp directory, with a second commit so the head differs. The overview prints the repository head and how it relates to the checked revision, and not-yet-surveyed reads the tree at the checked revision. That workspace is not committed with the corpus, so a rebuild from lens/memory.sql cannot reproduce those two pages. make-golden.py lists them in WORKSPACE_DEPENDENT and --recorded skips them; test-store-only-model.py and test-store-only-no-markdown.py skip both, test-store-only-convert-overview.py skips the lens index and test-store-only-convert-method.py skips lens not-yet-surveyed. Only a full regeneration rewrites them, and nothing reads them back.

First seen: materializer/make-golden.py:WORKSPACE_DEPENDENT@ec393801fd8140a8a9269d3e7132733c4bcb63df

§Scoped to P-01

§refusal

A tool answer that declines the call, either a thrown ToolError (with an optional rule code) or a returned {ok:false, error}; both reach the host as errors.

The dispatcher classifies each call as ok, refusal, validation (unknown tool or schema mismatch) or exception (any other throw) and records that class, the rule code and the throw site in the call log. A refusal does not undo writes the handler already made; atomicity is each handler's own transaction.

First seen: mcp-server/src/index.ts:refusal@ec393801fd8140a8a9269d3e7132733c4bcb63df

§workspace handshake

The first get_project_info call with an absolute workspace path, which binds a server process to one repository for its lifetime.

A server launched without a resolvable workspace starts unbound and refuses project tools. get_project_info(workspace) canonicalizes the path to its git root or realpath and binds the process; any later handshake naming a different workspace is refused, so one process serves one repository.

First seen: mcp-server/src/index.ts:WORKSPACE_INSTRUCTIONS@ec393801fd8140a8a9269d3e7132733c4bcb63df

§write lock
