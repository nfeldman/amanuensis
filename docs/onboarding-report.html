Reader's guide

Onboarding record

§Repository shape

One repository holds two programs and the text that drives them. mcp-server/ is the TypeScript MCP server, shipped to npm together with the installer CLI. src/index.ts binds a workspace and dispatches every tool call. src/schema.sql, db.ts and invariants.ts define memory.db, and src/code-index/ is the tree-sitter index.

materializer/ is the Python program that renders the HTML pages. Its entry point is materialize.py, and its code is in the amanuensis_materializer/ package. make-golden.py rewrites the golden corpus under fixtures/store-only-golden/. .claude/skills/amanuensis/ is the agent skill. dev/ holds repository-level checkers and harnesses, and .github/workflows/ runs CI and publishing.

The server writes the live memory.db. make-golden.py seeds two fixture databases through Python's sqlite3, and has the built server migrate and import the two legacy ones. The materializer and the store completeness checker in dev/ open it read-only, and both depend on table names in schema.sql. The materializer also requires two of its views.

The server runs the materializer as a child process. materialize_docs spawns materialize.py and records the read-back from the last line it prints. The write-time lint in orientation-lint.ts runs the materializer's own lint.py under python3, and lets the write through when it can't run.

gen-vocabulary.mjs writes both src/vocabulary.ts and the materializer's vocabulary.py from mcp-server/contracts/conspectus-vocabulary.json. CI fails when either copy, or a schema.sql CHECK literal, no longer matches it.

At prepack the skill and the materializer are copied into the npm package. check-reference-calls.mjs checks the tool calls the skill quotes against the built tool schemas.

mcp-server/package.json has no test script. .github/workflows/test.yml runs each gate as its own step, and its server job installs Python because the server's tests spawn the materializer.

§Runtime

The product is a Node.js MCP server, written in TypeScript and published as @gruetech/amanuensis, and a separate Python program that renders the pages. An agent host (Claude Code, Codex or Copilot) launches the server as a child process and calls its tools over stdio. The process binds to one workspace, taken from its launch arguments, its environment, a launch directory or the first get_project_info call, and refuses any other. One context object carries the binding, the database handle and the active session for every call. The dispatcher validates the arguments against the tool's schema, opens memory.db before any tool but get_project_info, and then calls the handler.

Most work inside the process is synchronous. The server uses better-sqlite3 for memory.db (in WAL mode) and for two sidecar databases, the code-index cache and the call log. It runs git in the target repository and keeps a long-lived git cat-file --batch reader open for the code index. The storage directory is its own git repository, or may sit in an outer one under a configured storage root, and the server commits after a WAL checkpoint.

The Python program is the materializer. materialize_docs runs it with spawnSync, which blocks the server for up to 900 seconds. The materializer opens memory.db read-only, so the schema is the contract between the two languages. It renders HTML, reads its pages back and prints a JSON summary as its last line of stdout, which the server parses and records. It also asks git for the origin and the branch that source links point at.

The amanuensis installer CLI ships in the same package. It rewrites each host's MCP registration and installs the skill, which is the Markdown method the host's model follows. Development scripts in dev/ read the store through node:sqlite and drive a Codex host. One of them runs the materializer and copies its pages into docs/, which GitHub Actions deploys to Pages. Actions also publishes the package to npm on a version tag.

§Stateful entities

Amanuensis keeps its records in the store directory, by default .amanuensis/ in the workspace, or else a configured shared storage root. At its centre is memory.db, a SQLite database in WAL mode. If the store is, or for shared storage sits in, a git repository, commit_phase_gate and end_session checkpoint the WAL and commit the directory. A new store is built in a staging directory and appears at the store path through one rename. The server migrates and seeds memory.db on opening; then only write tools change it, some without a session. start_session sets one session id for the whole process.

Most tables are append-only. Those listed in mcp-server/contracts/append-only-tables.txt have triggers refusing DELETE and UPDATE, though some, like composition_items, fix only part of the row. A correction is therefore a new row; for eligible subjects, explanation readers serve the newest whose commit resolves, or with no workspace bound the newest, unless withdrawn. A claim version's content is fixed but for setting valid_until_sha once; reset_subsystem can delete versions. A partial unique index allows one current version per claim_key. A few tables hold a current value that writes overwrite:

  • file_ledger: retiring a row deletes it.
  • dispositions: one verdict per subsystem and concern, deleted by reset_subsystem.
  • vocabulary: one gloss per term, whoever wrote last.
  • subsystems.status: each change also appends a transition row.
  • the single git_state row: set_git_state can move its last_checked_sha without a reconciliation.

Two sidecar databases sit under the store. The call log is queued in memory, flushed later and never pruned. The code index keeps one database per extractor generation; with the index on, opening the store removes other builds' generations untouched for 30 days.

Within one process, an awaiting handler, such as a code-index tool, lets other requests run. Processes sharing a store rely on SQLite's locking and a code-index recovery marker file.

§Concern calibration

All eleven territories apply, because the server is a long-lived process that shells out, keeps several SQLite files that more than one process may open, and publishes agent-written text as HTML. The calibration below says where each territory is sharpest in this codebase, so a surveyor knows which concern to press first.

Atomicity and exceptional paths matter most where one tool does several things that are not one SQLite transaction: commit_phase_gate checkpoints the WAL and then runs git in the storage directory, materialize_docs spawns Python and then promotes and records a receipt, and first-use initialization stages a store before marking it complete. Inside memory.db, a handler that writes and then refuses must run in one transaction, which is the concern EP-1 probe.

Concurrency is real despite Node's single thread, since several server processes and the materializer can open one store. Bounded waiting matters for the same reason: the call-log and code-index sidecars set a busy timeout explicitly, while memory.db relies on whatever better-sqlite3 sets by default, which a surveyor should confirm. Time limits on child processes are the concern TB-1 probe; the ps call at startup and the python3 spawn are the calls to check first.

Trust boundaries are sharpest at two points: paths and environment variables arriving from agents and hosts, and record text published into HTML and the search index. Seam contracts matter because the server and the materializer share a schema and a vocabulary across two languages, and the skill quotes tool names and refusal sentences that the server can change.

Cache coherence and incremental-versus-full equivalence centre on the code-index sidecar, keyed by blob and extractor, and on the reconciliation digests that decide whether a scope reading still stands. Resource lifecycle is sharpest for tree-sitter objects on the WebAssembly heap, which the garbage collector does not free. Identity concerns are worktrees sharing a project key, paths that change exclusion between revisions, and symbols resolved per revision. Aliasing is the weakest territory here, confined to module-scope state shared across tool calls.

§Survey plan

The survey runs layer by layer, and within a layer by priority, so that each subsystem is read after the ones it depends on.

The platform layer comes first: the store schema, migrations and storage history (P-02 (Store schema, migrations and storage history)), then server runtime and dispatch (P-01 (Server runtime and dispatch)), then workspace binding with the installer (P-03 (Workspace binding, activation and installer)) and the code index (P-04 (Code index)). The records layer follows: survey scope, ledger and reconciliation (R-01 (Survey scope, ledger and reconciliation)), evidence, claims and findings (R-03 (Evidence, claims and findings)), the survey ladder and judgment records (R-02 (Survey ladder and judgment records)), explanations and project records (R-04 (Explanations, narratives and project records)), and the vocabulary contract and parity checks (R-05 (Vocabulary contract and parity checks)). The consumer layer is the locus route, standing and attention (C-01 (Locus route, standing and attention)).

The workflows layer is read next, starting with change impact and refresh (W-01 (Change impact, refresh, revalidation and review brief)) and legacy import with carried findings (W-06 (Legacy import, carried findings and store comparison)), then review and composition (W-02 (Review sessions, review analysis and composition)), decisions and the codebase brief (W-03 (Decisions, design sessions and codebase brief)), research and the crosswalk (W-04 (Research, crosswalk and learning ledger)), and evaluation with the Chorusmith adapter (W-05 (Evaluation, operating envelope and Chorusmith adapter)).

The presentation layer starts at the materializer's entry and publication path (M-01 (Materializer entry, read model and publication)) and read-back (M-05 (Publication read-back)), then renderers (M-02 (Page renderers)), page truthfulness (M-03 (Page truthfulness: vocabulary, lint and coverage statements)) and the HTML projection (M-04 (HTML projection, search index and diagrams)), orientation exposure (M-06 (Orientation exposure)), and last the golden corpus (M-07 (Golden corpus generator and rebuildable goldens)) and lens pages (M-08 (Lens golden pages)). The agent skill (K-01 (Agent skill)) is read after the server so its quotations can be checked against code. The repository layer closes the survey: store gates and docs promotion (D-02 (Store gates, rebuild, docs promotion and reader measures)), repository docs and CI (D-03 (Repository docs, CI and documentation gates)), and the activation harness (D-01 (Activation evidence and release-readiness harness)).

The pilot should take one mid-sized subsystem with clear seams, such as the survey ladder (R-02) or the code index (P-04), to calibrate pace before the high-priority platform subsystems are read.
