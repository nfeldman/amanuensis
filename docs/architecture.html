Terms on this page

Subsystem
A part of the codebase the survey treats as one unit, with its own files and its own page. The agent chose the split during onboarding.
Layer
A group of subsystems with a similar role. Pages group subsystems by layer.
Survey depth
How far the survey of a subsystem has got. Unmapped: not started. Scoped and Structural: that pass is done. Reviewing concerns and Challenging claims: that pass is under way. Mapped: every pass is done. Deferred: left out of the survey on purpose. Each depth limits what the record may claim.
System boundary
A place where two subsystems share something (a table, a queue, a cache) and depend on each other's assumptions about it.
Recorded edge
A dependency or data flow between two subsystems that the agent wrote down. Edges are never guessed from names.
Purpose, account
A subsystem's one-sentence purpose and its longer explanation of how it works, each written from evidence.

Reader's guide

Architecture

§How the parts fit together

Amanuensis lets a coding agent survey a repository, keep what it learns as records bound to commits and evidence, and publish those records as a static HTML report. An agent host (Claude Code, Codex or Copilot) launches the amanuensis-memory MCP server over stdio. The amanuensis CLI registers the server with each host and installs the skill, the documents that teach the agent the survey method.

Every call goes through dispatchTool in mcp-server/src/index.ts, which rejects an unknown tool, or arguments that fail the tool's strict schema, before any handler runs. The workspace, bound at launch or by the first get_project_info, is never rebound. Handlers write to the store, memory.db, a SQLite database in WAL mode. Unless nested in an outer repository, the store's directory is its own git repository, committed at phase gates. The dispatcher does not undo what a handler wrote before it refused. Some writes, like severity regrades, use immediate transactions so concurrent servers serialize.

add_evidence resolves its commit and refuses a path outside the survey set: the tree minus what owner rules, ignore files and onboarding sorting exclude. Triggers make some tables append-only; dispositions are revised in place. A forward move checks each rung's prerequisites, unless resuming an unlogged parking. describe_locus reports a locus's standing: what the record authorizes saying about it. An examined file becomes stale once its commit is no longer an ancestor of HEAD.

materialize_docs spawns the Python materializer, which opens the store read-only and leaves all escaping to the HTML writer. A publication writes a receipt of page hashes; a server clean publish replaces the old pages only if a read-back against the store passes, which a hand run may skip. The server lints an explanation before storing it, refusing a failing one; a lint that cannot run lets it through.

Recorded at 94d98773. 1 of its 20 cited files changed since: mcp-server/src/schema.sql.

  • C-01 — Locus route, standing and attention: This is how agents ask the survey what it knows. describe_locus answers for one file, symbol, subsystem or term, and leads with its standing, so an unread or stale file is not mistaken for a read one. get_attention lists what is unresolved, get_history what was concluded, and get_dashboard gives project totals. The locus tools declare what a bounded reply leaves out.
  • D-01 — Activation evidence and release-readiness harness: In six Codex CLI runs, this subsystem shows maintainers the Amanuensis MCP server binding each run to its repository and leaving the user's Codex config as it found it. The evidence is receipts from a real Codex CLI host launching it in scratch Git repositories. A beta release-readiness report gathers them by digest, and red-gate tests show that each receipt checker refuses a sabotaged receipt.
  • D-02 — Store gates, rebuild, docs promotion and reader measures: Maintainer tools for a store and its published pages. One checks a store against ADR-0001's seven completeness clauses and names up to twelve unmet obligations per clause, or every one with --json. Another discards and reinitializes a store, carrying its findings forward. A third copies a verified publication into the tracked docs/ tree.
  • D-03 — Repository docs, CI and documentation gates: The GitHub workflows test the server, the materializer and the installed package on every branch push, and publish @gruetech/amanuensis to npm when a v* tag is pushed; that run checks the packed artifact, which runs the MCP compatibility test on the installed server, not the full suite. The dev/ documentation gates check the README, HISTORY, backlog and roadmap against the code and the plans.
  • K-01 — Agent skill: The skill is the method an agent follows to survey a codebase through the Amanuensis server. SKILL.md routes requests to references that say which tools to call, in what order, and what the server will refuse. The skill ships in the npm package and is installed into each host's skill directory. Its dev tests check that the text matches the server's tool names, refusals and statuses.
  • M-01 — Materializer entry, read model and publication: It renders memory.db, opened read-only, as a static HTML site in the store's docs directory. The server's materialize_docs tool runs it. A render refuses when the latest exclusions fail their digest. A default render overwrites the old pages before its read-back against the store; a server clean publish replaces the old site only when the read-back passes. The server records read-backs by run id.
  • M-02 — Page renderers: The renderers.render_* functions turn the survey store into published pages. Each reads memory.db and returns a page model (page.py) and hashes of sources it read; the manifest re-renders when these or the model change. The HTML writer in M-04 (HTML projection, search index and diagrams) lays the model out and escapes text; diagrams.py escapes its SVG.
  • M-03 — Page truthfulness: vocabulary, lint and coverage statements: Keeps the pages from claiming more than the store holds. vocabulary.py, generated from the vocabulary contract, supplies labels, meanings and the SQL for open findings and obligation-bearing files. lint.py withholds recorded prose that asserts survey status or states a count as a fraction; the server runs the same check on writes. Tests check page counts and placeholders against the store.
  • M-04 — HTML projection, search index and diagrams: It turns the survey's page models into the published report: a static HTML site that works from file:// as well as from a web server. Diagrams are drawn during materialization as inline SVG or HTML, so the browser needs no diagram runtime; unrecognized Mermaid prints as source. Every page shares one navigation rail, a search index, and a stylesheet and script stored under content-hashed names.
  • M-05 — Publication read-back: The read-back checks that the published pages say what the store holds. It reads memory.db and the finished files and reports where they disagree: a record missing, repeated or shown in the wrong state, a planned page or link absent, or bytes that differ from the publication receipt. --clean-publish keeps the live pages until it passes, unless --no-verify-readback is given.
  • M-06 — Orientation exposure: These CI gates check the published site's orientation features against design/orientation/PLAN.md: the page index's "Use it when" lines, the reader's guide, ID links, per-page terms, the overview, survey notes and the command-line render. A gate fails if a page's report or an ancestor is hidden by attribute or inline style. Each publishes a seeded store through materialize.py and reads the HTML.
  • M-07 — Golden corpus generator and rebuildable goldens: The golden corpus records the materializer's HTML page by page. The store-only tests rebuild each store fixture from its memory.sql and check today's pages match the recorded ones byte for byte, bar two workspace-bound lens pages. make-golden.py writes the corpus from an in-process materializer run, keeping what the HTML stage was given and what it printed. It writes any --packet name to VERSION.
  • M-08 — Lens golden pages: A synthetic survey for testing what the materializer publishes. test-lens-pages.py (CI gate P8) seeds it, publishes it and checks the page plan, navigation, Files index and Not yet surveyed. make-golden.py writes the same fixture to lens/ as a memory.sql dump and its HTML, which the store-only tests rebuild and compare byte for byte, except About this survey and Not yet surveyed.
  • P-01 — Server runtime and dispatch: Every Amanuensis tool runs in this process. It speaks MCP over stdio, binds to one workspace for its lifetime and holds one store connection; compare_conspectuses opens two more. Call outcomes go to a sidecar database, best effort; the reply never changes.
  • P-02 — Store schema, migrations and storage history: The store is memory.db, a SQLite file. This part defines its schema; triggers bar deletes from 104 tables and freeze listed columns. Opening migrates old stores and refuses one lacking a declared table, view, index or trigger. Tools call its checks to refuse what a subsystem's status or the store's reconciliation does not allow. Phase gates and session ends commit the store to git if in a repo.
  • P-03 — Workspace binding, activation and installer: Once bound, calls use one repo and store, except compare_conspectuses. This part picks the workspace once, freezes it in a binding receipt that each valid call rechecks, and builds the store, by default .amanuensis inside the workspace, on first use. Its amanuensis CLI writes the server into Claude, VS Code or Codex configuration, prints steps for other hosts, and copies in the workflow skill.
  • P-04 — Code index: The code index lets a survey session read a codebase by its definitions at any commit: outline_file lists a file's definitions, read_symbol returns one by name with its source, and find_symbol searches a whole revision. add_evidence uses it to anchor a cited symbol to an exact, hashed span. Parses are cached beside the store, keyed by git blob and language.
  • R-01 — Survey scope, ledger and reconciliation: Decides which files the survey must account for and keeps the file ledger in step with them. The survey set is a commit's tree minus excluded paths, including the owner's exclusions and the commit's own ignore files. detect_changes reconciles the ledger against that set at a revision, marking drifted or deleted files stale, and materialize_docs will not render until it has.
  • R-02 — Survey ladder and judgment records: These tools record each subsystem's place on the ladder and the survey's judgments: concern review, seams, terms and open questions. The ladder runs from unmapped to mapped; a phase is granted only once the previous one's deliverables are on record, except when resuming from an unrecorded parking. A disposition is refused before its phase and must cite evidence at revisions that resolve.
  • R-03 — Evidence, claims and findings: Evidence cites a file's lines at a resolved commit; a given symbol is tied to its definition if the code index reads the file. A claim is a typed statement over evidence, valid from one revision until closed there or at a descendant. A finding's resolution history is deleted with the finding on a subsystem reset. Overturning a finding or verifying its fix needs evidence from the session doing it.
  • R-04 — Explanations, narratives and project records: It keeps the survey's prose in the store, not in files. The prose is each subsystem's and the project's purpose and account, the longer narratives, and project-wide records such as the name and runtime crossings.
  • R-05 — Vocabulary contract and parity checks: One JSON contract defines some of the store's constrained vocabularies, each value with its label and meaning; the server and published pages use code generated from it, and the schema's CHECK lists it names must match. Checks compare the skill's instructions with the server: calls in code spans must use tools and arguments the server defines, and each registered refusal must appear in both.
  • W-01 — Change impact, refresh, revalidation and review brief: Keeps recorded claims in step with changing code. It predicts which claims a git range touches and, when applied, closes them at the new revision. A trigger in mcp-server/src/schema.sql opens their revalidations, which only new evidence can satisfy. A refresh run chains these steps unattended and resumes after a crash. A review brief packs one change's impact into a token-bounded context.
  • W-02 — Review sessions, review analysis and composition: These tools support reviewing a change at one assembled HEAD. A composition run checks whether every expected item reached that HEAD and passed its check; only then is it green. In a review analysis, generator, refuter and verifier passes contest each suspected defect. A review session combines both into one exportable list; each item gives an evidence count, and expanding it shows the evidence.
  • W-03 — Decisions, design sessions and codebase brief: Only a human or the owning system can accept a decision revision for an architecture choice. A CodebaseBrief, compiled from one review session without model calls, goes to three independent design lenses. Their options combine into at most a lean, which only advises. Decision-impact detection on an applied change-impact run opens a blocking review for accepted revisions whose premises it touches.
  • W-04 — Research, crosswalk and learning ledger: Outside research and past runs feed later Amanuensis runs, each through a check. A research question goes to Scholiast only if it could move a named decision, and its results stay apart from code claims. A method or lesson from a finished session becomes policy only after a scored test. The crosswalk keeps concepts from different sources distinct until someone resolves them as the same.
  • W-05 — Evaluation, operating envelope and Chorusmith adapter: Amanuensis measures its own method and opens its tools to an orchestrator. An operating envelope says, per repository, mode, context and model, whether the method beat baseline and its controls held. A historical evaluation scores work on past fixes from the pre-fix trees, checked for leaks. The Chorusmith adapter runs allowlisted tools; a run is verified only if it matches calling them directly.
  • W-06 — Legacy import, carried findings and store comparison: Keeps an earlier survey's work when a store is upgraded or rebuilt. The import copies an earlier version's hand-written files into the store verbatim, and fills in the project's purpose, name and runtime table where the store has none. The carry moves prior findings over, and an open one stays undecided until re-filed, ruled out or shown repaired.
