# Code index: find and cite code exactly, alongside reading it

Planned 2026-11-21 on Opus 5.5; revised 2026-11-22 to the owner's decisions (§9). Planning only:
no product code, no lane launched, nothing committed. The lane is cut from `main` at or after
`a6f07d5`, where the store-only lane merged. The executable form of §8 is `plan.json` beside
this file, generated by `make_plan.py` and valid under the store-only lane's `plan-tool.mjs`
(12 packets in 4 slices). The scripts behind §2 are in `baseline/`. Two Codex reviews
(`gpt-6.1-sol`) are in `reviews/`; §12 records every finding and what it changed.

## 0. Summary

**What the owner decided.** The index is a **hybrid**: it adds to file reading and takes nothing
away. Agents use the index to find a definition, see a file's shape, search what the store
already says, and cite code by a checked coordinate; they read whole files whenever they want
context, exactly as today. Because nothing is removed, no default waits on a trial, and the
benchmark of the first draft is gone. Backwards compatibility is not required: stores made
before this release may be discarded, so nothing in this plan exists only to carry old stores
or old evidence forward. It ships as **0.3.0-beta.2**, after store-only's 0.3.0-beta.1.

**Why it is worth building.** Amanuensis has no code index today, so agents locate code with
`rg` and `sed -n` and cite it by hand. In the 78 source-reading sub-sessions of a past survey
catch-up (§2.1), `sed -n` (314 calls) and `rg -n` (301) were the commonest shell commands: the
find-then-slice round trip. The citations that result are loose: a heuristic pass over this repository's
own store, made before planning, found that about half of the code evidence rows name a
`symbol` that is not a definition in the cited file (§2.2).

**What 0.3.0-beta.2 contains.**

1. **A structural code index** inside the Node server: `web-tree-sitter` 0.27.2 (pure
   WebAssembly, no native build) and ten grammars — TypeScript, TSX, JavaScript, Python, Rust,
   Go, Java, C, C++ and C# — vendored as `.wasm` files, with **the index's own definition
   queries** for each, so a definition's span is its whole declaration. Definitions (with a
   language-aware identity, span, signature, doc comment and a hash of the cited text), name-matched
   references and imports are cached in a sidecar database beside the store
   (`<storage>/code-index/<extractor_id>/index.db`), never in the store or its history.
2. **Four read tools.** `outline_file` (a file's definitions and imports, without source),
   `read_symbol` (one definition's source and the location arguments `add_evidence` takes to cite it),
   `find_symbol` (definitions by name or words; references matched by name only, and labelled
   so) and `search_records` (full-text search over the store's current records).
3. **Evidence anchored to definitions.** `add_evidence` keeps its input schema. When `symbol` is
   given for a supported language, the server resolves it at `ref_sha`, refuses a symbol it
   cannot find or cannot tell apart (listing candidates), keeps the cited range and excerpt
   inside that definition, fills the range when it is omitted, stores the canonical symbol id,
   and writes an append-only `evidence_anchors` row in the same transaction.
4. **A refresh hint.** For anchored evidence on a stale file, the backlog says whether the cited
   definition's text is the same, moved, changed, gone, ambiguous or unreadable at the new
   revision, so an agent knows where to look first. It changes no clearing rule.
5. **Skill guidance** that adds the tools to the workflow — locate with the index, cite with
   `read_symbol`'s arguments, read whole files for context whenever useful — and says plainly
   that a name-matched reference is a lead, not proof of a call.
6. **A descriptive token report**, a dev script over the per-call log and, when given them,
   Claude Code transcripts, showing tool-result bytes and tokens before and after on normal
   use (§6). It reports; it decides nothing.

**Install weight.** Ten grammars are 16.8 MB of `.wasm` (1.3 MB gzipped), and `web-tree-sitter`
4.7 MB, on a package that is 4.6 MB unpacked today: about **26 MB installed**, of which the C#
grammar alone is 7.3 MB (§4.8).

**What waits.** Embeddings, SCIP cross-references and ast-grep are later work with no trigger
in this plan; the token report is the evidence the owner can use to decide (§7). Universal
Ctags, multilspy, Joern and Semgrep are out; CodeQL is excluded by its license. Serena cannot be
bundled (GPL-3.0-or-later since v2) and can run beside Amanuensis as a separate MCP server.

**Packets.** 12, SI0–SI11, in four slices: index engine, tools, evidence and refresh, and
skill, report and docs (§8). Sonnet by default; SI2, SI3, SI4, SI6, SI7 and SI8 name Opus.

**Decisions.** The owner settled D1–D6, D10 and D12, and removed the benchmark decisions (§9).
None is open; §9 lists two follow-ups the owner may want to schedule.

## 2. What was measured before planning

Run 2026-11-21. Scripts and outputs: `baseline/`; `results.json` has every number with its
command. These are prototypes; they informed the design and gate nothing.

### 2.1 How agents read code today (transcripts)

`baseline/transcripts.py` pairs each `tool_use` with its `tool_result` in Claude Code
transcripts, classifies the **tool** (read-like: `Read`, shell `cat`, `sed -n`, `head`, `tail`
and similar; search-like: `Grep`, `Glob`, shell `rg`, `grep`, `fd`, `find`; git; Amanuensis
reads and writes; tooling; other), and sums result bytes and `usage`. A shell chain is
classified by its last command. It classifies tools, not targets, so read-like includes reads
of store pages and notes.

Corpus: the 78 sub-sessions of a survey catch-up on 2026-11-11 against a private repository
(not named here): 33 verifications, 34 blind reads, 5 refresh-backlog sessions, 4 traces, 2
other. Read-like results were 57% of tool-result bytes and search-like 18%; of 119 `Read` calls,
98 read a whole file; `sed -n` (314) and `rg -n` (301) were the commonest shell commands. Agents
read a great deal of code, and much of the searching is locating a definition in order to slice
it — the step `find_symbol` and `read_symbol` shorten. Usage: 238.0 M cache-read, 8.0 M
cache-creation and 1.45 M output tokens.

### 2.3 The prototype

`baseline/index.mjs` indexed this repository at `32ad430` with `web-tree-sitter` 0.27.2: 295
files, 7.07 MB, 6,865 definitions and 63,527 references; parse 1.14 s, total 4.1–4.5 s on Node

## 3. The suggestion, revisited

1. **tree-sitter symbols — in the server, with our own definition queries.** The materializer is
   dependency-free Python that only renders; the server already reads git for
   `requireEvidenceCitation`, owns the store, and is what agents call. ast-grep and Ctags add
   nothing for these languages.
2. **SCIP — deferred.** The indexers are separate toolchains and the diagram catalog
   (`design/diagrams/CATALOG.md`) rules call graphs out of the pages. Name-matched references,
   labelled as such, answer "who mentions this name"; resolved references would come through an
   `import_scip` of a user-built `.scip` file if they are ever needed (§7).
3. **Search by meaning — FTS5 now.** BM25 over definitions and over the store's records ships.
   Embeddings are later work; the code embedders named in the brief are not in Ollama's
   official library.
4. **Joern, Semgrep — out; CodeQL — excluded.** Data flow is the survey's work.
5. **Serena — beside, not inside.** It is GPL-3.0-or-later and knows nothing of the store, so it
   cannot anchor evidence or search records. Nothing stops a user running it as a second server.
6. **Order — tree-sitter and FTS5 first.** Measurement is a descriptive report on normal use
   (§6), not a gate in front of the engine.

## 4. Design

### 4.1 The sidecar: a cache keyed by content

`<storage>/code-index/<extractor_id>/index.db`, beside `memory.db`, created on first use. The
`code-index/` directory carries a `.gitignore` of `*` and is excluded from `STORAGE_PATHSPEC`
(`src/storage-git.ts:40`), the call log's pattern. Deleting it is always safe and nothing in
`memory.db` refers to a row in it. `storageManifest` (`src/project.ts:313`) is not touched: it
serves only `migrateLegacyStorage`, which moves stores from a pre-0.3 location, and a sidecar is
only ever created by this release at the current location (D6).

**Keys.** `extractor_id` is the sha256 of the extractor version, the definition-query files and
the grammar manifest. A parse is keyed by `(blob_sha, lang)` inside that generation: the same
bytes under `.ts` and `.js` are two entries. The language comes from the tree entry's path,
never from the cached blob.

**Generations.** Each `extractor_id` has its own directory, so two server versions sharing one
storage directory never rebuild each other's cache. A process using a generation touches its
`last_opened` file when it opens it and at least hourly while it runs. A server starting up
deletes other generations whose `last_opened` is more than 30 days old; a generation in use is
touched within the hour and so is never collected.

**Several processes.** WAL mode, `busy_timeout` 5 s. A blob is parsed outside any transaction
and published in one transaction that inserts its `symbols`, `refs` and `imports` rows and, last,
its `blobs` row; readers treat a blob as indexed only when its `blobs` row exists. Inserts are
`INSERT OR IGNORE` on primary keys, so two processes parsing one blob converge on identical rows
(the extractor is deterministic). A whole-tree index writes `trees` rows in batches and a
`trees_complete(rev, files, skipped)` row last; `find_symbol` reports `partial` until it exists.
Recovery is for corruption only. A busy, locked or unreadable file (`SQLITE_BUSY`,
`SQLITE_LOCKED`, a permission error) leaves the index `unavailable` for that call, and tools say
so. Only `SQLITE_CORRUPT` or `SQLITE_NOTADB`, or a failed `PRAGMA quick_check`, triggers
recovery: the process renames `index.db`, `index.db-wal` and `index.db-shm` together to
`*.corrupt-<time>` and creates a new file. Every process checks the database file's inode before
each request and reopens when it has changed, so a process that had the old file open moves to
the new one; its in-flight writes to the old file are lost, which a cache can afford.

**Tables** (no triggers; it is a cache):

- `blobs(blob_sha, lang, bytes, lines, parse_errors, status, indexed_at)`, PK `(blob_sha, lang)`;
  `status` ∈ `ok`, `parse-partial`, `too-large`, `not-utf8`.
- `symbols(blob_sha, lang, ordinal, symbol_id, name, qname, kind, start_line, end_line,
  occurrence, doc_start_line, start_byte, end_byte, signature, doc, span_sha256)`, PK `(blob_sha, lang,
  ordinal)`. Lines are 1-based and counted by `\n`, as `requireEvidenceCitation` counts them;
  bytes are UTF-8 offsets converted from the WebAssembly binding's UTF-16 offsets.
- `refs(blob_sha, lang, name, kind, line)`, `imports(blob_sha, lang, specifier, line)`.
- `trees(rev, path, mode, blob_sha, lang, skip_reason)` and `trees_complete(rev, files, skipped,
  completed_at)`; the newest eight revisions are kept.
- `symbols_fts` (external content over `symbols`: name and qname split on case and punctuation,
  signature, doc; `porter unicode61`), and the records index of §4.6.

**Reading git.** One long-lived `git cat-file --batch` per request; trees from `git ls-tree -r -z
--full-tree <rev>`. Only modes `100644` and `100755` are parsed; symlinks (`120000`) and gitlinks
(`160000`) are recorded with a `skip_reason`. A missing object (shallow clone, pruned history) is
`unavailable`, never `gone`. Text is decoded as UTF-8 with `fatal: true`; invalid UTF-8 is
`not-utf8`. CRLF is kept: lines split on `\n`.

**Budgets.** 2 MB per file; per whole-tree call 20,000 files (`AMANUENSIS_CODE_INDEX_MAX_FILES`),
200 MB of source and 30 s, past which the call returns what it has with `partial: true` and the
next call resumes; 1 GB per generation on disk, past which blobs not in the newest eight trees
are deleted, oldest first. Each limit is reported when it bites.

**Off switch.** `AMANUENSIS_CODE_INDEX=off`: the four tools are not registered, `add_evidence`
behaves as it does without a symbol, and nothing under `code-index/` is created.

### 4.2 The extractor

`mcp-server/src/code-index/extract.ts`: blob text and language in, a deterministic definition
table out. Definitions come from the index's own queries, `mcp-server/queries/<lang>.scm`, kept
outside `src/` because `npm run build` is `tsc` and copies no `.scm` file; they ship through
`files` and are loaded relative to the package root, the same way as `grammars/`. The
grammars' `tags.scm` serve only references.

| Language | Definitions, each spanning its whole declaration node |
|---|---|
| TypeScript, TSX, JavaScript | function and generator declarations; classes, methods, getters, setters, constructors, fields; interfaces; type aliases; enums; namespaces; top-level `const`/`let`/`var` declarators (arrow functions and object literals included); default exports |
| Python | functions, async functions, classes, methods (decorators in the span); module-level single-name assignments |
| Rust | functions; `impl` blocks and their functions, consts and types; structs, enums, unions, traits and their items; type aliases; consts and statics; modules; `macro_rules!` |
| Go | functions; methods; type specs; top-level consts and vars |
| Java | classes, interfaces, enums, records, annotation types; methods; constructors; fields |
| C | function definitions with their bodies; struct, union and enum specifiers with a body; typedefs; top-level declarations with an initializer; `#define` macros |
| C++ | everything C has, plus namespaces; classes and structs with their members; function definitions in and out of class (`void Foo::bar() {}`), with `template` wrappers in the span; constructors, destructors and operators; declarations without a body — member declarations in a class and namespace-level prototypes such as `void run();` — as kind `declaration`, so a header can be cited; type aliases (`using`); enum classes; concepts |
| C# | namespaces (block and file-scoped); classes, structs, interfaces, records, enums, delegates; methods, constructors, destructors, operators, indexers; properties and events (accessors in the span); fields and constants; a partial method's defining declaration (no body) as kind `declaration` and its implementation as kind `method`; local functions are not definitions |

**Identity.** `qname` is the chain of enclosing definitions (`Class.method`, `module.func`), with
these language rules:

- Go: a method is `<Receiver>.<name>` (pointer stripped).
- Rust: inside `impl T` an item is `T.<name>`; inside `impl Trait for T`, `<T as Trait>.<name>`.
  Duplicate captures of one node collapse.
- C++: `::` is written as `.`. A qualified declarator is relative to its lexical namespace
  chain, so `namespace ns { void Foo::bar() {} }` is `ns.Foo.bar`; a declarator starting with
  `::` is global and takes no lexical prefix. A prototype and its definition share a
  `symbol_id` and differ by kind; in one file they are two occurrences.
- C#: block and file-scoped namespaces are segments. Each declaration of a partial type is a
  file-local fragment: the outline marks it `partial: true`, and its members are qualified by
  the type, whichever file they are in. The two halves of a partial method share a `symbol_id`;
  one is kind `declaration`, the other `method`, and each can be read and cited.
- Overloads share a qname, so `symbol_id` appends a syntactic signature discriminator, never a
  position:
  - Java: parameter types as written: `Parser.parse(String,int)`.
  - C++: parameter types as written, then cv- and ref-qualifiers, and a template's parameter
    count: `Buf.get() const`, `Buf.get() &&`, `make<2>(int)`.
  - C#: generic arity on the method and on each containing type, and parameter modifiers with
    types: ``Cache`1.Get`1(ref int,out string)``.
  - TypeScript overload signatures, Python, Go and Rust have no overloads to tell apart.

`symbol_id` is a stable key across revisions: reordering, inserting or deleting other
definitions never changes it. Where two definitions in one file still share a `symbol_id` (two
`if`-branch definitions of one Python function, a C# partial method's declaration and its
implementation), each is a separate **occurrence**: the outline lists both with their lines, and
a caller picks one with `line_range` (§4.4). `occurrence` (1, 2, … in file order) is a
revision-local label in responses, never part of an identity.

`doc_start_line` extends the span upward over contiguous leading comments (through `export`
wrappers, decorators, attributes and `template` lines), or covers a Python docstring; this
**citeable span** is what `read_symbol` returns and an anchor covers. `span_sha256` hashes the
citeable span's exact bytes, documentation included, so an edit to a leading comment is a
change. `signature` is the first line (≤200 bytes); `doc` ≤2,000 bytes. Any other language is
`unsupported-language`, which every tool reports instead of an empty answer.

### 4.3 Tools

All four are reads, take `ref_sha` (default: workspace HEAD, resolved by
`resolveWorkspaceCommit`), require a bound workspace, and return compact JSON.

- **`outline_file(path, ref_sha?)`**: the file's definitions as a nested list (`symbol_id`, kind,
  lines, signature, first doc line), its imports, `bytes`, `lines`, `blob_sha` and `status`.
- **`read_symbol(path, symbol, ref_sha?, context_lines?)`**: `symbol` is a `symbol_id`, a qname
  or a bare name. One match: its source (doc comment included) with line numbers and
  `evidence_args` — `{ file_path, symbol, ref_sha, line_range }`, the location fields
  `add_evidence` takes, with `symbol` the canonical `symbol_id` and `line_range` the full
  citeable span. They are not a complete call: `add_evidence` also requires `kind`, which only
  the agent can choose (`code-verified`, `comment-asserted`, …), and takes an optional `excerpt`
  and `note`. Several matches: the candidates, no source. None: a refusal listing the nearest
  `symbol_id`s. A definition over 400 lines returns its first 400 lines, its nested definitions'
  outline, `truncated: true` and no `evidence_args`, so a citation never covers source the agent
  was not shown; reading the file, or a nested definition, is the way on.
- **`find_symbol(query, mode?, kind?, path_prefix?, ref_sha?, limit?)`**: `mode` is
  `definitions` (default; BM25 over `symbols_fts`) or `references`. A reference is a place where
  the name appears as an identifier; it is not resolved, so it may be a different thing with the
  same name, and every reference row carries `match: "name"`. Results carry paths, `symbol_id`s,
  lines and signatures, no bodies, and `partial` when the tree index is incomplete.
- **`search_records(query, kinds?, subject?, include_history?, limit?)`**: BM25 over the
  store's records (§4.6). Each hit carries id, kind, subject, status and a 240-byte snippet.

Each tool's refusals get rule ids and rows in `contracts/refusal-parity.json`, and the skill
names each tool so `check-reference-calls.mjs` sees it.

### 4.4 Evidence anchors (in the store)

One new append-only table in `schema.sql`, with its two triggers and a row in
`contracts/append-only-tables.txt`:

```sql
CREATE TABLE IF NOT EXISTS evidence_anchors (
    evidence_id     INTEGER PRIMARY KEY REFERENCES evidence(id) ON DELETE RESTRICT,
    blob_sha        TEXT    NOT NULL,
    lang            TEXT    NOT NULL,
    symbol_id       TEXT    NOT NULL,
    kind            TEXT    NOT NULL,
    def_start_line  INTEGER NOT NULL,   -- doc_start_line: the citeable span's first line
    def_end_line    INTEGER NOT NULL,
    span_sha256     TEXT    NOT NULL,
    extractor_id    TEXT    NOT NULL,
    range_source    TEXT    NOT NULL CHECK (range_source IN ('cited','filled')),
    anchored_at     TEXT    NOT NULL DEFAULT (datetime('now')),
    CHECK (def_start_line >= 1 AND def_end_line >= def_start_line)
);
```

A separate table rather than new columns on `evidence`: the anchor is optional, written once,
and append-only, while `evidence` is not in the append-only contract; and the table needs no
change to any existing write path that does not anchor.

**Input is unchanged.** `add_evidence` keeps `file_path`, `symbol`, `line_range`, `ref_sha`,
`kind`, `excerpt`, `note`, with `additionalProperties: false`. The server re-resolves everything
itself; `read_symbol`'s `evidence_args` fills the location fields, and the agent adds `kind`. With the
index on and a supported language:

- `symbol` resolves (by `symbol_id`, then qname, then a unique bare name): the evidence row's
  `symbol` is stored as the canonical `symbol_id`, and the anchor row is written in the same
  transaction as the evidence row.
  - `line_range` absent: filled with the definition's span (`range_source = 'filled'`).
  - `line_range` present: every span of it (comma lists included) must lie within
    `def_start_line`–`def_end_line`, else a refusal naming both ranges.
  - `excerpt` present: it must be found, by `requireEvidenceCitation`'s matching rules, within
    the definition's exact byte extent intersected with the cited spans — not merely on the
    cited lines, since two definitions can share a line.
- `symbol` matches several definitions: if `line_range` lies within exactly one of them, that
  one is anchored; otherwise refuse, listing each candidate's `symbol_id` and lines.
- `symbol` matches none: refuse, listing up to five nearest `symbol_id`s and saying that a
  free-text label belongs in `note` (D4).
- No `symbol`, an unsupported language, a file the index cannot read, or the index off: no
  anchor, and the write proceeds as it does today. Citing a whole file or a region that is not a
  definition stays available this way.

**Readers of `evidence.symbol`.** Anchored rows hold a `symbol_id`; unanchored rows hold what the
agent wrote. `describe_locus` matches a symbol locus with `e.symbol = ?`
(`src/tools/locus.ts:431`), and the standing block computes its own match
(`src/standing.ts:1049`, exact equality plus a parenthetical-prefix rule). SI7 puts one matcher in
a shared module used by both: a locus symbol matches an evidence row whose `symbol` equals it,
or is a `symbol_id` whose qname or last segment equals it; when a bare name matches more than one
`symbol_id`, both surfaces say so instead of merging them. Every other reader of
`evidence.symbol` is listed in SI7's notes with the change it needs.

**Invariants** (`invariants.ts`): every anchor's evidence row exists; its `symbol` equals the
anchor's `symbol_id`; every span of its `line_range` lies within the anchor's definition span,
and equals it when `range_source = 'filled'`.

**Older stores (D6).** The table is created on open like every other, so a 0.3.0-beta.1 store
opens; its evidence simply has no anchors. Nothing backfills, migrates or reports on old rows. A
store that should have anchored evidence is discarded and surveyed again.

### 4.5 The refresh hint

For each anchored evidence row on a stale ledger file, `get_stale_backlog` (and the refresh plan
built from it) adds `anchor_state` at the target revision:

- `same-text`: exactly one definition with that `symbol_id` and kind, same `span_sha256`, same
  lines;
- `moved`: exactly one, same `span_sha256`, different lines;
- `changed`: exactly one, different `span_sha256` (documentation edits included);
- `gone`: the target blob parsed with status `ok` and has no definition with that `symbol_id`
  (renames are not followed);
- `ambiguous`: more than one definition with that `symbol_id` and kind at the target;
- `unavailable`: absence cannot be shown — the file, blob or grammar cannot be read (missing
  object, `not-utf8`, `too-large`, index off), or the target parsed `parse-partial` and the
  definition is not among what parsed;
- `unanchored`: the evidence row has no anchor.

It says what happened to the cited text, nothing more. A definition with the same text can
behave differently because something it calls, reads or is configured by changed, so
`same-text` is a place to look at the diff around, not a verdict. File-level staleness and
`clear_staleness` are unchanged (`clear_staleness` clears a whole ledger file,
`src/tools/stale.ts:117`), and nothing is cleared automatically.

### 4.6 Records search

`search_records` finds records by text; what it returns is decided by the store's own readers,
called with the bound workspace's HEAD where they take a revision. Per kind:

- claims: as `get_claims` with `query_sha` set to HEAD (`src/tools/claims.ts:793` checks
  revision applicability only when given one), so superseded, invalidated and inapplicable
  claims drop out;
- narratives: as `get_narratives` (`src/tools/narratives.ts:298`, via `readNarratives`): the
  effective row per section and topic, withdrawn keys excluded. That reader applies no revision
  check, and search adds none of its own;
- explanations: as `get_explanations` (`src/tools/explanations.ts:352`): the newest row whose
  `ref_sha` the workspace reaches, with its phase rule (not-recorded below `structural`);
- findings, field notes, open questions and vocabulary: as `get_findings`, `get_field_notes`,
  `get_open_questions` and `lookup_term` return them, with their status.

`include_history: true` adds the rows those readers leave out, each with its status.

Keeping the index current, per source table: append-only tables use a cursor on SQLite `rowid`
(text ids are caller-supplied, so they are not monotonic); tables updated in place (findings;
vocabulary, upserted by `term` at `src/tools/vocabulary.ts:131`; field notes; open questions) are
reconciled by content digest — each call compares `(key, sha256 of indexed text)` for every row
and re-indexes what changed, appeared or vanished. The source list is one constant in
`code-index/records.ts`, checked against `schema.sql` by the gate.

### 4.7 Fit with the store's conventions

- The only new store table is append-only with triggers, written atomically with its evidence
  row, and bound to the row's `ref_sha` through `blob_sha`.
- The sidecar is not a record; its rows are keyed by content and language under an extractor
  generation, so it can lack rows but never contradict a revision.
- The index never writes a claim. It makes evidence coordinates checked facts.
- `outline_file` and `read_symbol` report what the parser saw, labelled with the extractor
  generation, with parse errors reported per file.

### 4.8 Packaging and install weight

- `dependencies`: `web-tree-sitter` pinned exactly (`0.27.2`), with no dependencies and no
  install script. `better-sqlite3` keeps its own install script as today.
- Grammars are not npm dependencies. `mcp-server/grammars/sources.json` pins each grammar
  package's name, version and `sha512` integrity. `scripts/vendor-grammars.mjs` runs `npm pack
  <name>@<version>` into a temporary directory (no install, no scripts), checks the integrity,
  and extracts the `.wasm`, `queries/tags.scm` and `LICENSE` into `mcp-server/grammars/<lang>/`
  (gitignored), writing `grammars/manifest.json` with sha256 and size per file. `prepack` and CI
  run it. The server checks the manifest's hashes when it loads a grammar and refuses one whose
  bytes differ.
- `files` gains `grammars/`, `queries/` and `THIRD_PARTY_NOTICES.md` (in `mcp-server/`).
- Weight, measured: TypeScript 1.41 MB, TSX 1.45, JavaScript 0.41, Python 0.46, Rust 1.10, Go
  0.22, Java 0.41, C 0.63, C++ 3.43 and C# 7.25: **16.8 MB unpacked, 1.32 MB gzipped**. With
  `web-tree-sitter` (4.7 MB, of which 0.37 MB is the runtime) and today's 4.6 MB package, an
  install is about **26 MB**, and the download grows by about 2.5 MB. `test-package-artifact.mjs`

## 6. Seeing the effect: a descriptive token report

The owner asked for one descriptive measure, not a gate: `dev/token-report.mjs` (SI10).

**What it reads.**

- One or more copies of the call log (`<storage>/call-log/calls.db`, layer A, on `main` since
  `21623df`), opened read-only. Each row has the tool, outcome, `args_bytes` and
  `response_bytes`; each connection has its `server_version`.
- Optionally, Claude Code transcript files. The call log sees only Amanuensis's own calls; the
  agent's `Read`, `Grep` and shell reads happen in the host and appear only in its transcripts.
  Without transcripts the report cannot show whether file reading went up or down, and it says
  so in its output.

**What it prints**, split into *before* and *after* by server version (call log) or by a cutover
date or two file lists (transcripts):

- per Amanuensis tool: calls, response bytes (total, median, 90th percentile), refusals;
- per session from transcripts: tool-result bytes by class — the four index tools, other
  Amanuensis reads, `Read` whole-file and sliced, search, shell reads, other — and the four
  `usage` counts, deduplicated by message id, with their sum weighted by the published price
  ratios recorded in the output;
- per-session medians and totals for each side, the number of sessions, and a reminder that the
  two sides differ in task, subject and time, so the comparison is descriptive.

It writes nothing anywhere but standard output (or `--out <file>`) and decides nothing.

**Keeping a "before".** The call log lives in the store directory, and a discarded store takes
its call log with it (D6). It is a WAL database written from a queue after each response, so a
plain file copy of `calls.db` taken while a server runs can miss recent calls. Before discarding
a store or upgrading: stop every Amanuensis server on that store (each flushes its queue at
exit), then take a consistent copy with `sqlite3 <storage>/call-log/calls.db ".backup
before-calls.db"`, and keep the transcripts of a few ordinary sessions. That is the *before*
side; the owner does it, and it is not a packet. A call log alone gives calls, outcomes and
response bytes; token counts and host file reads come only from transcripts.
